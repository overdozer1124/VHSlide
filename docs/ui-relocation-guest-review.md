## 画面確認の範囲

- 3種類のゲスト権限を、1366／1024／810px幅、高さ768pxで確認。別アカウントのブラウザにもPC／タッチの端末設定を適用し、`navigator.maxTouchPoints`で設定を確認した。
- JSON保存と発表が画面内で直接押せること、編集画面の開始位置が104px以内であること、ホスト専用の集合・ゲスト設定がないこと、編集・付箋の有効条件、画面遷移時のページ例外を検査。
- マップ・編集画面のスクリーンショットを保存し、810px幅の担当ゲスト編集画面と閲覧ゲストのマップを目視確認した。小幅の編集ツールバーは横スクロールを使う既存構成で、すべての道具が同時に見えるという意味ではない。
- 新しい画面確認のボタン操作はPlaywrightのclickを使う。タッチ端末のブラウザエミュレーションであり、実Chromebookの指・ペン操作の検証ではない。既存の集合試験の40接続は40台の実端末を描画する試験ではなく、描画ゲストは1つ。

## 発見と対応

### アプリの誤案内

`src/App.tsx`のMapViewへの`onDelete`は、`commit()`が権限エラーでfalseを返しても、その直後に成功通知を出していた。閲覧ゲストへの権限制御は`Cloud.apply`→`assertDeckAccess`で行われるが、エラー通知が成功通知に上書きされる。

v0.61.7での対応は、`commit()`の成功時だけ削除成功を通知すること。権限・削除仕様・保存形式の変更は不要。回帰試験では閲覧ゲストの削除拒否、9枚の維持、エラー文言、サーバー上の作品が変わらないことを確認する。

閲覧者にもマップ内の追加・移動・削除の小ボタン自体が表示される既存構成は残る。今回は操作失敗を成功扱いする問題に限定し、権限ごとの全ボタン非表示化へ範囲を広げない。

### テスト基盤

新たにページ例外を記録したところ、`scopeLogin`の全画面表示拒否の置き換えが、HTMLルート生成前に走ると`document.documentElement`がnullで例外になることを検出。`Element.prototype.requestFullscreen`のテスト専用の置き換えへ変更し、全画面表示を拒否する既存試験条件は維持した。本番コードには含まれない。

## 修正後の検証結果

- `npm test`：アプリ173件、Nodeサーバー18件、成功。
- `npm run build`、`npm run cf:check`：成功。既存のバンドルサイズ警告あり。
- Node：新しいゲスト棚卸し6件成功（PC／タッチ設定）。削除拒否の正しい通知、サーバーの作品不変、ホストの削除成功・Undoも含む。
- Cloudflare相当：棚卸し・ゲスト用メニュー・編集道具・強制フィルタ・集合・対象範囲・復旧の44件成功（PC／タッチ設定）。
- 修正前の追加削除テストはNodeの両設定で失敗し、期待した権限エラーの代わりに「削除しました」が表示されることを確認した。初回棚卸しの6件の失敗は上述のテスト用全画面拒否処理の例外で、修正後はページ例外なし。失敗ログも保存した。
- 棚卸しの初回段階ではNodeの既存38件とCloudflare相当の44件も成功。その時点では追加した削除通知の回帰条件は含まないため、最終版の検証件数と重複して集計しない。
- Cloudflare相当の40接続・描画ゲスト1つ・20サンプルのP95はPC約134.1ms、タッチ設定約134.2ms。ローカルでの測定であり、学校回線や40実端末の性能保証ではない。生の計測値を証拠内に保存した。
