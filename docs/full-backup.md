# 完全バックアップと復元（0.37.2）

0.37.0で追加した機能を0.37.1で改修。[整合性・復元ジョブの設計と試験結果](backup-recovery-fixes.md)も参照。

0.37.2ではZIP生成・読み込み・検証をWeb Workerへ移し、保存時は写真を順番にSTORE形式で格納する。読み込み結果の画像バッファは転送し、検証済みのハッシュを再利用する。Workerは完了・失敗・中断時に終了する。「処理を中断する」はZIP処理を中断する。復元開始後の取り消しは従来どおり専用APIで確定状態を確認し、完成作品を削除しない。Workerを起動できない場合、メインスレッドの同期ZIP処理へ自動的に戻さずエラーを案内する。[応答性とメモリ測定](backup-worker-performance.md)も参照。

クラウド画面の「作品一覧」に追加した。作成者が開いている作品を「完全バックアップを保存」で `.vhslide.zip` に保存し、「バックアップから復元」で内容を確認して**新しい作品**へ戻す。復元にもGoogleサインインが必要。

## 保存するもの

- 全シート・スライド・要素・画像本体・ページ名・フッター。
- 行列の安定IDと見出し、共有者名表示の設定。
- 付箋の本文、配置、色、サイズ、投稿日時、元の投稿者名。
- 共有相手のメールアドレス・参考表示名・範囲別権限・付箋の許可。参加済みの人も、参加前に登録したアカウントも対象。元のホスト自身は共有相手の一覧に含めない。

作品に含まれる個人情報やメールアドレスを含む**暗号化されていないファイル**なので、適切な場所で保管する。

保存対象はサーバーへ保存済みの作品のスナップショット。0.37.1ではRoomとDirectoryの永続リビジョンを確認し、画像取得・ZIP生成後にも再検証する。スライド・付箋・共有設定などが取得中に変わった場合、ZIPを配布せず再実行を案内する。自動で無制限に再試行しない。最終検証の読み取り時点より後の変更は含まない。

自分の未送信スライド更新や保存失敗した付箋がある間は保存できない。バックアップ前に付箋の自動保存を完了させる。別の共同編集者の端末だけに残る未送信の変更や、取得後に行われた編集は含まれない。

## 引き継がないもの

セッション・Googleのトークン・ユーザーID・招待トークン・招待リンク・接続情報は含めない。Undo履歴・削除済みスライド本体・過去の版・端末のフィルタ／ズーム／選択状態も対象外。今回の「完全」は現行作品の画像・付箋・共有設定を含む可搬な保存を意味し、運用DB全体のダンプや版管理ではない。

削除されたスライドを参照する付箋がDBに残っている場合、その付箋もファイルへ保持するが、存在しないスライドを生成するわけではない。

## 復元の確認と権限

復元前に作品名、スライド・画像・付箋・共有の件数を表示する。共有権限は**既定では戻さない**。「共有アカウントと編集権限も確認して復元する」を選ぶと、メールアドレスと編集範囲を一覧で確認できる。

復元した作品のホストは、復元を実行したアカウント。共有を戻す場合、確認したメールアドレスを参加前の共有として登録し、Googleで確認済みのメールアドレスによって参加資格を付与する。バックアップ内のユーザーIDを信用して権限を付けることはしない。元の招待リンクは復活しない。参加者の実表示名は現在のGoogleアカウント情報を使う。

スライド・シートIDと行列の安定IDは、作品の範囲内で保持する。画像URLは新しい作品のアセットURLへ置き換える。付箋IDは新しくし、元の投稿者名に「（復元）」を付けて保存する。復元した付箋の管理上の作者は復元者にするため、元のユーザーIDを流用したなりすましは起きない。

## 容量とファイル形式

ZIPの中身は `manifest.json`、`work.json`、`images/<番号>.bin`。

- `work.json`：`vhslide-backup` version 1。スライドは既存のDeck version 1。
- `manifest.json`：`vhslide-archive` version 1。各ファイルのバイト数・SHA-256・画像の元参照との対応。
- ZIPはSTORE（無圧縮）。元画像が圧縮済みなので再圧縮のCPUを使わず、画像のbase64埋め込みを避ける。
- 全体300MB、メタデータ12MB、画像1点6MB・2000点まで。付箋2000枚、共有相手500件まで。上限超過は失敗として表示し、切り捨てない。
- インポートは期待するファイル名だけを受け付け、重複パス、圧縮形式、宣言サイズの不一致、過剰展開、画像の欠落、SHA-256不一致、不正な要素・権限を拒否する。ファイルをOSの任意パスへ展開しない。

SHA-256は破損検出用であり、出所の証明・電子署名ではない。編集されたファイルをインポートする際もサーバーが構造・写真の所属・所有者を検証する。

復元は画像を1点ずつアップロードする。Cloudflareに300MBのZIPを一括送信・展開する仕組みではない。既存の画像容量上限・作品数上限は維持する。同じアカウントに複製する場合、**元の作品と復元先の両方の容量が必要**。空き不足で復元できない場合も元の作品を削除・上書きしない。APIの操作上限では30秒ずつ最大2回待ち（送信は合計3回まで）、取り消しも可能。

300MB近いファイルの処理はブラウザのメモリを使用する。上限は端末での快適性を保証するものではなく、実Chromebook／iPadでの最大容量試験は未実施。

## 新規作品への復元と失敗時の保護

1. `POST /api/restores`で冪等キー・バックアップの内容識別子・共有の選択を登録し、非公開の復元先を新規作成する。同じ要求・同じ内容と選択の再実行は同じ復元先へ戻る。
2. その作品へ画像をアップロードする。画像本体のSHA-256とジョブIDで保存先を識別し、再送しても重複しない。
3. `POST /api/decks/:id/restore`で作品・付箋・確認済みの共有を確定する。同じ内容の再確定は、同じ完成作品IDを返す。

Nodeでは専用の`restore_jobs`レコード、Cloudflareでは`status=restoring`を検査する。さらに両構成で永続的な`restore_tasks`を保持する。通常作品のIDを指定しても復元で上書きできない。復元中は通常の閲覧・編集・共有・WebSocket接続を拒否し、所有者の画像アップロードと確定／状態確認／取り消しだけを許可する。

NodeはSQLiteトランザクションで作品・付箋・共有設定・ジョブ完了を確定する。CloudflareはRoom内のスナップショット・付箋・確定内容ハッシュをトランザクションで保存し、Directoryの共有設定と公開可能な状態を確定する。Room保存後にDirectoryが失敗しても、同じジョブ・内容でRoomを再作成せず確定を再試行できる。個々のDOをまたぐ一つのDBトランザクションという意味ではない。

**通信エラーでは途中作品を自動削除しない。** まず認証付きのジョブ照会で完成済みか確認する。完成済みなら成功へ復帰し、途中ならサーバーに保持して再開できる。クラウドの「未完了の復元」に表示するので、再読み込み後も同じZIPを選び直して再開できる。ZIP本体をブラウザーへ自動保存しないため、ファイルの再選択は必要。前回共有ありの場合も、再開時に共有のチェックをもう一度確認する。

利用者が明示的に取り消す場合だけ、`DELETE /api/decks/:id/restore`で途中作品と画像を削除する。このAPIは完成作品を削除しない。確定と取り消しを直列化し、確定が先なら取り消しを409で拒否、取り消しが先なら確定を拒否する。削除中に通信が切れた場合も、ジョブの状態を保持し取り消しを再試行できる。削除済みのフラグを残すため、遅延した画像送信による再生成も拒否する。

同じバックアップと共有の選択で再実行した場合、完成済みの同じ作品を開く。別コピーを意図する場合は既存の作品コピー機能を使う。従来のZIP version 1は読み込める。旧版の途中作品はlegacyジョブに移行するが、旧版には内容ハッシュの記録がないため、ファイル一致を新版と同じように自動確認することはできない。

## 旧版の未送信キャッシュ

0.36.1で追加した保護を維持し、0.37.0では読み取り専用の復元画面に専用の案内を追加した。

1. 「未送信の作品をJSONで保存」を押す。
2. ファイルが保存されたことを確認する。
3. 「クラウドの作品に戻る」でクラウドの内容を開き直す。

このJSONは未送信のスライド変更を退避するための従来形式であり、今回の完全バックアップZIPとは別。旧キャッシュを無条件でサーバーへ送ったり、自動で捨てたりしない。

## 主な実装と検証

- `src/backupData.ts`：バックアップの共通データ型・検証・共有情報と付箋の安全な再構成。
- `src/backupArchive.ts`：ZIP生成・上限・ファイル一覧・整合性検証。
- `src/backupClient.ts`、`src/BackupPanel.tsx`：確認画面・配布前検証・画像の逐次復元・ジョブ照会と再開。
- `src/backupProtocol.ts`：共通の永続リビジョン、ジョブ型、SQLマイグレーション。
- `server/app.ts`、`cloudflare/directory.ts`、`cloudflare/room.ts`：ホスト限定の取得、新規作品限定の復元、永続化。
- `src/cloud.ts`、`src/SlideComments.tsx`：付箋保存の待ち合わせと未送信チェック。
- `src/backup.test.ts`：JSON上限を超える27MBの画像バッファ、破損・不正ZIP、認証情報の除外、投稿者の扱い。
- Node／Cloudflareのバックエンドテスト：認可、写真・付箋・安定ID、共有オン／オフ、別作品の画像参照拒否、通常作品の上書き拒否、確定済み作品の取り消し拒否。
- ブラウザテスト：写真と付箋を作成→ZIP保存→共有の確認→新規復元、破損ファイルの拒否、画像送信失敗後の保持・再読み込みによる再開、画像と確定の応答消失からの回復。

公開ルームのデータや実際のGoogleアカウントを使う検証ではなく、独立したテスト環境で確認する。公開サイトへのデプロイは別操作。

### 0.37.0時点の確認結果（履歴）

- 単体77件、Nodeバックエンド10件、Cloudflareバックエンド9件成功。
- 既存のJSON入出力・保存・画像・発表等のブラウザ操作10件成功、端末条件による2件スキップ。
- クラウドUI全体22件成功。最終変更後は、新しいバックアップ・旧キャッシュ復元の4ケースを再実行して成功。
- 本番ビルド成功。既存の500kB超の主JSチャンク警告は残る。ZIP処理は必要になったときに読み込む別チャンク。
- npmの本番依存監査ではQuillの既知のlow警告1件。fflateについての警告は報告されなかった。これは安全性の保証ではなく、Quillの警告を今回修正したものでもない。
- 実端末、実Googleアカウント、公開ルームでの試験・デプロイは実施していない。
