# 段階①フェーズ2 先行検証ハーネス ― 設計と §2.7 対応表

実施計画 v0.5（`docs/stage1-phase2-implementation-plan.md`）第2節の独立認可の設計について、§2.7 先行検証の対象をローカルで試作したもの。**これは模擬層であり、実環境（Cloudflare 検証環境）への配備は行っていない。** §2.7 は各項目について「検証環境での実測を必須とし、未実施は合格としない」と定めているため、本ハーネスの PASS は受入条件の充足ではなく「ローカル模擬での確認」として記録する。実環境でなければ確認できない部分は、下の対応表で「実環境必須」と明示して区別する。

### プラットフォーム経路（`POST /platform/apply`）

- 提示された ID トークンの主体ハッシュ・環境・用途・一回値が、バインディングの固定値と**すべて一致**した場合にだけ動作する。不一致は理由コードつきで拒否（`bad_one_time_value` / `purpose_mismatch` / `env_mismatch` / `approval_expired` / `subject_mismatch`）。
- 照合・nonce 消費・操作IDの消費・登録簿の差し替え・完了記録の作成は RegistryDO の単一 `transactionSync` で行う。消費は**操作ID単位**（用途では一意にしない。全面復旧を繰り返せるため）。
- 初期投入（`bootstrap`）は「初期化済み」の状態で再実行を拒否する（`already_initialized`）。全面復旧（`full-replace`）は初期化済みの登録簿への操作であり、初期化前の状態では拒否する（`not_initialized`）。消費済み操作IDは、旧い一時ビルドを再配置してもサーバー側の状態（`op2_consumed_ops`）で照合して拒否する（`operation_consumed`）。
- **未消費・未期限の操作IDの扱い（定義）**: サーバー側には「発行済みの承認の一覧」が存在しないため、未消費の操作IDを**取り消す手段はない**。旧い一時ビルドが再配置されれば、その操作IDは引き続き実施可能になる（試験で現行の振る舞いとして確認した）。歯止めは有効期限の経過のみである。ただし再配置という行為自体がプラットフォーム経路（アカウント保有者によるデプロイ）であり、実施できるのは信頼境界の内側に限られる。製品実装で承認の取り消し手段（発行一覧の管理や失効リスト等）を設けるかどうかは未解決事項として残す（下記）。
- 一回値は照合のためだけに使い、ストレージには保存しない。完了記録（`op2_completion`）には操作ID・環境・主体ハッシュ・用途・実施時刻を不変に保存する（更新・削除の経路は存在しない）。
- 固定値の照合をすべて通った後にだけ nonce を消費する（拒否で nonce を燃やさない）。
- 試験用の失敗注入（`_fault`: `platform-mid`＝途中失敗、`platform-after-commit`＝コミット後の応答喪失）は、tier=local-mock かつ `ALLOW_TEST_HOOKS=1` のときだけ働く。判定は RegistryDO 自身が行い、Worker の HTTP 入口での剥離と合わせて二重の制限になっているため、DO への直接入口からでも verify 等では起動しない（「試作の制約」5）。なお `platform-mid` の注入位置は「nonce 消費後・登録簿／完了記録の書込み前」であり、**書込み済み内容のロールバックの実証にはならない**。実環境の途中失敗（項目9）は、書込み「後」に例外を投げる故障版ビルド（`fault-builds/apply-after-writes/`）で確認する。
- 期限チェックは apply 処理の入口で行う。期限切れの承認では、他の固定値の照合結果によらず apply へのすべての要求が `approval_expired` で拒否される。確認範囲はこの apply 経路であり、`/nonce` の発行自体は期限切れでも止まらない（発行された nonce は、期限切れの承認では apply が拒否するため消費できない）。

### アプリ側管理ルート（`/admin/*`）

- 運営者セッションは発行しない。操作のたびに新しい ID トークンを検証し、nonce の消費・在籍照合・世代照合・変更の適用を同一トランザクションで行う（2.5）。失効した運営者は次回操作で `not_operator` として拒否される（失効前に用意されたトークンでも同じ）。
- 登録簿の変更（追加・失効・ローテーション）は、提示された `expected_generation` が現在の世代と一致する場合にだけ適用し、適用ごとに世代を1つ進める。古い世代に基づく同時更新は `stale_generation` で拒否される。
- **最後の運営者の失効はアプリ側では行わない**（計画 2.1: 全運営者の緊急失効と、全運営者喪失時の回復はプラットフォーム経路に限定される）。失効の適用前に、同一トランザクションの中で運営者の総数を数え、対象が最後の1人であれば `last_operator` で拒否する。並行する2件の失効（互いを失効させる場合を含む）は世代照合で直列化されるため、すり抜けて登録簿が空になることはない（試験で確認）。ローテーションは削除と追加を同一トランザクションで行い員数が減らないため、この制限の対象外とした。
- 照会の失敗はすべて拒否（fail-closed）。セッションを持たないため、CSRF 対策は Origin の完全一致＋nonce の認証試行コンテキスト（HttpOnly Cookie）結び付け＋ワンタイムなトークン提示で行う（フェーズ1の流儀）。

### モック ID トークンと検証器

- 形式: `mockop|<sub>|<nonce>|<iss>|<aud>|<exp>`（iss の URL に含まれる `.` と衝突しないよう区切りは `|`）。
- ローカル検証器は、実物と同じ項目を明示的に検査する: iss（許可値のみ）、aud（`GOOGLE_CLIENT_ID` と照合、省略しない）、exp（有限数値であることを明示検査し、期限切れを拒否）、nonce・sub の存在。
- **実 Google の経路はモックでは代替できない（実環境確認が必須）**: 次のすべては実環境で確認するまで未確認であり、モックの合格はその代替にならない。
  - **nonce の取得経路**: 試作では自前の `/nonce` が発行した値をモック文字列に埋め込んでいる。実 Google では、nonce はサインイン時に Google 側へ渡し、署名済み ID トークンのクレームとして戻ってくるものであり、その取得・受け渡しの経路自体がモックでは再現されていない。
  - **署名検証**: モック値は署名を持たない。実トークンの署名検証（tokeninfo または JWKS による検証）は未実施。
  - **iss・aud・exp の実物での照合と失敗時の挙動**: 実トークンに対する照合、および検証基盤側の失敗（tokeninfo の応答エラー・不正な応答・到達不能）ときに拒否側に倒れるかどうかは、実環境で確認する。
- 識別子は生の sub を保存せず SHA-256 ハッシュで記録する（フェーズ1の流儀。仮名識別子であり匿名化ではない）。

## §2.7 対応表（ローカル確認の範囲と実環境必須の区別）

| §2.7 項目 | ローカルで確認したこと（試験ランナー） | 実環境必須として残ること |
|---|---|---|
| 1. 固定値との照合 | 主体・環境・用途・一回値の各不一致の拒否、完全一致での初期投入の成功、拒否の連続で状態が変わらないこと | 実環境のバインディング固定と実トークンでの照合 |

## 試作としての解釈（計画に明記がなく、試作側で置いた前提）

1. **プラットフォーム操作でも世代を1つ進める**とした（初期投入で世代 0→1、全面復旧でも +1）。計画 2.5 の世代の記述はアプリ内管理ルートについてのもので、プラットフォーム経路での扱いは明記がない。→ **Codex レビュー（6652438246）で妥当と確認済み**。
2. **全面復旧は初期化前の状態では拒否する**（`not_initialized`）。当初は「初期化前にも適用できる（差し替えとして動作する）」と仮置きしていたが、レビュー指摘を受けて計画 2.1 の区別（初期投入と全面復旧は別の操作）に整合させ、初期化前の全面復旧を拒否する形に改めた。これは仮置きの変更であり、根拠は計画側の区別である。
3. **一時ビルドにも `/nonce` 発行を含めた**（専用経路の認証試行に nonce が必要なため）。→ **Codex レビュー（6652438246）で妥当と確認済み**。
4. 登録簿の読み戻しは、プラットフォーム経路の読み戻し（Data Studio 等）の代替として、DIAG_KEY で守った診断読み取りで代用した（フェーズ1の abort 版 v2 と同じ型）。

## 試作の制約と実環境試験の安全条件

この試作はローカル模擬であり、次の制約を持つ。実環境（検証環境）で試験する際は、ここに挙げた点を安全条件として扱うこと。

1. **nonce の無制限蓄積・無制限発行**: `/nonce` は発行回数の制限も期限切れ行の掃除も持たず、`op2_pending_nonce` に行が貯まり続ける。未使用のまま残った nonce は有効期限（5分）まで有効であり、発行し放題はリプレイの材料と保管肥大を招く。実環境試験では、検証環境を公開しないこと、試験中は発行経路への到達範囲を限定すること、製品実装では発行制限と期限切れ行の削除を入れることが条件になる。
2. **一時秘密の比較方法**: 一回値・DIAG_KEY・ctx の照合は通常の文字列比較であり、定数時間比較ではない（タイミング差の余地が残る）。試作のダミー値では問題にならないが、実環境では承認の有効期限を短く保ち、消費が一度きりであることで被害範囲を限定する前提に立つこと。製品実装で定数時間比較を採るかは未検討事項として残す。
3. **Cookie の Secure 設定**: nonce の認証試行コンテキスト Cookie は `HttpOnly; SameSite=Strict` を付ける。**verify 構成（実環境）では Secure 属性も付ける**よう実装した（両ビルドの /nonce。ローカル模擬は http://localhost 起点のため付けない。属性の有無はローカルテストで確認済み）。残る実環境の確認は、変形B（ブラウザーから見た生成元は `http://localhost:8787`）でブラウザーが Secure つき Cookie を実際に送り返すことの実測である（手順書 v0.3 項目8 手順7、および手順B冒頭の実測確認点）。送り返されない場合は属性を外して進めず、判断を仰ぐ。
4. **運用期限と時計への依存**: 承認の有効期限（`APPROVAL_EXPIRES_AT`）は Worker 側の時計で判定しており、期限の管理そのもの（誰がいつまでに復帰させるか）は試作の範囲外である。実環境試験の安全条件として、承認の有効期限は分単位の短さに保つこと、操作の直後に通常ビルドへ復帰させること、期限切れで拒否されるのは apply 経路の実施だけであり（/nonce 発行は止まらない）、経路の消滅は復帰によって担保するものとして、期限切れに依存して復帰を先送りしないことを、運用条件として明記する。
5. **故障注入フックの制限**: 失敗注入の入力（`_fault`）を受け付けるのはプラットフォーム経路の DO 内2箇所だけであり（途中失敗・コミット後）、通常ビルド側にはフック自体が存在しない。発火条件は tier=local-mock かつ `ALLOW_TEST_HOOKS=1` で、ゲートは (i) Worker の HTTP 入口での `_fault` 剥離と (ii) DO 自身の判定（`faultHooksEnabled()`）の二重である。verify では `ALLOW_TEST_HOOKS=1` の構成自体を設定検証が拒否する（fail-closed）ため、実環境の検証構成でフックが発火する経路はない。試験では、フック無効時の HTTP 入口と DO 直接入口で「500 にならず通常処理され、状態変更は通常分だけ」であること、フック有効時の DO 直接入口で従来どおり発火すること、verify 構成で発火せず消費も起きないことを確認している。なお、この制限はローカル模擬での確認であり、実環境で一時ビルドを配置する際も、故障注入を含む成果物であること自体は変わらない。実環境の途中失敗（§2.7 項目9）はフックではなく故障版ビルド（`fault-builds/apply-after-writes/`、用意済み）で確認する。

## 決定した扱い（レビューで確定したもの）

1. **アプリ側ルートで最後の運営者は失効できない**: 当初は未決定事項として残していたが、レビュー指摘と計画 2.1（全運営者の緊急失効・喪失時の回復はプラットフォーム経路に限定）の整合から、アプリ側では同一トランザクションの計数で拒否する（`last_operator`）形に確定した。全運営者を失効させたい場合・全運営者喪失からの回復は、プラットフォーム経路でのみ行う。

## 付録：不一致試験専用画面（Codex 再レビュー 6715453178 への対応）

項目1の環境不一致・一回値不一致の再試験にあたり、既存の実ログイン画面では「送信直前の実値と応答の対応」を示す証拠を作れない、という Codex の指摘を受けた。送信する JSON の全文表示は ID トークンと一回値を含むため採用しない。代わりに検証専用の最小の画面・スクリプト `public/trial-apply.html` / `tools/trial-apply.mjs` を用意した。

- 送信に使う単一の要求オブジェクトを `buildTrialRequest` で作り、深く凍結する。表示の元と送信する本体はこの同じオブジェクトであり、表示後に差し替えはできない。
- 送信直前に表示するのは試験 ID・試験種別・env_id・purpose・主体の確認事実・一回値の比較事実だけである。ID トークン・一回値・Cookie・nonce・主体ハッシュは表示・ログ・Issue・チャットに出さない。画面のソースにも秘密の項目名そのものが現れない（マニフェストのソース検査で確認）。
- 一回値の比較はブラウザーのメモリー内だけで行い、「一致」／「不一致」の真偽だけを表示する。試験の前提（環境不一致試験は「一致」、一回値不一致試験は「不一致」）を満たさなければ要求を作らず進まない。
- 主体の確認は、アカウント選択での所有者の確認と、ブラウザー内の JWKS 署名検証（`tools/subject-hash-verify.mjs` を再利用）の通過の両方が揃った場合にだけ「主体Aとして確認」と表示する。sub やハッシュの値は表示しない。
- 表示と応答は同一の試験 ID で結んだ試験ログ（`makeTrialLogEntry`）に記録する。応答は HTTP 状態と理由コードだけを含む。
- 表示と実送信の同一性は `verifyDisplayMatchesSent` で送信直前に確認する（表示の env_id・purpose が実際に送る本体のものと一致すること）。試験 `test/trial-apply.test.mjs`（10 件）で、凍結・表示の秘密不出力・表示と実送信の同一性・試験ログの対応・不正入力の拒否を確認した。
- 画面は PC 専用で、提供サーバーが 127.0.0.1:8787 で配信する。どの Worker 版にも含めない。スモーク試験で配信・クライアント ID 差し込み・検証モジュールの配信を確認した（全 10 件）。

## 付録（続）：trial-apply 画面の堅牢化（Codex レビュー 6715525086 への対応）

初版（dc60881a）へのレビューで、2点の修正を求められた。

1. **環境条件の機械検証**：初版は env_id が空でないことしか検証せず、正しい環境IDでも環境不一致試験を送信できた（前回の 201 再発の余地）。修正では、凍結済み要求そのものの env_id を、検証環境に限定して固定した正しい環境ID（`stage1-verification-only-20261101`、秘密ではない）と比べる。環境不一致試験は「異なる」こと、一回値不一致試験は「一致」することを要求し、満たさなければ送信不能（`verifyEnvCondition`、試験で両負例と成功ケースを確認）。入力欄の表示値ではなく、実送信に使う凍結済みの値を検証する。
2. **試行ごとの ID と競合対策**：初版は試験 ID をページ読込時に1個だけ発行し、準備の再実行で使い回していた。修正では、準備の開始ごとに新しい試験 ID を発行し（`createTrialSession`）、前回の保留要求・送信ボタン・表示を新規準備の開始時に無効化する。認証・JWKS取得など非同期処理の古いコールバックは、試行ごとの世代照合で拒否する。準備失敗や二重操作の負例は、セッションの試験（準備失敗での無効化、送信済み試行の再送不能、古い試行の拒否）で確認した。実画面レベルでは、スモーク試験で画面に世代管理の配線があることを確認した（実 GIS の経路は実環境で確認する）。
3. **補足の2点**：主体の確認は、アカウント選択での所有者の申告とトークンの署名検証の通過であり、sub と承認済み主体ハッシュの機械的照合ではない。その区別を表示記録の文言に明記した（主体の機械的照合はサーバー側の subject 判定が行う）。また、応答の理由コードは固定の許可一覧（両ビルドの HttpError が返す試行で観測しうる理由コード）へ正規化してから記録し、一覧にない値は `unexpected_error` に置き換える（`normalizeResponseError`、試験で確認）。
