# 段階①フェーズ2 先行検証ハーネス ― 設計と §2.7 対応表

実施計画 v0.5（`docs/stage1-phase2-implementation-plan.md`）第2節の独立認可の設計について、§2.7 先行検証の対象をローカルで試作したもの。**これは模擬層であり、実環境（Cloudflare 検証環境）への配備は行っていない。** §2.7 は各項目について「検証環境での実測を必須とし、未実施は合格としない」と定めているため、本ハーネスの PASS は受入条件の充足ではなく「ローカル模擬での確認」として記録する。実環境でなければ確認できない部分は、下の対応表で「実環境必須」と明示して区別する。

## 構成

| ファイル | 役割 |
|---|---|
| `src/worker.js` | 通常ビルド。アプリ内管理ルート（計画 2.1/2.5）＋診断読み取り。専用経路 `/platform/apply` は持たない |
| `src/platform-worker.js` | プラットフォーム経路の**一時ビルド**。専用経路 `/platform/apply` はこのビルドにだけ存在する。承認内容は `APPROVAL_*` バインディングとして配置前に固定する（2.3）。RegistryDO と検証ロジックは通常ビルドと同一（生成時に共通部分を共有） |
| `test/run.mjs` | 試験ランナー。Miniflare をプログラムから起動し、一時ビルド→通常ビルドの差し替え（同一永続化ディレクトリ）で「配置→操作→復帰→読み戻し」という実際の手順の順序を再現する |

### プラットフォーム経路（`POST /platform/apply`）

- 提示された ID トークンの主体ハッシュ・環境・用途・一回値が、バインディングの固定値と**すべて一致**した場合にだけ動作する。不一致は理由コードつきで拒否（`bad_one_time_value` / `purpose_mismatch` / `env_mismatch` / `approval_expired` / `subject_mismatch`）。
- 照合・nonce 消費・操作IDの消費・登録簿の差し替え・完了記録の作成は RegistryDO の単一 `transactionSync` で行う。消費は**操作ID単位**（用途では一意にしない。全面復旧を繰り返せるため）。
- 初期投入（`bootstrap`）は「初期化済み」の状態で再実行を拒否する（`already_initialized`）。消費済み操作IDは、旧い一時ビルドを再配置してもサーバー側の状態（`op2_consumed_ops`）で照合して拒否する（`operation_consumed`）。
- 一回値は照合のためだけに使い、ストレージには保存しない。完了記録（`op2_completion`）には操作ID・環境・主体ハッシュ・用途・実施時刻を不変に保存する（更新・削除の経路は存在しない）。
- 固定値の照合をすべて通った後にだけ nonce を消費する（拒否で nonce を燃やさない）。

### アプリ側管理ルート（`/admin/*`）

- 運営者セッションは発行しない。操作のたびに新しい ID トークンを検証し、nonce の消費・在籍照合・世代照合・変更の適用を同一トランザクションで行う（2.5）。失効した運営者は次回操作で `not_operator` として拒否される（失効前に用意されたトークンでも同じ）。
- 登録簿の変更（追加・失効・ローテーション）は、提示された `expected_generation` が現在の世代と一致する場合にだけ適用し、適用ごとに世代を1つ進める。古い世代に基づく同時更新は `stale_generation` で拒否される。
- 照会の失敗はすべて拒否（fail-closed）。セッションを持たないため、CSRF 対策は Origin の完全一致＋nonce の認証試行コンテキスト（HttpOnly Cookie）結び付け＋ワンタイムなトークン提示で行う（フェーズ1の流儀）。

### モック ID トークンと検証器

- 形式: `mockop|<sub>|<nonce>|<iss>|<aud>|<exp>`（iss の URL に含まれる `.` と衝突しないよう区切りは `|`）。
- ローカル検証器は、実物と同じ項目を明示的に検査する: iss（許可値のみ）、aud（`GOOGLE_CLIENT_ID` と照合、省略しない）、exp（有限数値であることを明示検査し、期限切れを拒否）、nonce・sub の存在。
- **署名検証だけはモックでは代替できない**（モック値は署名を持たない）。実 Google トークンでの署名検証は実環境必須。
- 識別子は生の sub を保存せず SHA-256 ハッシュで記録する（フェーズ1の流儀。仮名識別子であり匿名化ではない）。

## §2.7 対応表（ローカル確認の範囲と実環境必須の区別）

| §2.7 項目 | ローカルで確認したこと（試験ランナー） | 実環境必須として残ること |
|---|---|---|
| 1. 固定値との照合 | 主体・環境・用途・一回値の各不一致の拒否、完全一致での初期投入の成功、拒否の連続で状態が変わらないこと | 実環境のバインディング固定と実トークンでの照合 |
| 2. 原子的な一回消費 | 二重実施の拒否（409）、並行実施6件で成功が正確に1件、旧ビルド再配置での消費済み操作IDの再利用拒否、別操作IDでの初期投入の二重拒否（初期化済み） | 実 Durable Object 上での並行性の実測 |
| 3. 値の漏洩を想定した試験 | 一回値を正しく知っていても対象以外の主体は `subject_mismatch` で拒否される | 実際の値の生成・保管・共有範囲の運用確認 |
| 4. 期限切れの拒否 | 期限が過去の承認は `approval_expired` で全要求を拒否 | 実環境での期限経過後の旧ビルドの振る舞い |
| 5. 終了手順 | 通常ビルドへの復帰後に専用経路が 404 になること（特定の要求条件での経路消滅の観察のローカル代替）、診断読み取りによる登録簿の読み戻しが承認内容と一致すること | 実際のデプロイ復帰、プラットフォーム経路（Data Studio 等）での読み戻し、実配置での経路消滅の観察 |
| 6. 失効と世代 | 失効した運営者の次回操作の拒否、失効前に用意した同一トークンの拒否、古い世代に基づく更新の拒否、同じ世代への並行更新で正確に1件だけ成功、ローテーション元／先の可否 | 実環境の Directory DO での直列化の実測 |
| 7. 失敗手順の実施 | 応答喪失を想定した手順の形（再送せず読み戻しで未消費を確認してから再実施できること）はローカルで確認 | 応答喪失の実発生下での判断、復帰失敗時の別経路（API／Wrangler／ダッシュボード）での再試行は、ローカルでは再現不能なため未実施 |
| 8. トークン検証とリプレイ対策 | iss・aud・exp（有限数値検査を含む）・nonce・主体の照合、同一 nonce の再送拒否（`nonce_replayed`）、コンテキスト不一致の拒否と拒否時の非消費、Origin 不一致の拒否 | **署名検証**、実 Google トークンでの一連の確認、環境識別の信頼できる根拠（配置時の対象照合という手順側の担保） |
| 9. 途中失敗・異主体・並行消費 | 失敗注入による途中失敗でトランザクションがロールバックし状態がすべて元に戻ること、固定対象と異なる主体の拒否、並行消費で正確に1件だけ成功 | 実環境での途中失敗（実環境では障害版ビルド等の手段が必要。フェーズ1と同じ制約） |

### §5 のフェーズ1引き継ぎ項目との関係

- (ii) 同一 nonce の再送の拒否: 本ハーネスの管理ルートでローカル確認済み（上表の項目8）。実環境での確認は別途必要。
- (i) A2/A7 の原子性、(iii) 並行初回登録、(iv) 保持済み旧セッションの拒否: これらは製品実装（手順4）の受入条件であり、本ハーネス（運営者認可の先行検証）の対象外。なお (iv) について、運営者認可はセッションを持たない設計のため、運営操作については「保持済み旧セッション」に相当するものが存在せず、失効は次回操作で効くことを項目6で確認した。製品の利用者セッションに対する拒否は製品側で別途確認する。

## 試作としての解釈（計画に明記がなく、試作側で置いた前提）

1. **プラットフォーム操作でも世代を1つ進める**とした（初期投入で世代 0→1、全面復旧でも +1）。計画 2.5 の世代の記述はアプリ内管理ルートについてのもので、プラットフォーム経路での扱いは明記がない。
2. **全面復旧は初期化前の状態にも適用できる**とした（差し替えとして動作し、初期化済みになる）。実務上は初期投入と区別される想定だが、計画に明記がない。
3. **一時ビルドにも `/nonce` 発行を含めた**（専用経路の認証試行に nonce が必要なため）。実環境の一時ビルドの構成要素として妥当かは、レビューで確認したい。
4. 登録簿の読み戻しは、プラットフォーム経路の読み戻し（Data Studio 等）の代替として、DIAG_KEY で守った診断読み取りで代用した（フェーズ1の abort 版 v2 と同じ型）。

## 未決定として残す事項（勝手に決めていない）

1. **アプリ側ルートで最後の運営者を失効できるか**: 計画に明記がない。現行の試作ルールでは自己失効を含め可能であり、全運営者喪失がアプリ側からも起こり得る（全面復旧で回復可能ではある）。禁止するかどうかは判断が必要。
2. 上記「試作としての解釈」1〜3 は、レビューで覆る前提の仮置きである。
3. 計画 §6 の未確定事項（監査ログの必須／任意、本番での sub の記録方法）は、本ハーネスでは前提にしていない。試作は完了記録と消費記録を持つが、それが監査ログの要否判断を代替するものではない。
4. 一回値の照合は通常の文字列比較である。定数時間比較などのタイミング対策は、実環境実装時の検討事項として残す。
