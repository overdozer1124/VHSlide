# 段階①フェーズ2 先行検証ハーネス ― 設計と §2.7 対応表

実施計画 v0.5（`docs/stage1-phase2-implementation-plan.md`）第2節の独立認可の設計について、§2.7 先行検証の対象をローカルで試作したもの。**これは模擬層であり、実環境（Cloudflare 検証環境）への配備は行っていない。** §2.7 は各項目について「検証環境での実測を必須とし、未実施は合格としない」と定めているため、本ハーネスの PASS は受入条件の充足ではなく「ローカル模擬での確認」として記録する。実環境でなければ確認できない部分は、下の対応表で「実環境必須」と明示して区別する。

### プラットフォーム経路（`POST /platform/apply`）

- 提示された ID トークンの主体ハッシュ・環境・用途・一回値が、バインディングの固定値と**すべて一致**した場合にだけ動作する。不一致は理由コードつきで拒否（`bad_one_time_value` / `purpose_mismatch` / `env_mismatch` / `approval_expired` / `subject_mismatch`）。
- 照合・nonce 消費・操作IDの消費・登録簿の差し替え・完了記録の作成は RegistryDO の単一 `transactionSync` で行う。消費は**操作ID単位**（用途では一意にしない。全面復旧を繰り返せるため）。
- 初期投入（`bootstrap`）は「初期化済み」の状態で再実行を拒否する（`already_initialized`）。全面復旧（`full-replace`）は初期化済みの登録簿への操作であり、初期化前の状態では拒否する（`not_initialized`）。消費済み操作IDは、旧い一時ビルドを再配置してもサーバー側の状態（`op2_consumed_ops`）で照合して拒否する（`operation_consumed`）。
- **未消費・未期限の操作IDの扱い（定義）**: サーバー側には「発行済みの承認の一覧」が存在しないため、未消費の操作IDを**取り消す手段はない**。旧い一時ビルドが再配置されれば、その操作IDは引き続き実施可能になる（試験で現行の振る舞いとして確認した）。歯止めは有効期限の経過のみである。ただし再配置という行為自体がプラットフォーム経路（アカウント保有者によるデプロイ）であり、実施できるのは信頼境界の内側に限られる。製品実装で承認の取り消し手段（発行一覧の管理や失効リスト等）を設けるかどうかは未解決事項として残す（下記）。
- 一回値は照合のためだけに使い、ストレージには保存しない。完了記録（`op2_completion`）には操作ID・環境・主体ハッシュ・用途・実施時刻を不変に保存する（更新・削除の経路は存在しない）。
- 固定値の照合をすべて通った後にだけ nonce を消費する（拒否で nonce を燃やさない）。
- 試験用の失敗注入（`_fault`: `platform-mid`＝途中失敗、`platform-after-commit`＝コミット後の応答喪失）は、tier=local-mock かつ `ALLOW_TEST_HOOKS=1` のときだけ働く。判定は RegistryDO 自身が行い、Worker の HTTP 入口での剥離と合わせて二重の制限になっているため、DO への直接入口からでも verify 等では起動しない（「試作の制約」5）。なお `platform-mid` の注入位置は「nonce 消費後・登録簿／完了記録の書込み前」であり、**書込み済み内容のロールバックの実証にはならない**。実環境の途中失敗（項目9）は、書込み「後」に例外を投げる故障版ビルド（`fault-builds/apply-after-writes/`）で確認する。
- 期限チェックは apply 処理の入口で行う。期限切れの承認では、他の固定値の照合結果によらず apply へのすべての要求が `approval_expired` で拒否される。確認範囲はこの apply 経路であり、`/nonce` の発行自体は期限切れでも止まらない（発行された nonce は、期限切れの承認では apply が拒否するため消費できない）。

### アプリ側管理ルート（`/admin/*`）

- 運営者セッションは発行しない。操作のたびに新しい ID トークンを検証し、nonce の消費・在籍照合・世代照合・変更の適用を同一トランザクションで行う（2.5）。失効した運営者は次回操作で `not_operator` として拒否される（失効前に用意されたトークンでも同じ）。
- 登録簿の変更（追加・失効・ローテーション）は、提示された `expected_generation` が現在の世代と一致する場合にだけ適用し、適用ごとに世代を1つ進める。古い世代に基づく同時更新は `stale_generation` で拒否される。
- **最後の運営者の失効はアプリ側では行わない**（計画 2.1: 全運営者の緊急失効と、全運営者喪失時の回復はプラットフォーム経路に限定される）。失効の適用前に、同一トランザクションの中で運営者の総数を数え、対象が最後の1人であれば `last_operator` で拒否する。並行する2件の失効（互いを失効させる場合を含む）は世代照合で直列化されるため、すり抜けて登録簿が空になることはない（試験で確認）。ローテーションは削除と追加を同一トランザクションで行い員数が減らないため、この制限の対象外とした。
- 照会の失敗はすべて拒否（fail-closed）。セッションを持たないため、CSRF 対策は Origin の完全一致＋nonce の認証試行コンテキスト（HttpOnly Cookie）結び付け＋ワンタイムなトークン提示で行う（フェーズ1の流儀）。

### モック ID トークンと検証器

- 形式: `mockop|<sub>|<nonce>|<iss>|<aud>|<exp>`（iss の URL に含まれる `.` と衝突しないよう区切りは `|`）。
- ローカル検証器は、実物と同じ項目を明示的に検査する: iss（許可値のみ）、aud（`GOOGLE_CLIENT_ID` と照合、省略しない）、exp（有限数値であることを明示検査し、期限切れを拒否）、nonce・sub の存在。
- **実 Google の経路はモックでは代替できない（実環境確認が必須）**: 次のすべては実環境で確認するまで未確認であり、モックの合格はその代替にならない。
  - **nonce の取得経路**: 試作では自前の `/nonce` が発行した値をモック文字列に埋め込んでいる。実 Google では、nonce はサインイン時に Google 側へ渡し、署名済み ID トークンのクレームとして戻ってくるものであり、その取得・受け渡しの経路自体がモックでは再現されていない。
  - **署名検証**: モック値は署名を持たない。実トークンの署名検証（tokeninfo または JWKS による検証）は未実施。
  - **iss・aud・exp の実物での照合と失敗時の挙動**: 実トークンに対する照合、および検証基盤側の失敗（tokeninfo の応答エラー・不正な応答・到達不能）ときに拒否側に倒れるかどうかは、実環境で確認する。
- 識別子は生の sub を保存せず SHA-256 ハッシュで記録する（フェーズ1の流儀。仮名識別子であり匿名化ではない）。

## §2.7 対応表（ローカル確認の範囲と実環境必須の区別）

| §2.7 項目 | ローカルで確認したこと（試験ランナー） | 実環境必須として残ること |
|---|---|---|
| 1. 固定値との照合 | 主体・環境・用途・一回値の各不一致の拒否、完全一致での初期投入の成功、拒否の連続で状態が変わらないこと | 実環境のバインディング固定と実トークンでの照合 |

## 試作としての解釈（計画に明記がなく、試作側で置いた前提）

1. **プラットフォーム操作でも世代を1つ進める**とした（初期投入で世代 0→1、全面復旧でも +1）。計画 2.5 の世代の記述はアプリ内管理ルートについてのもので、プラットフォーム経路での扱いは明記がない。→ **Codex レビュー（6652438246）で妥当と確認済み**。

## 試作の制約と実環境試験の安全条件

この試作はローカル模擬であり、次の制約を持つ。実環境（検証環境）で試験する際は、ここに挙げた点を安全条件として扱うこと。

1. **nonce の無制限蓄積・無制限発行**: `/nonce` は発行回数の制限も期限切れ行の掃除も持たず、`op2_pending_nonce` に行が貯まり続ける。未使用のまま残った nonce は有効期限（5分）まで有効であり、発行し放題はリプレイの材料と保管肥大を招く。実環境試験では、検証環境を公開しないこと、試験中は発行経路への到達範囲を限定すること、製品実装では発行制限と期限切れ行の削除を入れることが条件になる。
2. **一時秘密の比較方法**: 一回値・DIAG_KEY・ctx の照合は通常の文字列比較であり、定数時間比較ではない（タイミング差の余地が残る）。試作のダミー値では問題にならないが、実環境では承認の有効期限を短く保ち、消費が一度きりであることで被害範囲を限定する前提に立つこと。製品実装で定数時間比較を採るかは未検討事項として残す。
3. **Cookie の Secure 設定**: nonce の認証試行コンテキスト Cookie は `HttpOnly; SameSite=Strict` を付ける。**verify 構成（実環境）では Secure 属性も付ける**よう実装した（両ビルドの /nonce。ローカル模擬は http://localhost 起点のため付けない。属性の有無はローカルテストで確認済み）。残る実環境の確認は、変形B（ブラウザーから見た生成元は `http://localhost:8787`）でブラウザーが Secure つき Cookie を実際に送り返すことの実測である（手順書 v0.3 項目8 手順7、および手順B冒頭の実測確認点）。送り返されない場合は属性を外して進めず、判断を仰ぐ。
4. **運用期限と時計への依存**: 承認の有効期限（`APPROVAL_EXPIRES_AT`）は Worker 側の時計で判定しており、期限の管理そのもの（誰がいつまでに復帰させるか）は試作の範囲外である。実環境試験の安全条件として、承認の有効期限は分単位の短さに保つこと、操作の直後に通常ビルドへ復帰させること、期限切れで拒否されるのは apply 経路の実施だけであり（/nonce 発行は止まらない）、経路の消滅は復帰によって担保するものとして、期限切れに依存して復帰を先送りしないことを、運用条件として明記する。
5. **故障注入フックの制限**: 失敗注入の入力（`_fault`）を受け付けるのはプラットフォーム経路の DO 内2箇所だけであり（途中失敗・コミット後）、通常ビルド側にはフック自体が存在しない。発火条件は tier=local-mock かつ `ALLOW_TEST_HOOKS=1` で、ゲートは (i) Worker の HTTP 入口での `_fault` 剥離と (ii) DO 自身の判定（`faultHooksEnabled()`）の二重である。verify では `ALLOW_TEST_HOOKS=1` の構成自体を設定検証が拒否する（fail-closed）ため、実環境の検証構成でフックが発火する経路はない。試験では、フック無効時の HTTP 入口と DO 直接入口で「500 にならず通常処理され、状態変更は通常分だけ」であること、フック有効時の DO 直接入口で従来どおり発火すること、verify 構成で発火せず消費も起きないことを確認している。なお、この制限はローカル模擬での確認であり、実環境で一時ビルドを配置する際も、故障注入を含む成果物であること自体は変わらない。実環境の途中失敗（§2.7 項目9）はフックではなく故障版ビルド（`fault-builds/apply-after-writes/`、用意済み）で確認する。

## 決定した扱い（レビューで確定したもの）

1. **アプリ側ルートで最後の運営者は失効できない**: 当初は未決定事項として残していたが、レビュー指摘と計画 2.1（全運営者の緊急失効・喪失時の回復はプラットフォーム経路に限定）の整合から、アプリ側では同一トランザクションの計数で拒否する（`last_operator`）形に確定した。全運営者を失効させたい場合・全運営者喪失からの回復は、プラットフォーム経路でのみ行う。

## 付録（続々々）：現行試行の失敗時の password 欄の消去（Codex レビュー 6715858226 への対応）

再レビュー（seq 472）で、現行試行の失敗時に一回値入力欄が残ることが指摘された。`onGoogleSignIn` の現行世代の catch は `session.failAttempt(...)` で現行試行を無効化してから finally に入るため、finally の `session.isCurrent(...)` が false になり、署名検証失敗や環境条件失敗などで入力済みの一回値2欄が消去されずに残った。

## 付録（続々々々）：S4/S5 試験準備（Codex レビュー 6720499137 への対応）

S4〜S8 の計画共有（Issue 6720491936）に対する Codex のレビュー（seq 496、Issue 6720499137）の要求を受け、S4 以降の試験画面と並行要求の方法・証拠取得方法を先に共有するための準備である。実環境での承認作成・試験はこの作業の範囲外であり、レビュー後に承認固定へ進む。

### S4 画面の仕組み（trial-apply 画面の拡張）

新画面は作らず、既存の trial-apply 画面を拡張した。理由は、S4 の2試験は「固定値照合と nonce context を通過した上での状態による拒否」という点で不一致試験と同じ形の単一要求の試験であり、seq 466/469/472 で積み重ねた堅牢化（凍結要求・送信前表示・試験 ID による表示と応答の結び付け・per-attempt ID と generation ガード・送信中の準備禁止・現行試行の失敗時に password 欄を無効化の前にクリアする）をそのまま再利用できるからである。

- 試験種別は `TRIAL_KINDS` に2種を追加した。`operation-consumed`（期待する応答は 409 `operation_consumed`）と `already-initialized`（期待する応答は 409 `already_initialized`）である。
- 用途は試験種別で決まる固定値である（`purposeForKind`）。不一致試験は full-replace、S4 の2試験は bootstrap である。画面で用途を手入力できないため、用途の誤りによる試験の混線は起きない。
- 一回値の比較事実も試験種別で決まる固定値である（`expectedOneTimeFact`）。環境不一致試験は「一致」、一回値不一致試験は「不一致」、S4 の2試験は「一致」である。S4 の2試験は、固定値（環境・用途・一回値）が承認内容と一致することが前提であり、拒否が状態（消費済み／初期化済み）によるものであることを示すためである。
- 環境条件は、S4 の2試験では固定した正しい環境 ID と一致することを凍結済み要求に対して機械的に検証する（`verifyEnvCondition` の拡張）。不一致の場合は送信不能である。
- 証拠は従来どおり、試験 ID で結んだ試験ログ（表示と応答の対応）である。応答は HTTP 状態と理由コードだけを含む。`operation_consumed`・`already_initialized` は応答エラー正規化の許可一覧に既に含まれており、記録される。
- S4 の `operation_consumed` 試験の方法上の区別を、ローカルでも確認した。`test/run.mjs` に追加したチェックでは、消費済みの操作 ID を新しい有効期限と新しい一回値で固定した別版（検証環境の未配信版に相当）を一時ビルドに読み込み、その版で apply すると 409 `operation_consumed` が返り、状態（消費1・完了1・世代1）が変わらないことを確認した。これは旧版そのものの再配置とは異なる証拠であり、旧版の再配置の試験（S6）とは区別する。

### S5 並行送信の方法

#### 制約（正面から解決する点）

nonce context は `/nonce` 発行時に設定される Secure; HttpOnly; SameSite=Strict の Cookie（`op2_nonce_ctx`）で結び付く。ブラウザーの fetch では Cookie ヘッダーを任意に設定できない（forbidden header）ため、単一ブラウザー・単一プロファイルから6要求それぞれに異なる nonce context Cookie を送ることはできない。同じプロファイルで6件の nonce を発行しても、最後に発行された ctx だけが送られ、他の5件は `nonce_context_mismatch` で失敗する。S5 の並行送信方法はこの制約を正面から解決する。

証拠の区別（Codex レビュー 6734640413 の指摘3）：属性値そのもの（Secure / HttpOnly / SameSite=Strict）の実環境での実測元は存在しない。実環境の Set-Cookie ヘッダー値は記録されていないため、実環境では未確認である。上の属性の記述はソース（両ビルドの /nonce が verify 構成で Secure を付ける箇所）とローカル試験だけが根拠であり、実測したものとして扱わない。一方、Cookie の返送は S9 正常系の実施記録（Codex seq 632/634：GET /nonce 200、POST /admin/verify-only 200 ok）で実証済みである。ctx が一致しなければ 403 nonce_context_mismatch になるため、200 ok は Cookie が返送され ctx が一致したことの実証である。

#### 採用案：画面で6つの実トークンを取得し、Cookie jar を分けた Node 送信スクリプトで並行送信する

- 画面（`public/s5-apply.html`）：6スロット分の準備を順に行う。6件分の nonce をまとめて取得し、各スロットで GIS ログイン（A のみ）を行い、実トークンを JWKS で署名検証する（`tools/subject-hash-verify.mjs` を再利用）。6件の要求を凍結し、送信直前に6件の条件（env_id・purpose・一回値）が等しいことと nonce が異なることを表示して、その同じ6件の要求を送信指示として送信器へ渡す。送信する JSON の全文表示はしない。
- 送信器（`tools/s5-sender.mjs`、Node 専用でブラウザーには配信しない）：スロットごとに Cookie jar を分ける。送信前に、(a) 準備済みであること、(b) nonce の発行開始から4分以内であること（nonce の TTL は5分。期限切れのまま送信しない。起点は6件の発行を始めた時刻であり、応答の受信時刻ではない）、(c) 6件の要求が揃っていること、(d) 6件の条件が等しいこと、(e) 各スロットのトークンの nonce 申告値が発行した nonce と一致すること、を確認する。いずれかが満たされなければ1件も送らない。確認が通れば6件を `Promise.all` で並行送信し、各スロットに自分の ctx を `Cookie: op2_nonce_ctx=<ctx>` として付ける。送信の完了直後に保持（nonce・ctx・トークン・一回値）を破棄する。
- トークン・一回値・Cookie・nonce の値は表示・記録・Issue／チャットへ送らない。画面のソースにも秘密の項目名そのものが現れない（マニフェストのソース検査で確認）。トークン・一回値は提供サーバーのメモリー内だけを通る（既存の /platform/apply 中継と同じ範囲）。
- GIS の `initialize` は1つの設定しか持たないため、画面はスロットごとに再初期化・再描画してボタンを切り替える。実ブラウザーでの連続再初期化のふるまいは PC 側での確認項目であり、jsdom では確認できない。

#### 却下案

- **6つの別ブラウザプロファイル／プライベートウィンドウ（各プロファイルが自分の nonce・Cookie・GIS トークンを持つ）**：却下。手動のクリックでは6件の送信を飛行中に重ねられず（同時性の証拠にならない）、6画面のログの対応付けが脆く、送信前に「他の条件が等しいこと」を1か所で機械的に確認する仕組みがない。並行性の証拠として弱い。
- **単一プロファイルで6件の nonce を発行し、ブラウザーの fetch で順に送る**：却下。上記の Cookie 制約により、最後の ctx だけが送られ、他の5件は `nonce_context_mismatch` で失敗する。並行消費の証拠にならない。
- **画面で6件の要求を作り、送信は画面の fetch で1件ずつ行う**：却下。同じ Cookie 制約に加え、順次送信では「並行」の証拠にならない。

#### 証拠の取り方

- 送信前の表示：6件の条件が等しいこと（env_id・purpose・一回値の比較事実）と、nonce が6件とも異なること（値そのものではなく「異なる」という事実）。表示と送信指示は同じ凍結済み6件の要求から作る（`verifyS5DisplayMatchesSent`）。
- 送信結果：スロットごとに {status, error} を記録し、試験 ID で表示と結ぶ。応答がなかったスロットは `no_response`（送信器内の局所的な符号。Worker の応答コードではない）として記録し、再送しない。集計は `aggregateS5Results` で、201 が正確に1件・残り5件が 409 `operation_consumed` の場合にだけ成功とする。
- 状態の差分：送信前後の Data Studio 読み戻しで、世代 +1（1→2）、消費に新しい操作 ID が追加、完了 +1、operator 行の更新を確認する。S4 の2試験は状態不変が期待値であり、前後の読み戻しで確認する。

### S6・S7・S8 の扱い

- S6（旧版の再配置）は、期限切れ旧版の `approval_expired` が旧版再配置後の期限拒否のみを示し、消費済み ID の拒否の証明にはならない、という限界を維持する。S4 の別版による消費済み拒否を独立の証拠とする。期限内の実際の消費済み版を安全に再配置できる場合は、追加観察として検討する。
- S7（期限切れ実測と未消費記録）と S8（復帰・読戻し）は、Codex のレビューで異議がなかったため、従来の方法のまま行う。S7 の承認は未消費台帳の3件目として記録する。

## 付録（続々々々々）：S5 送信器の修正（Codex レビュー 6720755818 への対応）

S4/S5 試験準備の共有（Issue 6720746656、コミット 1f679e96）に対する Codex のレビュー（seq 499、Issue 6720755818）で、S5 送信器に4点の修正を求められた。S4 の画面拡張と、S5 で nonce/context をスロットごとに分ける方向は妥当とされた。S5 の実環境試験は修正確認まで保留である。

### 1. リダイレクト追従による秘密流出

`tools/s5-sender.mjs` の `/platform/apply` への fetch は `redirect` を指定せず既定で追従していた。307/308 でローカル中継が外部 URL を返すと、ID トークン・一回値・Cookie を含む POST が転送され得る。修正では、既存の `serve-real.mjs` の中継と同じく `redirect: "manual"` を明示し、3xx は追従せず再送なしの失敗（局所コード `redirect_not_followed`、スロットごとの {status, error} として記録）として処理する。`/nonce` も同様に 3xx 非追従とし、3xx は発行失敗（`s5_nonce_issuance_failed`）として扱う。

実行試験（`test/s5-sender.test.mjs`）：偽の fetch で /platform/apply が 307 を返す場合に、6件とも 307・`redirect_not_followed` として記録され、実リダイレクト先へは要求せず、Worker の状態が変わらないこと（世代1・消費1・完了1）を確認した。/nonce が 307 を返す場合に、発行が失敗し、リダイレクト先へは要求せず、/nonce への要求は1回だけであることも確認した。fetch に `redirect: "manual"` が指定されることも、偽の fetch 側で確認した。

### 2. 並行 send・nonce 再発行の競合

修正前は、send が `issued` を保持したまま `await Promise.allSettled(...)` し、最後に `clear()` していたため、複数の `/s5/send` が同時に来れば同じ6枠を2回発行できた。UI ボタンの無効化だけでは送信器の排他にならない。修正では、発行中・送信中の状態を `busy`（"issuing" / "sending" / null）で同期的に管理する。入力の検証後・送信前に、最初の await の前に同期的に発行状態を消費して送信中へ遷移する（`issued = null; busy = "sending"`）。重複の send、送信中の nonce 再発行、並行 issue の競合は `s5_busy` で拒否する。応答喪失・失敗時も自動再送しない（喪失したスロットは `no_response` として記録し、送信後の再送は `s5_not_prepared` で拒否する）。

実行試験（`test/s5-sender.test.mjs`）：応答を 200ms 遅らせた偽の fetch で、送信中に2件目の send を呼ぶと `s5_busy` で拒否され、6件の apply 呼び出しは正確に6回だけであること（1件の 201 と5件の 409 operation_consumed、世代2）を確認した。送信中の nonce 再発行は `s5_busy` で拒否され、送信が終われば改めて発行できること、並行する2件の issue は1件だけが成功すること、応答喪失時は再送せず `no_response` として記録されること（各スロットは1回だけ送られ、集計は不成立）を確認した。

### 3. ローカル入口の呼出し元境界

修正前は、`/s5/nonces` と `/s5/send` にローカルサーバー側の呼出し元制限がなく、共有の送信器状態を別オリジンからの GET 等で上書きできた。修正では、提供サーバー側で次の境界を設けた（`tools/serve-real.mjs` の `checkS5Entry`）。

- Host がこのサーバーのループバック宛て（`127.0.0.1:PORT` / `localhost:PORT` / `[::1]:PORT`）であること。DNS rebinding で別名から届いた要求は Host が異なるため拒否する。
- Origin があれば、このサーバーの同一生成元（`http://127.0.0.1:PORT` または `http://localhost:PORT`）であること。同一生成元の GET には Origin が付かないため、Origin なしは Host・セッションで判断する。
- 試験単位の不可推測セッション（`x-s5-session` ヘッダー）が、起動時に発行した値と一致すること。セッションは起動ごとに `crypto.randomUUID()` で新規発行し、`/s5-apply` 画面へメモリ上で差し込む（ファイルは書き換えない）。別オリジンのページは配信された画面を読めない（CORS なし）ため値を知ることはできず、セッションなし・不一致の呼び出しは状態を変更しない。
- `/s5/send` は JSON content-type であること（それ以外は 415）、本体は 64 KiB 以下であること（超過は 413）。本体が大きすぎる場合は、応答の送信後にソケットを破棄する（応答より先に破棄すると、クライアントに 413 が届かない）。
- 発行した6枠は、発行時に渡された試行 ID に結び付ける（`issueNonces({ trialId })`）。送信指示の試行 ID と一致しなければ `s5_trial_mismatch` で拒否する。別画面（別試行）の発行が先行試行の送信を無効化する。画面は、準備の開始ごとに新しい試験 ID を発行し、`/s5/nonces?trial_id=...` で示す。

### 4. nonce 寿命の起点

## 付録（続々々々々々々々々々）：クリーン起動試験の終了処理の修正（Codex コメント 6737085464 への対応）

実装：`tools/s10-add.mjs`（新規、純粋モジュール）と `public/s10-add-operator.html`（新規、専用画面）。順序は B の主体取得 → A の認可 → 凍結 → 送信の固定順で、状態機械 `createAddSession` が強制する。A の認可は B の主体取得が完了してからしか始められない（B 取得の nonce・Cookie 文脈を、A 取得の /nonce が上書きしないため）。B／A の本人確認は画面側が PC 内署名検証（`verifyIdTokenLocal`）で署名・iss・aud・exp・nonce を確認した結果を `markBCaptured`／`markACaptured` に渡す。検証が不完全なら試行は進まない。A と B の主体ハッシュが同一の場合は `same_subject` で試行を停止する（同一アカウントを両方に使う誤りを、送信前に機械的に防ぐ）。凍結要求は B 取得で保持した主体ハッシュと手順の固定値（期待世代 2）から生成し、手入力欄はない（画面に主体ハッシュ・世代・トークンの入力欄はない。チェックだけである）。画面は `displayData` の内容（試行 ID・action・対象・期待世代・送信先）を送信直前に表示し、所有者が「開始前の読み戻しで generation=2 を確認した」チェックとともに送信ボタンを押した場合にだけ、凍結した要求をそのまま送信する。送信は一度だけで、期待は 200 ok かつ返された generation が 3 であること。不一致なら試行を停止する。fetch が例外（レスポンスなし）の場合は状態未確定として停止し、再送を許可しない。送信は fetch で redirect: "manual"（リダイレクトは追従しない）。トークン消去の契機は `S10_TOKEN_ERASE_TRIGGERS`（追加完了・追加停止・試行の破棄・新規試行の開始）で、消去はメモリー内の変数を空にし、表示した主体ハッシュも画面から消す。nonce の期限は要求開始時刻＋5分で、s9-negative.mjs と同一の規則である。別タブ干渉については、op2_nonce_ctx Cookie は同一生成元で共有されるため別タブで /nonce を取得すると現行試行の Cookie 文脈が上書きされ、送信は nonce_context_mismatch で拒否される（誤った適用にはならない）。画面は試行中に他の検証ページを開かないよう注記し、順序の固定と取得中の排他で窓を狭める。なお、開始前の世代の生の読み戻しは画面では行わない。画面の凍結要求の期待世代は手順の固定値（2）であり、所有者が開始前の読み戻し（Data Studio と API の2経路）と照合してチェックする。サーバー側の世代照合（stale_generation）が不一致の背後の防壁であり、送信後の読み戻しで最終確認する。

remote preview の自動再試行の扱い（指摘5）：S9 の初回 /nonce 500 は、Wrangler の remote preview ProxyWorker が失敗時に 3回試行した後の内部エラーであった（Issue #3 コメント 6758216490）。変更 POST（/admin/registry/add）が同じ経路で二重配信された場合の影響を、サーバー側の保護で独立に確認した。同一要求の再送（同じ nonce・同じトークン・同じ Cookie・同じ body）は、consumeNonce が先に効いて 403 nonce_replayed で拒否される。新しい nonce での再送（同じ期待世代 2・同じ対象 B）は、成功後は世代が 3 になっているため 409 stale_generation で拒否される。新しい nonce・期待世代 3 での同じ対象 B の追加は 409 already_member で拒否される。いずれの場合も変更は二重に適用されない。これらを `test/s10-add-guard.test.mjs`（新規）で実際の通常ビルド（ローカル模擬）により確認した。残る失敗様式は応答の喪失（初回が成功したが応答が返らない場合）であり、この場合は画面は再送せず、登録簿の読み戻しで結果を確かめる（手順案の失敗時の扱いと同じ）。ProxyWorker が POST を再試行するかどうか自体は、この試験では直接確認していない（再試行の有無によらず、上の3つの保護で二重適用にならないことを確認した）。
