## 3. 安全条件と停止条件

### 3.1 安全条件（常時）

1. **対象の限定**： 書き込みは検証用 Worker `vhslide-stage1-verify-20261101-a` に対してだけ行う。書き込みの前に必ず対象（アカウント・Worker 名・名前空間・バインディング・有効なバージョン・環境 ID）を読み戻し、記録済みの対象と一致することを確認する。**不一致なら書き込まず停止する**。識別子を操作者が入力し直すことは独立した確認とみなさない（フェーズ1検証計画 第3節の流儀）。
2. **一度に1つの制御された操作**： 配置・有効化・復帰・操作の実行は1つずつ行い、結果（読み戻し）を確認してから次へ進む。並行実施は、項目2・項目9の並行消費試験として意図的に行う場合に限る。
3. **公開経路を作らない**： workers.dev は無効のまま維持する。一時ビルドの配置中も、到達経路は変形B（PC 側バインディング経由）に限る。
4. **故障注入フックを使わない**： verify 構成では `ALLOW_TEST_HOOKS=1` の構成自体を拒否する。実環境でフックを有効化する試みはしない。途中失敗の確認はフックではなく、検証専用・非公開・差分固定の故障版ビルドで行う（第4.5節）。故障版ビルドの配置は「一時ビルドの配置」と同じ統制（一度に1つの制御された操作、直後の復帰、読み戻し）に従う。
5. **秘密の扱い**： シークレット類の値はチャット・文書・記録に残さない。応答・ログには状態と理由コードだけを残す（フェーズ1の提供サーバーのログ秘匿の流儀）。
6. **応答喪失時の原則**： 状態変更要求の応答が失われた場合は**再送しない**。先に状態（完了記録・消費記録・登録簿）を読み戻してから判断する。再試行は冪等な読み取りに限る。
7. **復帰失敗時の原則**： 通常ビルドへの復帰が失敗した場合は、別経路（API ↔ Wrangler／ダッシュボード）で**1回だけ**再試行する。それでも戻せない場合は状態を記録して直ちに開発者へ上げる。戻せない間も、期限切れ後は apply 経路の実施がすべて拒否される（第4.2節 項目4の範囲）とはいえ、それは経路の消滅の代わりにはならない（`/nonce` の発行は止まらず、未消費の承認の残余リスクも残る）ため、期限切れに依存して復帰を先送りしない。
8. **未消費の承認の残余リスク**： 未消費・未期限の操作IDには**取り消す手段がない**（サーバー側に発行済み承認の一覧が存在しない。ハーネス設計書の定義どおり）。旧い一時ビルドが再配置されれば、その操作IDは引き続き実施可能になり、歯止めは有効期限の経過のみである。これを残余リスクとして明示し、次の運用で被害範囲を限定する： (a) 有効期限は分単位に短く保つ、(b) 操作の直後に通常ビルドへ復帰させる、(c) 操作IDは二度と再利用しない、(d) 未消費のまま残した操作IDは記録し、期限経過まで台帳で追う、(e) 一回値の漏洩が疑われる場合は第3.2節の封じ込めに従う。なお再配置自体はアカウント保有者によるデプロイであり、実施できるのは信頼境界の内側に限られる。**取り消し手段を製品で設けるかどうかは未解決事項として維持する**（第7節）。

### 3.2 侵害が疑われる場合の封じ込め（計画 2.4 の引き継ぎ）

想定外の登録簿の状態が見つかった場合、または未承認の登録が疑われる場合は、直ちに次を行う： (1) 通常ビルドへ戻して専用経路を消す、(2) 登録簿の全面入替（新たなプラットフォーム経路の操作、新しい操作ID）で正しい内容に置き換える、(3) 関係するセッションを失効させる、(4) 経緯を記録する。完了記録の有無だけで「侵害がなかった」と判断しない。操作の終了条件は記録ではなく**登録簿の読み戻し**である。

### 3.3 停止条件（いずれかに当たれば、その場で止めて開発者へ上げる）

- 対象の照合で不一致がある、または実行先を独立に確認できない。
- Muse の API 操作で認証・権限の異常（401／403 等）が返る。盲目的な再試行はしない。
- 登録簿に想定外の状態が見つかり、第3.2節の封じ込めでも説明がつかない。
- 通常ビルドへの復帰が、別経路の1回の再試行でも成功しない。
- 本番 Worker `vhslide` への書き込みが必要になる、または誤って触れた疑いがある。
- 設計と実物の食い違いが見つかり、手順の前提が崩れる（範囲の拡大や設計変更は実施前に開発者の判断を仰ぐ）。

## 4. 実施手順

全体の流れ： 手順0（対象照合とベースライン記録）→ 手順A（通常ビルドの配置とカナリア）→ 手順B（プラットフォーム経路： 項目1〜5）→ 手順C（アプリ内管理ルート： 項目6・8）→ 手順D（失敗手順のドリル： 項目7）→ 手順E（途中失敗ドリル： 項目9）→ 終了手順（第5節）。

各段階の終了時点での固定状態（登録簿・世代・消費済み操作ID・完了記録件数）は第4.7節の表で固定する。**各段階では、読み戻しで固定状態と一致することを確認してから次へ進む**。並行実施などで対象が変わり得る段階は、表の固定状態をもって後続の前提とする（前提が崩れたまま後続を実施しない）。

各項目は「対象／手順／合格の証拠／失敗時の扱い」で記す。理由コードはハーネスの実装に定義されたもの（`subject_mismatch` 等）をそのまま記録する。

### 4.0 手順0 ― 対象照合とベースライン記録

- 対象： 検証用 Worker の現在の状態（書き込みはしない）。
- 手順：
  1. Muse が API 経由で読み取る： アカウント、Worker 名、有効なバージョン、バインディング（名前と種別）、workers.dev の有効／無効、シークレット一覧。
  2. Codex が別経路（ダッシュボード／Data Studio）で独立に読み取り、両者の結果を照合する（フェーズ1手順0の型）。DO の名前空間 ID とインスタンスの状態（登録簿が未初期化であること、または開始時点の内容）もここで特定して記録する。あわせて、配置予定の成果物について、両者が手元の成果物のハッシュを固定したマニフェスト（`realenv-manifest.json`）と照合する（第2.2節の独立照合。両者が別々のツールでハッシュを算出する）。対象同一性の確認は、成果物や Worker 自身の設定（ENV_ID 等の自己申告）の読み返しには依存しない（第2.2節）。
  3. ベースライン（有効なバージョン `dbb7d21e-e0ee-45e9-9f1e-e3fbdb286379`、バインディングは VERIFY_ONLY のみ、シークレット一覧は空）と一致することを確認する。
  4. **非公開状態の確認**： 検証用 Worker の workers.dev が無効のままであること（公開エンドポイントが存在せず、到達経路は変形Bに限られること）を、API とダッシュボードの2経路で確認して記録する。
  5. **対象 DO の特定**： 本試験の対象 DO は、検証用 Worker に配置するハーネスの `REGISTRY` バインディング（RegistryDO）の名前空間である。手順Aの配置後に名前空間 ID を2経路で読み取って実測記録し、**本番 Worker の DIRECTORY／ROOMS の名前空間ではない**ことを、既知の本番の名前空間 ID と異なることの照合で確認する（本番側の値はフェーズ1・本番デプロイ記録の既知値を参照し、本番への新たな読み取りは行わない）。
  6. **本番の無変更確認（読み取りのみ）**： 本番 Worker `vhslide` の有効なバージョンが、フェーズ1終了時および直近の既知記録（バージョン `e3f91020` が 100%）から変わっていないことを、読み取りのみで1回確認して記録する（第1.2節の例外）。変わっている場合は、本試験の影響ではないことの切り分けが付くまで実施に入らない。
- 合格の証拠： 両経路の読み取り結果が一致し、記録に残ること。
- 失敗時の扱い： 不一致があれば実施に入らず停止し、状態を記録して開発者へ上げる。

### 4.1 手順A ― 通常ビルドの配置とカナリア

- 対象： ハーネス通常ビルド（`src/worker.js`）の検証用 Worker への配置。
- 手順：
  1. 配置前に、成果物の固定（第2.5節）と対象照合（第3.1節1）を行う。バインディングに `ALLOW_TEST_HOOKS=1` を含めないこと、tier が verify 相当であることを一覧で確認する。
  2. Muse が API で配置・有効化し、バージョン ID とバインディング一覧を読み戻して記録する。
  3. カナリア確認（変形B経由）： 模擬形式のトークンでの管理操作が拒否されること（模擬認証が実配置で効いていないことの振る舞いによる確認。フェーズ1の流儀）。あわせて通常ビルドでは専用経路 `POST /platform/apply` が 404 になることを、要求条件（メソッド・パス・生成元）を添えて観察する（通常ビルドには専用処理の実装自体が含まれないことはローカルで静的確認済みであり、ここでの 404 は実配置での観察として記録する）。
- 合格の証拠： バージョン ID・バインディング一覧の読み戻し、カナリアの拒否応答（状態と理由コード）。
- 失敗時の扱い： 配置内容が固定した成果物と異なる場合は有効化を進めず、ベースラインへ戻して停止する。

### 4.2 手順B ― プラットフォーム経路（項目1〜5）

承認の固定は操作ごとにアカウント保有者（開発者）が行い、操作ID・環境・用途・対象主体ハッシュ・一回値・有効期限をバインディングとして一時ビルドに埋め込む。一時ビルドの配置〜復帰は操作のまとまりごとに行い、各まとまりの終わりに通常ビルドへ復帰させる。

#### 実測確認点（手順Bの冒頭、項目1の実施前に行う）

手順Bは実 ID トークンを初めて使う段階である。項目1の実施に先立ち、次を実際に測って記録する。これらは項目8（トークン検証とリプレイ対策）の証拠の一部を兼ね、項目8では再実施せず本記録を参照する。

1. **Secure Cookie の実測**: 一時ビルドの `/nonce` の応答について、Set-Cookie ヘッダーに `Secure; HttpOnly; SameSite=Strict` が付いていることを、応答ヘッダーの実物で確認する（属性の有無はローカルで確認済みであり、ここでは実配置での実測とする）。
2. **ブラウザーの送り返しの実測**: 変形B経由（ブラウザーから見た生成元は `http://localhost:8787`）で、後続の要求に当該 Cookie が実際に送り返され、認証試行コンテキストの照合が通ること（項目1の手順1等の実施が `nonce_context_mismatch` にならないこと）で確認する。送り返されない場合は、その観察を記録して止め、属性を外して進めることはしない（扱いは第7節の確認事項4）。
3. **実 Google nonce の実測**: PC 側の画面が `/nonce` で取得した nonce を Google Identity Services へ渡してサインインし、戻ってきた署名済み ID トークンのクレームに、発行した nonce と一致する nonce が含まれていることを PC 側で確認する。**トークンや nonce の値そのものは記録に残さない**（一致したという事実と、確認したクレーム名だけを記録する）。モックでは再現されていない経路そのものの実測であり、項目8 手順1の証拠とする。

#### 項目1 ― 固定値との照合（主体・環境・用途の不一致の拒否）

- 対象： 一時ビルドの専用経路 `POST /platform/apply`（用途 = 初期投入 bootstrap、対象 = アカウントA、操作ID #1）。
- 手順（変形B経由で、1件ずつ）：
  1. 主体の不一致： 一回値を正しく提示し、アカウントBの実 ID トークンで実施を試みる → 拒否されること。
  2. 用途の不一致： 要求側の用途を固定値と変えて試みる → 拒否されること。
  3. 環境の不一致： 要求側の環境識別子を固定値と変えて試みる → 拒否されること。
  4. 一回値の不一致： 値を変えて試みる → 拒否されること。
  5. 完全一致： アカウントAの実 ID トークンと正しい値で実施する → 初期投入が成功すること（この成功が項目2以降の土台になる）。
- 合格の証拠： 各不一致が理由コードつきで拒否されること（`subject_mismatch` / `purpose_mismatch` / `env_mismatch` / `bad_one_time_value`）。**拒否の連続で状態が変わらないこと**を、診断読み取りまたは Data Studio の読み戻しで確認する（登録簿は未初期化のまま、操作ID #1 は未消費のまま）。成功後は完了記録（`op2_completion`）に操作ID・環境・主体ハッシュ・用途・実施時刻が固定内容どおり保存されること。
- 失敗時の扱い： 不一致が通ってしまった場合は侵害として扱い、第3.2節の封じ込めを行って停止する。成功すべき実施が拒否される場合は、再送を繰り返さず、理由コードと読み戻しを記録して止める。

#### 項目3 ― 値の漏洩を想定した試験

- 対象： 項目1の主体不一致と同型だが、「一回値を知っている第三者が、先に登録を試みる」場面として独立に記録する。**実施の順序は項目1の完全一致（手順5）より前**とする。消費後に試みると消費済みによる拒否が先に立ち、主体照合の証拠にならないためである。
- 手順： 一回値を正しく知っている前提で、アカウントBの実 ID トークンによる実施を試みる（項目1の手順1と同一の実施でも、漏洩場面としての記録を分ける）。加えて、トークンなし・形式の異なるトークンでの実施も拒否されることを確認する。
- 合格の証拠： いずれも `subject_mismatch` 等で拒否され、登録簿・消費状態に変化がないことの読み戻し。
- 失敗時の扱い： 項目1と同じ（封じ込め＋停止）。

#### 項目2 ― 原子的な一回消費（二重実施の拒否・並行で正確に1件）

- 対象： 操作ID単位の消費（`op2_consumed_ops` によるサーバー側照合）。
- 手順：
  1. 二重実施： 消費済みの操作ID #1 で再度実施を試みる → `operation_consumed` で拒否されること。
  2. 初期化済みによる拒否： 新しい操作ID #2（用途 = 初期投入）で実施を試みる → `already_initialized` で拒否されること。
  3. 並行実施： 新しい操作ID #3（用途 = 全面復旧 full-replace、内容は現在値と同一に保つ）を固定した一時ビルドを配置し、PC 側から同一内容の実施要求を並行に複数件（例： 6件）送る → **正確に1件だけ成功**し、残りは消費済みとして拒否されること。読み戻しで、完了記録が1件だけ増え、登録簿の世代が1つだけ進むことを確認する。
  4. 旧ビルドの再配置： 消費済みの操作IDを含む旧い一時ビルドのバージョンを再配置し、実施を試みる → サーバー側の状態照合により拒否されること。再配置後は直ちに通常ビルドへ復帰させる。
- 合格の証拠： 各拒否の理由コード、並行実施の成功件数 = 1、完了記録と世代の増分が読み戻しで一致すること。実 Durable Object 上での並行性の実測として記録する。
- 失敗時の扱い： 並行で2件以上成功した場合は原子的消費の不成立として直ちに停止し、登録簿を読み戻して第3.2節の扱いを検討する（成功扱いにしない）。

#### 項目4 ― 期限切れの拒否

- 対象： 有効期限を過ぎた承認と、期限切れ後の専用経路の振る舞い。
- **確認範囲（実装の実際の経路に合わせた定義）**: 期限チェックは専用経路の apply 処理（`POST /platform/apply` のトランザクション入口）で行われる。期限切れ後は、apply への**すべての**要求が、他の固定値の照合結果によらず `approval_expired` で拒否される（実装は v0.2 で期限チェックを apply 処理の入口へ移し、ローカルテストで確認済み）。一方、`/nonce` の発行自体は期限切れでも止まらない。これは確認範囲の外として明示する： nonce は単独では状態を変更できず、発行された nonce も期限切れの承認では apply が拒否するため消費できない。したがって本項目の合格は「ビルドへの全要求の拒否」ではなく「apply 経路の全要求の拒否＋状態の不変」で判定する。計画 §2.4／§2.6 の「すべてを拒否」という表現との差は、Codex 再レビュー（6654220077）の承認した整理に基づき実施計画の文言修正版で解消済みである（第7節の判断事項7。【v0.3 で解決済み】）。
- 手順：
  1. 専用の操作ID #4（用途 = 全面復旧、有効期限 = 1〜2分）を固定した一時ビルドを配置し、**実施せずに期限の経過を待つ**。
  2. 期限経過後に、完全一致の内容で実施を試みる → `approval_expired` で拒否されること。
  3. 期限経過後に、一回値を変えた内容でも実施を試みる → 他の照合に先立って `approval_expired` で拒否されること（期限チェックが apply の入口にあることの確認）。
  4. 拒否の前後で状態が変わらないことを読み戻しで確認する（第4.7節の固定状態 S7）。
  5. 期限切れの操作ID #4 は未消費のまま残る（取り消し手段はない）。台帳に記録し、通常ビルドへ復帰させる（第3.1節8の運用）。
- 合格の証拠： 期限経過後の各拒否応答（状態と理由コード）、実施時刻・期限・試行時刻の記録、状態不変の読み戻し。
- 失敗時の扱い： 期限経過後に実施が通った場合は停止し、封じ込めの要否を開発者と判断する。

#### 項目5 ― 終了手順（復帰・経路消滅の観察・読み戻し）

- 対象： 手順Bの各まとまりの終了と、手順B全体の終了。
- 手順：
  1. 通常ビルドへ復帰させ、有効なバージョンを読み戻して確認する。
  2. 専用経路の消滅の観察： 変形B経由で `POST /platform/apply` へ、項目1の成功時と同一の要求条件（メソッド・パス・生成元・ヘッダー構成）で要求し、404 になることを**要求条件を添えて**記録する（経路消滅の確認は特定の要求条件のもとでの観察である、という計画 2.6 の扱い）。
  3. 登録簿の読み戻し： プラットフォーム経路（Data Studio 等、API とは別経路）で登録簿の内容を読み戻し、最後に承認した内容と一致することを確認する。**この読み戻しが終了条件**であり、完了記録の存在だけでは終了としない。
- 合格の証拠： 復帰後のバージョン読み戻し、404 の観察記録（要求条件つき）、登録簿の読み戻し結果と承認内容の一致。
- 失敗時の扱い： 復帰できない場合は第3.1節7（別経路で1回だけ再試行→エスカレーション）。読み戻しが承認内容と一致しない場合は第3.2節。

### 4.3 手順C ― アプリ内管理ルート（項目6・8）

対象は通常ビルドの管理ルート。運営者セッションは発行せず、操作のたびに新しい実 ID トークンを提示する。前提として手順Bで初期投入が済み、アカウントAが運営者として登録されていること。

#### 項目8 ― トークン検証とリプレイ対策（実 Google の経路）

- 対象： 実 ID トークンの検証（署名・iss・aud・exp・nonce・主体）、nonce の取得経路、CSRF／リプレイ対策、Secure Cookie、環境識別の根拠。
- 手順：
  1. **nonce の取得経路（実経路の確認）**： PC 側の画面が `/nonce` で取得した nonce を Google Identity Services へ渡してサインインし、署名済み ID トークンのクレームとして同じ nonce が戻ることを確認する（モックでは再現されていない経路そのものの確認）。実測は手順B冒頭の実測確認点3で実施済みであり、本項目ではその記録を証拠として参照する（管理ルートでも同じ取得経路を使うため、経路自体の再実測はしない）。
  2. **正常系**： アカウントAの新しい実 ID トークンで管理操作（例： 読み取りまたは無害な登録簿照会相当の操作）が通ること。
  3. **署名の改変**： トークンのペイロードを改変したものを提示する → 署名検証で拒否されること。
  4. **aud／iss の不一致**： 提示されたトークンの aud・iss が期待値と異なる場合に拒否されること（取得できる実トークンの範囲で実施する。異なる aud の実トークンを用意できない場合は、その部分は未実施として記録する）。
  5. **同一 nonce の再送（リプレイ）**： 一度使ったトークン（同一 nonce）を再度提示する → `nonce_replayed` で拒否されること。
  6. **コンテキスト結び付け**： nonce の認証試行コンテキスト Cookie を持たない要求（別ブラウザー・Cookie なし）では、トークンと nonce が正しくても拒否されること。Origin が完全一致しない要求も拒否されること。
  7. **Secure Cookie の確認（必須）**： verify 構成では認証試行コンテキスト Cookie に Secure を付けるよう実装済みである（両ビルドの `/nonce`。属性の有無はローカルテストで確認済み）。実環境での実測は手順B冒頭の実測確認点1・2で実施済みであり、本項目ではその記録を証拠として参照する： Set-Cookie ヘッダーに `Secure; HttpOnly; SameSite=Strict` が付くことの観察と、変形B経由でブラウザーが当該 Cookie を後続の要求で実際に送り返すことの機能確認である（ローカル模擬では送り返しの実測はできない。ブラウザーがループバックを信頼できる起点として扱うかは実装依存であり、前提にしない）。送り返されない場合は、その観察を記録して止め、属性を外して進めることはしない（扱いは第7節の確認事項4）。
  8. **環境識別の根拠**： 手順0の両者独立の照合記録をもって「環境識別の信頼できる根拠」とし、本項目の証拠に含める（配置した側の設定の読み返しだけを根拠にしない）。
- 合格の証拠： 各拒否の状態と理由コード、正常系の成功応答、Set-Cookie の観察記録、手順0の照合記録。
- 失敗時の扱い： 改変トークンや再送が通った場合は停止し、影響範囲を読み戻して記録する。
- **本項目で実環境でも確認できない部分**（第6節にも集約）：
  - 期限切れの実トークンの拒否： 実トークンの有効期間（約1時間）の自然な経過を待つか、前セッションで取得した期限切れトークンを PC 側に保持して使う方法が考えられるが、保持の可否は判断事項とする。実施できない場合は未実証として記録する（exp の検査ロジック自体はローカルで確認済み）。
  - 検証基盤（tokeninfo 等）の到達不能・応答異常時に拒否側へ倒れるか： verify 構成では検証先の上書き設定が拒否されるため、実環境で到達不能を意図的に作る正規の手段がない。未実証として記録する。

#### 項目6 ― 失効と世代

- 対象： 登録簿の変更（追加・失効・ローテーション）と世代照合の、実 Durable Object での直列化。
- 手順（すべて実 ID トークンを操作ごとに新しく提示する）：
  1. 追加： 運営者Aの認可でアカウントBを運営者に追加する（世代が1つ進むこと）。
  2. 正常系： Bの新しいトークンで管理操作が通ること。
  3. 古い世代での更新： 追加前の世代を `expected_generation` に指定した変更要求 → `stale_generation` で拒否されること。
  4. 並行更新： 同じ現在世代を指定した**同一の変更要求**（アカウントCの追加）を並行に2件送る → 正確に1件だけ成功し、もう1件は世代不一致で拒否されること。同一要求にそろえるのは、勝者がどちらでも結果の状態が変わらないようにし、第4.7節の固定状態（{A, B, C}、世代 +1）と照合可能にするためである。
  5. 失効： Aの認可でBを失効させる。Bの**次回操作**（新しいトークン）→ `not_operator` で拒否されること。Bが失効前に用意したトークン（有効期間内）での操作も同様に拒否されること。
  6. 最後の運営者の保護： まずAの認可でCを失効させ、登録簿を {A} だけにする（第4.7節 S13）。そのうえで、唯一の運営者A自身をアプリ側で失効させようとする → `last_operator` で拒否され、状態が変わらないこと（全運営者の失効・回復はプラットフォーム経路に限る、という計画 2.1 の確認）。
  7. ローテーション： AからBへのローテーション（同一トランザクションでの削除＋追加）が通り、登録簿が {B} になること（第4.7節 S14）。ローテーション元（A）の主体が次回操作で拒否され、先の主体（B）が通ること。
- 合格の証拠： 各操作の成否と理由コード、世代の増分の読み戻し、失効後の拒否応答。実 Durable Object での直列化の実測として記録する。
- 失敗時の扱い： 失効した運営者の操作が通った場合、または並行更新で2件成功した場合は停止し、登録簿を読み戻して記録する。

### 4.4 手順D ― 失敗手順のドリル（項目7）

#### 項目7 ― 失敗手順の実施（応答喪失・復帰失敗）

- 対象： 運用失敗時の判断手順が実環境で回ること。**故障注入フックは使わない**（verify 構成では構成自体が拒否される。第3.1節4）。
- **実測の基準（応答破棄の扱い）**: 応答を破棄する方法によっては、接続を早く閉じたことで要求自体が処理されない可能性がある。したがって本ドリルでは、結果の判定を応答ではなく読み戻しだけで行い、次のように区分する：
  - 読み戻しで**コミット済み**（操作ID #5 が消費され、完了記録と登録簿が第4.7節 S15 の固定状態と一致する）を確認できた場合のみ、「コミット後の応答喪失」の**実測**とする。
  - 読み戻しで**未消費**だった場合は、その試行では「コミット後の応答喪失」は**未成立**と記録し、実測に数えない。未消費であることを読み戻しで確認できた場合に限り、未成立分の実施をやり直してよい（これは状態確認を経た再実施であり、「再送しない」原則への違反ではない。再実施は最大で2回までとし、それでもコミットを読み戻せなければ未成立のまま閉じる）。
  - 要求の送信方法は、送信自体は完了し、応答の読み取りだけを行わない形（応答本文を読まずに接続を閉じる等）に限る。送信完了すら確認できない方法は使わない。
  - **登録簿の内容が現在値と同一であることについて**： 本ドリルの全面復旧（操作ID #5）の内容は、現在値 {B} と同一に保つ。これは意図的な同一値であり、成否の判断は登録簿の差分ではなく消費記録・完了記録の読み戻しで行う。これに対し、途中失敗のロールバック実証（手順E／S17）では旧値≠新値を必須とする（差し替われば差分が観測できることが実証の前提であるため）。両者の扱いを混同しない。
- 手順：
  1. **応答の破棄を伴う観察（コミット後の応答喪失）**： 全面復旧（操作ID #5、対象主体 = B、内容は現在値 {B} と同一）の一時ビルドを配置し、実施要求を送る際に **PC 側で応答を意図的に読み取らず破棄する**。応答からは成否を判断できない状態を実環境で作る。そのうえで手順どおりに振る舞う： **再送せず**、先に状態を読む（完了記録・消費記録・登録簿の読み戻し）。上記の基準で実測／未成立を区分し、実測の場合は「再送しない」という判断で操作を閉じる。読み戻しを経ない再送をした場合は手順違反として記録する。
  2. **配置の切替に伴う応答喪失**： 復帰（通常ビルドへの配置切替）の応答が失われた場合を想定し、同じく再送せず、有効なバージョンとバインディングを読み戻して復帰の成否を判断できることを確認する（実際の切替操作で、応答の成否表示に依らず読み戻しで判断する進め方を取る）。
  3. **別経路での復帰ドリル**： 通常ビルドへの復帰を1回、主経路（Muse の API）ではなく別経路（PC 側の Wrangler／ダッシュボード）で実行し、別経路が実際に回ることを確認する。これは失敗の意図的な発生ではなく、復帰失敗時に使う経路の実施可能性の確認である（実際の復帰失敗そのものは実環境で意図的に作らない）。
- 合格の証拠： 応答破棄後に（読み戻しを経ない）再送をしなかったことの記録、読み戻しに基づく判断と最終状態の一致（実測／未成立の区分つき）、別経路での復帰の完了記録。
- 失敗時の扱い： 読み戻しの結果と実際の状態が食い違う場合は停止して記録する。
- **本項目で実環境でも確認できない部分**： 復帰操作そのものの失敗（配置 API の障害等）を意図的に発生させる手段はなく、「復帰失敗時に別経路で再試行する」という手順のうち**失敗の発生側は未実証として残る**（手順3で確認するのは別経路の利用可能性であり、両者を分けて記録する。第6節の受入条件の整理を参照）。

### 4.5 手順E ― 故障版ビルドによる途中失敗ドリル（項目9）

計画 §2.7 項目9は、3つの要素を実環境で確認することを求める。本書での対応は次のとおりであり、対応表に明示する。

| 要素 | 本書での実施 | 記録区分 |
|---|---|---|
| 固定対象と異なる主体の拒否 | 項目1・項目3で実トークンにより実施 | 実測（予定） |
| 並行消費（正確に1件だけ成功） | 項目2の手順3で実 DO により実施 | 実測（予定） |
| 途中失敗時のロールバック | 故障版ビルド（書込み「後」の例外）で実施（本節） | 実測（予定） |

#### 項目9 ― 途中失敗時のロールバック（故障版ビルド）

- 対象： 故障版ビルド（`fault-builds/apply-after-writes/worker.js`。検証専用・非公開・差分固定の別成果物。フェーズ1の障害版ビルドの流儀）。クリーンな一時ビルドとの差分は1点のみ： apply のトランザクション内で、登録簿の書込み（運営者の削除・挿入、世代と初期化状態の更新）を行った「後」、消費記録・完了記録を書く「前」に、無条件に例外（マーカー `injected_fault_apply_after_writes`）を投げる。現行ハーネスの `_fault=platform-mid` は「nonce 消費後・登録簿書込み前」の注入であり、本項目の実証には**使わない**。汎用 500 や書込み前の故障をもってロールバックの実証としない。
- 前提： 手順Dまでが完了し、登録簿が {B} であること。承認は操作ID #6（用途 = 全面復旧、**対象主体 = A**、有効期限は分単位）を固定する。バインディング構成はクリーンな一時ビルドと同一であり、成果物だけが故障版である。
- **旧値≠新値の形（S17 の具体化）**: 本ドリルでは、登録簿の現在値 {B}（旧値）に対して、全面復旧の内容を {A}（新値）とする。旧値と新値が異なるため、ロールバックが効かなければ次の差分が全量読み戻しで直接観測できる： (a) 運営者集合が {B} から {A} に変わる、(b) 世代が1つ進む、(c) 運営者行の added_by が `platform:#6` に、added_at が実施時刻に変わる。したがって合格の判定は「実施後の全状態が実施前と**完全一致**すること」に置き、部分的な一致（例： 運営者集合だけが不変）をもってロールバック成立とはしない。対象を A とする理由は、S14 のローテーションで登録簿が {B} になっているためであり、A はこの時点では運営者ではないが、プラットフォーム経路の実施は運営者の在籍を要件としない（アカウント保有者による配置と、固定値に一致する主体のトークン提示が要件であり、初期投入と同じ形である）。実施にはアカウントAの実 ID トークンを使う。ハーネス側でも同じ型（旧値 {A} → 新値 {B} の全面復旧を故障版で失敗させる形）のローカル確認を追加済みである。
- 手順：
  1. **実施前の全状態読み戻し**： 登録簿の全状態（運営者集合・世代・初期化状態・消費済み操作IDの一覧・完了記録の全件・未消費 nonce の内訳。第4.7節の読み戻し対象の定義のとおり）をプラットフォーム経路（Data Studio 等）で読み戻し、記録する。これが比較の基準になる（第4.7節 S16）。
  2. **故障版ビルドの配置**： 操作ID #6 の承認を固定した故障版ビルドを配置し、バージョン ID とバインディング一覧を読み戻して、固定したマニフェスト（故障版のハッシュと差分を含む）と照合する。あわせて、応答本文を PC 側で直接取得する手段（第2.5節の事前確認 (b)。画面のログに依存しない方法）が、この配置でも使えることを実施前に確認しておく。
  3. **実施**： アカウントAの実 ID トークンと正しい一回値で実施する → 500 が返ること。例外到達の識別は、応答本文の detail に含まれるマーカー `injected_fault_apply_after_writes` で行う（ブラウザーの開発者ツール等で応答本文を直接確認する。画面のログは理由コードまでしか出さない）。応答本文が取得できない場合は、マーカーなしの 500 だけでは到達の証拠とせず、「完全一致の入力に対する 500」＋「実施後の全状態が実施前と完全一致」＋「手順5でクリーン版が同じ承認で成功する」の3点の組合せをもって到達の証拠とし、本文が取得できなかったこと自体を記録する。
  4. **実施後の全状態読み戻し**： 手順1と同じ方法で全状態を読み戻し、実施前と**完全一致**すること（書込み済みだったはずの内容を含め、すべて巻き戻っていること）を確認する。読み戻しには未消費 nonce の内訳も含め（第4.7節の読み戻し対象の定義）、今回の認証試行の nonce が未使用に戻っていること（使用済み件数が実施前と変わらないこと）も完全一致の判定に含める。任意の傍証として、同一の ID トークン（同一 nonce）での再実施が再びマーカーつき 500 になることを確認してもよい。
  5. **復帰と再実施**： 故障版から通常ビルドへ復帰させた後、**クリーンな一時ビルド**（同じ操作ID #6 の承認を固定）で、アカウントAの実 ID トークンにより実施する → 201 になり、状態が正確に1件分だけ進むこと（登録簿は新値 {A}、世代 +1、消費に #6 を追加、完了記録 +1件。第4.7節 S17）。これにより、故障版での実施が未消費のままであることと、ドリルが登録簿を壊していないことが確定する。その後、通常ビルドへ復帰し、項目5の終了手順を行う。
- 合格の証拠： 実施前後の全状態の読み戻し記録とその一致、500 応答とマーカー（または上記の組合せによる到達の証拠）、クリーン版での再実施の成功と状態の増分。
- 失敗時の扱い： 実施後の状態が実施前と異なる（部分的に進んでいる）場合は、ロールバック不成立として直ちに停止し、登録簿を読み戻したうえで第3.2節の封じ込め（全面入替による置き換えを含む）の要否を開発者と判断する。成功として記録しない。また、例外到達の証拠がマーカーでも上記の組合せでも得られない場合は、ロールバックの実証としては**未実証**として記録し、項目9を合格としない（第6節の整理に従う）。

### 4.7 段階ごとの固定状態と進行条件

各段階の終了時点での固定状態を次の表で固定する（「登録簿」は運営者の主体ハッシュの集合、「消費」は消費済み操作IDの集合、「完了」は完了記録の件数）。並行実施などで結果が分岐し得る段階は、本書の手順の定義（例： 項目6の並行更新は同一要求にそろえる）により結果が一意になるようにし、それでも実測が表と異なる場合は、表を書き換えて進むのではなく**停止して記録し、開発者・Codex と扱いを判断する**。

#### 読み戻し対象の定義（全段階 S0〜S17 共通）

各段階の読み戻しは、固定状態の表の項目に加えて、次を対象とする。

- `op2_operators` の全行（主体ハッシュ・added_at・added_by を含む。集合だけでなく行の属性まで見る。S17 の差分観測はこれによる）。
- `op2_meta`（世代・初期化状態）。
- `op2_consumed_ops` の全行、`op2_completion` の全行。
- **`op2_pending_nonce` の内訳**： 総数・使用済み数・未使用数の件数のみを記録する（nonce の値と ctx ハッシュは記録に残さない）。試験で使った個別の nonce については、発行・使用した PC 側が、その値で used の状態を確認する（値は記録しない）。段階ごとの不変条件は表の進行条件に含める（例： S9 では再送に使った nonce が使用済みのままであること、S17 では故障実施の前後で使用済み件数が変わらないこと）。ハーネスの読み戻し（`snapshot()`）にも同じ内訳を含めてあり、ローカルの全状態比較はこの定義に沿っている。
- 読み戻しの経路は段階の性質による： プラットフォーム経路の読み戻しは Data Studio 等（API とは別経路）を正とし、診断読み取りは実環境では使わない（マニフェストの `must_not_be_set` のとおり DIAG_KEY は設定しない）。

#### 外部の承認入力に対応しない生成データの保持／破棄方針

試験中には、外部の承認入力（アカウント保有者が固定した承認）に対応しない生成データが生じる： 未消費のまま残る nonce 行、拒否された試行が残した nonce 行、期限切れのまま未消費で残る操作IDの台帳記録、PC 側・Muse 側の作業ログである。これらの扱いを次のとおり定める。

- **保持（工程の終了まで）**: 上記の生成データは、工程の実施中はその場に保持する。途中で消すと読み戻しによる証拠の連鎖が切れるため、掃除目的の削除・消費は行わない（未消費 nonce を人為的に消費して片付けることはしない。nonce 行は有効期限（5分）の経過で無効になるが、行自体は残る）。
- **記録**: 未消費 nonce は件数の内訳として段階記録に残す。未消費の操作ID は第5.2節7の台帳で追う。
- **破棄（工程の終了時）**: 登録簿・完了記録等とあわせた検証データ一括の扱いとして、第5.2節6に従う（破棄する場合は開発者の直接の承認を得て PC 側で実施し、読み戻しで確認する。本書は破棄を既定としない）。保持を選んだ場合も、その旨と理由を終了記録に残す。
- 外部入力のない段階（読み戻しのみを行う S0・S1・S6 等）の記録についても同様とし、読み戻し記録そのものは工程の証拠として保持する。

## 5. 終了手順と閉じの条件

### 5.1 操作ごとの終了（プラットフォーム経路）

一時ビルドを使うまとまりごとに： 通常ビルドへの復帰 → 専用経路の消滅の観察（要求条件つき）→ 登録簿の読み戻しが承認内容と一致することの確認（4.2 項目5）。この3点が揃うまで、その操作は終了としない。

### 5.2 工程全体の終了（閉じの条件）

次をすべて満たしたときに、本実環境試験の工程を閉じる。

1. **通常ビルドへの復帰**： 手順A〜Dの最後に、検証用 Worker が通常ビルド（または開始時のベースライン。最終状態の選択は記録する）に戻っていることを、有効なバージョンの読み戻しで確認する。
2. **専用経路の消滅の観察**： 5.1 の観察を最終状態でも行い、要求条件を添えて記録する。
3. **登録簿の読み戻し**： 最終の登録簿の内容をプラットフォーム経路（Data Studio 等）で読み戻し、最後に承認した内容と一致することを確認する。
4. **シークレットの後始末**： 検証で使ったシークレット類（一回値等）を、有効版・最新版から除去し、一覧が空であることを確認する（フェーズ1終了手順の引き継ぎ）。PC 側で生成・保管した値の控えも、PC 側で削除する。なおフェーズ1で確認されたとおり、**過去バージョンに残り得るバインディングまで消去できるわけではない**。この範囲の限定を記録に引き継ぐ（旧版の再配置はアカウント保有者の操作であり、信頼境界の内側である）。
5. **トークンの失効**： 開発者が、実施用に発行した Muse のトークンを失効させる。Muse 側で失効（401 になること）を検証して記録する。
6. **検証データの扱いの記録**： 検証で作った登録簿・完了記録等のデータについて、保持／破棄の扱いを記録する（未消費 nonce 行を含む生成データの扱いは第4.7節の保持／破棄方針に従う）。破棄する場合（例： フェーズ1の mtrial_* と同様のテーブル破棄）は、**開発者の直接の承認を得てから** PC 側で実施し、読み戻しで対象が消えたことを確認する。本書は破棄を既定としない。
7. **未消費の操作IDの台帳**： 未消費のまま残した操作ID（項目4の期限切れ分を含む）を一覧にし、それぞれの有効期限を記録する。期限経過後の扱いは第3.1節8に従う。
8. **項目ごとの結果の確定**： §2.7 の項目ごとに「実測（合格）／ローカル模擬のみ／未実施・未実証」を確定し、最終記録に残す。**工程を閉じることと「§2.7 全合格」は別の判断である**： 未実施・未実証が1つでも残る場合は全合格とは記録せず、残余を明示する（第6節）。閉じの条件を満たしても、ゲート（手順4への着手可否）は第6.1節の扱いに従う。

## 6. 受入条件の整理と未実証の扱い

### 6.1 総則

- 結果は項目ごとに「実測／ローカル模擬／未実施（未実証）」を分けて記録し、**未実施は合格としない**（計画 §2.7、フェーズ1の記録の流儀）。
- **未実施・未実証が1つでも残る場合は、本試験をもって「§2.7 全合格」とは記録しない**。その場合は残余を明示したうえで、ゲート（手順4への着手可否）の扱いを開発者と Codex が判断する。本書はゲートを緩和しない： 判断がない間は、手順4に着手しないのが既定である。
- 障害に関する項目は、「障害の発生自体を実測したか」と「障害時に使う別経路・代替手順が実際に回るか（利用可能性）」を**分けて**記録する。利用可能性の確認をもって、発生自体の実測の代わりにしない。

### 6.3 未実証として残る見込み（現時点）

1. 項目7： 復帰失敗の「発生」自体 ― 実環境で意図的に発生させる手段がないため（別経路の利用可能性は確認する）。また、応答破棄の試行が読み戻しで未消費だった場合は「コミット後の応答喪失」は未成立として残り（再実施は第4.4節の基準の範囲でのみ）、未成立のまま閉じた場合は項目7の当該部分を実測としない。
2. 項目8： 検証基盤の到達不能・応答異常時に拒否側へ倒れること ― verify 構成で到達不能を意図的に作る正規の手段がないため。
3. 項目8： 期限切れの実トークンの拒否 ― 取得方法（自然な経過待ち／前セッションのトークンの保持）の判断次第で未実証になり得る。
4. 項目9： 例外到達の証拠 ― 応答本文が取得できず、かつ第4.5節の組合せ（完全一致入力への 500＋全状態の完全一致＋クリーン版での成功）も成立しない場合は、ロールバックの実証として未実証になる。

（v0.1 で未実証の見込みとしていた項目9の途中失敗は、故障版ビルドの用意により「手段あり・実環境での実施が本試験の対象」に移った。）
