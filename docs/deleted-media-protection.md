# 0.39.1 削除済み画像・付箋の取得制限

調査・修正日：2026-10-24。対象は個人情報監査の項目3のみ。本番データ・公開ルームへのアクセス、デプロイは行っていない。

## 変更した動作

- 一般参加者は、現在のいずれのシート・ページからも参照されない画像を取得できない。画像URLを知っていても404となる。
- 一般参加者への付箋一覧には、現在存在するページの付箋だけを含める。ページ削除時は接続中の参加者にも一覧の更新を通知する。
- 別ページ・別シートでも使用中の画像は取得可能なまま。編集範囲の制限を閲覧範囲の制限へ変更するものではない。
- 未使用の新規アップロードは、アップロードした本人とホストだけが取得・追加可能。最初にページへ保存する際に、この特例を同じ永続化トランザクション内で消費する。一度使用してから削除した画像に、この特例は復活しない。
- 一般参加者が削除済み画像のURLを編集データに書き戻す操作も拒否する。削除済み付箋が残るページIDを再利用する回避操作も拒否する。
- ホストは、過去の画像・付箋を取得し、履歴から復元できる。元作品の履歴・画像・付箋は物理削除しない。

**操作上の制約：** 一般参加者が削除済み画像や付箋を戻す場合は、ホストへの依頼が必要になる。通常の「もとに戻す」であっても、この制限を回避できない。拒否された更新は既存の権限エラー処理により送信を停止するため、作品を開き直す必要がある。削除時の案内と更新履歴に制約を明記した。画像・保存済み付箋のないページの取り消しまで一律に禁止するものではない。

Nodeではストレージ読み込み後にも所属と参照を確認する。S3署名付きURLへのリダイレクトは廃止し、認証付きサーバー経由で配信する。CloudflareではDirectory経由の所属確認後、Roomが現行参照を判定して配信する。画像は`private, no-store`。

追加SQLテーブルは起動時に作成する。旧画像のうち現在参照されている画像はそのまま使える。旧データに未公開画像の本人用アクセス権を遡って付与しないため、旧版でアップロードしたまま未保存の画像は一般参加者から再追加できない場合がある。

## 保証しない範囲

- 削除前にすでに読み込んだ画像・付箋、ダウンロード・スクリーンショット・ブラウザ内の保存を回収するものではない。
- Node/S3で旧版がすでに発行した署名付きURLは、旧設定の有効期限（60秒）までは失効できない。新版は新規発行しない。
- ホストは復元用の過去データを取得できる。現在の別ページに残っている同じ画像も配信対象。
- 端末内キャッシュ、オフラインのサインアウト、画像EXIFはユーザーの指定により今回は変更しない。
- Chromebook・iPad・Windows実機では未検証。ブラウザ試験はLinux Chromiumのデスクトップ／タッチエミュレーションであり、実機の代用である。

## 検証

すべて合成アカウント・一時ディレクトリ・ローカルのRoom/Directoryを使用。

### 回帰試験の内容

共通のバックエンド試験 `tests/support/deleted-media.ts` をNode／Cloudflareから実行する。

1. 編集者の新規アップロードは本人にのみ配信し、保存後は閲覧者にも配信する。
2. 別シートに同じ画像が残る間は画像を配信する。ページ削除後の付箋だけを隠す。
3. 最後の画像参照を削除すると、元のアップロード者を含む参加者には404。クエリ文字列でホスト扱いにはならない。
4. 古い画像URL・付箋が残るページIDを書き戻す偽造WS更新を拒否する。
5. 再起動後も同じ制限を維持する。ホストは削除前の版・画像・付箋を取得できる。
6. ホストの意図的な復元後は、現行の画像・付箋として再び表示できる。

`tests/cloud/deleted-media.spec.ts` はデスクトップ／タッチ設定で実際の削除メニュー、他参加者の一覧更新、画像404、ホストによる別作品への履歴復元、新作品が未共有であることを確認する。

`tests/audit/privacy-audit.ts` は以前の指摘を再検証し、削除済み画像・付箋の取得拒否と、偽装した内部ヘッダーでも404になることを両バックエンドで確認する。他の指摘は今回直したと判定しない。

証拠ログ：[検証ディレクトリ](audit-evidence/deleted-media-2026-10-24/)。ログに登場するアカウント・作品は合成データ。

### 既存ブラウザー試験の一時競合

Cloudflare全体試験の初回は、復元作品のタイトル編集直後に`/backup`が409（`backupChanged`）を返し、既存テストが`deck.title`を無条件に参照して1件失敗した。トレースで実際の応答本文が「取得中に作品・付箋・共有設定が変更されました…」であることを確認した。安全なスナップショット取得を拒否する正常な経路であり、今回の配信制限の回避やデータ消失ではない。

`tests/cloud/collaboration.spec.ts`の当該ポーリングだけを修正した。既知の409と正確なエラー本文が一致した場合だけ既存の有限時間ポーリングで再確認し、それ以外のエラーは失敗させる。アプリ・バックアップAPIの整合性検証は変更していない。初回全体実行の失敗を消さず、証拠に記録する。

修正後、Node・Cloudflareそれぞれで「既存の版復元・ごみ箱」と「今回の削除・取得拒否・別作品復元」の重点ブラウザー試験を、デスクトップ／タッチで再実行し、各4件（計8件）が成功した。最終ビルドでの結果。全体試験を再びすべて実行したものとしては扱わない。
