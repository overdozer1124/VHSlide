# 段階① フェーズ1 次期独立試作の実施計画（A と C の組み合わせ案）v0.3

根拠： 実装設計書 v2.10 第3節、段階①検証計画 v0.4（A1〜A7）、候補比較（中間、7826fa3 反映済み）。v0.1・v0.2 に対する Codex レビュー（Issue #3、2026-11-02）を受けて改訂した。変更点は第9節にまとめている。これは独立試作の計画であり、製品実装の承認や本番方式の確定ではない。実施は検証専用環境に限る。変形は開発者の判断により変形Bに決定済みである。

## 1. 目的

候補比較で残った不足のうち、次の4点を実証の対象とする。

- A4： 検証用 Worker 自身による Origin／CSRF の拒否を、実経路（検証用 DO への実際の到達経路）で確認する（従来はローカル模擬のみ）。経路の形は第3節の変形A／変形Bのどちらかとし、選ばなかった側の残余は未検証として記録する
- A5： 運営（設定操作）と復旧の認可と対象本人の証明を、異なる保持者・異なる経路に分け、Worker がその分離を強制することを確認する。証拠の範囲は第5節の限定どおりとする
- A2・A7 の記録： 完了記録・復旧記録に、対象環境の識別子、対象の識別子、登録日時（復旧では旧新の対応と日時）を、後から照合できる形で残す
- A6： 実行先の照合を、実施者（Muse、API 経由）と独立した確認者（Codex、ダッシュボード／Data Studio）の双方で行う

## 2. 識別子の記録方法と扱い

- 設計書第3節は完了フラグに「対象環境・sub・登録日時」の記録を求め、user_id は sub から決定的に導出される（第2.2節）。現行コードでは user.id は sub そのものである。
- 本試作では、生の sub を検証用 DO に保存せず、sub の SHA-256 ハッシュを対象識別子として記録する。導出が決定的であるため、提示された sub を同じ方法で変換すれば事後の照合が可能であり、塩を削除した HMAC（照合不能）とは異なる。
- このハッシュは本人との対応付けが可能な仮名識別子であり、匿名化ではない。読み取りは運営側（Muse の API 経由の読み取りと Codex の Data Studio）に限る。保持はフェーズ1最終報告までとし、その後 `mtrial_*` テーブルは破棄する（保持する場合は開発者の判断として記録する）。実 ID・鍵・生の sub は Issue・チャット・文書に出さない。
- 記録に残る日時は検証実施時のものであり、本番時刻の実証ではない。
- 本番で生の sub を記録するか導出済み ID とするかは、フェーズ1最終報告で解釈として明記し、方式確定時の確認事項とする。本試作の記録方法はその判断を先取りしない。

## 3. 構成

検証用 Worker `vhslide-stage1-verify-20261101-a`、DO 名前空間 `ef29957c85744eccaea6db64af433868`、インスタンス `stage1-verification-only-20261101` を使う。試作用テーブルは新しい接頭辞 `mtrial_*` とし、既存の `gtrial_*` 等の記録には触れない。

受付経路の開き方には2つの変形があり、どちらで進めるかは開発者の判断事項である。未決定の間は変形Bを前提に準備を進め、変形Aの手順は実行しない。

- 変形A（workers.dev の一時有効化）： 検証用 Worker に限り、試験時間帯だけ workers.dev を開く。公開され得る対象は検証専用 Worker のみで、本番データは含まない。認証は初回用シークレット＋Google ID トークン＋セッション連動 CSRF とする。撤去の順序と失敗時の扱いは手順7に定める。これは「公開先・workers.dev を作らない」という現行条件の変更にあたるため、開発者が明示的に承認するまで実行しない
- 変形B（現行条件の維持）： 公開先は作らない。PC 側のローカル中継（remote service binding）経由で検証用 Worker を呼び出す。前回試作と同じ到達形態であり、実経路の測定はこの経路で行う。ブラウザーの公開エッジそのものは通らないため、その部分は未検証として残る

共通の構成要素：

- 案A の要素（一時性）： 受付は試験時間帯だけ有効にする。登録は本人の Google セッション（ID トークン）と初回用シークレットの提示の両方を要求する。完了後は受付を停止し、シークレットを除去する
- 案C の要素（運営の独立認可）： 第4節のとおり、設定操作・復旧の認可・対象本人の証明を分ける
- 中継（変形B、および変形A でログイン画面を localhost に置く場合）： ブラウザーの Origin を変更せず素通しし、固定値を付けない。中継はアプリケーションレベルの拒否を行わない。Worker は受け取った Origin の値を応答に含めて返し（試験用の読み取り）、拒否がすべて Worker 自身のものであることを、中継を介さない直接要求との対照試験で確認する
- 変更要求の保護： 正規 Origin（`http://localhost:8787`）の完全一致を要求し、CORS はこの生成元のみ許可する。セッション Cookie は HttpOnly、SameSite=Strict、Path はハーネスの範囲、Max-Age は30分とする。CSRF 値はセッションごとの乱数とし、DO 内でセッション記録に結び付けて保持し、ログイン・復旧のたびに再発行し、セッションと同時に失効させる
- ID トークンの検証： nonce はログイン試行ごとに生成し、DO の認証待ち記録に有効期限（5分）つきで保持して単回使用とする。Worker が aud・iss・exp・nonce・email_verified・sub の存在を照合する（tokeninfo の利用は前回試作と同じ）
- 原子性： 登録と完了記録は DO の1トランザクションで記録する。復旧は旧資格の失効・新資格の付与・復旧記録を同一の原子的更新で行い、復旧キーの提示と対象の新しい ID トークンを結び付けて判定する
- 状態の正本： 完了記録は初代登録の履歴（対象環境・初代の対象識別子・登録日時）として不変に保ち、復旧では更新しない。ログイン可否と操作可否の正本は「現在の資格」であり、復旧は資格の切り替えと復旧記録（旧新の対応・日時）の追加だけを行う。状態遷移は、登録（資格なし→初代の資格＋完了記録）／復旧（現在の資格を旧→新へ原子的に入れ替え、復旧記録を追加、旧セッションを削除）／再起動（保存状態は不変）の3つとする
- 検証用セッションは登録後に発行し、管理操作の判定では毎回現在の資格を照合する。再ログイン用の経路（/login）を登録とは別に持ち、提示された subject が現在の資格に現存する場合のみセッションを再発行する（登録の一回性は保つ）

## 4. 鍵と権限の所在

値はチャット・文書・GitHub に残さない。

- 設定操作（デプロイ、受付の有効化・停止）： Muse の Cloudflare API トークン（運営チャネル）。これは管理 API 権限の保持であり、復旧ごとの認可とは区別する
- 復旧キー： Codex が PC 側で生成し、Wrangler から Worker シークレットとして設定する。提示も PC 側からのみ行い、Muse は値を保持しない
- 初回用シークレット： Codex が PC 側で生成し、Wrangler から設定する。提示は対象本人のログイン画面経由で行う
- 対象の証明： 対象アカウントの通常の Google ログインによる ID トークン。旧アカウントのセッションは復旧に要求しない
- どの鍵も単独では登録も復旧もできないことを試験項目に含める（初回用シークレットだけでは本人の証明にならず、ID トークンだけでは登録できず、復旧キーだけでは対象の新しい証明と結び付かない）

## 5. 受入条件への対応

- A1： 手順2・3 で、選んだ変形の経路による到達と登録を確認する。Data Studio の直接操作（案B）の実証とは混同しない
- A2： 手順3 の競合・再実行拒否・途中失敗のロールバックと、手順6 の再起動後の保持、完了記録の必須項目（環境識別子・対象識別子・登録日時）で判定する
- A3： 手順2 の生成・設定、手順7 の削除と削除後の拒否で判定する。実運用の保管・ローテーション手順そのものは本試作の対象外と明記する
- A4： 手順3 で、正規／不正／欠落の Origin と CSRF 欠落／不一致を、状態が変わらないことまで含めて実経路で確認する。変形Bではブラウザーの公開エッジを通らない残余を未検証として記録する
- A5： 証拠の範囲は「固定されたコード・設定を前提として、経路の運営（設定操作）・復旧の承認（復旧キー）・対象本人（Google ログイン）の3つの役割の分離を Worker が強制すること」までに限定する。Muse は API 権限によりコードや設定自体を変更し得るため、Cloudflare の管理権限を持つ主体に対する独立性や、その主体との相互不正防止は示さない。組織的な独立性や、実運用での運営者認証そのものの証明とも主張しない。鍵の設定・提示の主体は第4節のとおりとし、監査の範囲は「誰が・どの経路で・何を設定し提示したか」を記録できることまでに限る。この範囲で、保持者と経路が実際に分かれていること、各鍵の単独使用で登録・復旧ができないことで判定する
- A6： 手順0 と手順7 で、Muse と Codex が独立に照合する
- A7： 手順5 の復旧の実演（旧セッション・旧トークンの拒否、記録の事後照合を含む）で判定する。製品セッションの失効を示すものではない

## 6. 手順

- 手順0（照合）： Muse が API で検証用 Worker の設定と連携（VERIFY_ONLY のみ、名前空間 ID 一致）を読み取り、Codex がダッシュボードで独立に照合する。DO 内の既存テーブル一覧を取得し、開始時点の状態として記録する。対象が一致しなければ中止する
- 手順1（ローカル模擬）： Muse の環境でハーネス一式（Worker、ログイン画面、中継）を作成し、Miniflare の模擬 DO と模擬 ID トークンで全フローを試験する。結果は模擬層として区別して記録する。公開先や検証用 Worker への変更を伴わないため、変形の決定を待たずに進める
- 手順2（配置）： 配置に先立ち、ハーネスと中継の実コード・設定・試験ランナーを、秘密値・実 ID・認証情報を含まない形でリポジトリ（`docs/prototypes/stage1-next-prototype/`）に共有し、Codex のコード確認を受ける。Muse が API 経由でハーネスを検証用 Worker へデプロイする（API デプロイ自体の可否確認を含む。コードの配置だけでは公開先は生じない）。Codex が初回用シークレットと復旧キーを生成・設定する。シークレットの一覧に想定外の項目があれば中止する。変形Bで PC 側の remote service binding を実行する際の edge-preview セッション取得は、準備・照合とは別の関門とし、Codex が通常の承認・審査の手続きに従ってその都度実行する。拒否や権限不足が出た場合は別経路で回避せず、事実として記録する
- 手順3（登録の試験）： 通常登録、再登録の拒否（409）、並行登録（成功1・拒否1）、登録途中の意図的失敗後の資格なし、誤った初回用シークレットの拒否、不正 Origin・Origin 欠落・CSRF 欠落／不一致の拒否（いずれも状態変更なし）、中継を介さない直接要求での対照
- 手順4（セッションの試験）： 登録後に発行した検証用セッションで操作が通り、復旧を挟むと旧セッションが拒否され、新セッションが通ること
- 手順5（復旧の試験）： 誤った復旧キーの拒否、復旧キーだけ（対象の新しい ID トークンなし）では復旧できないこと、復旧途中の意図的失敗で旧資格が維持されること、正常な復旧で旧 ID トークンの拒否・新 ID トークンの許可、復旧記録が旧新の対応を含むこと。復旧後に両アカウントで再ログインし、完了記録・復旧記録との事後照合（ハッシュの再計算による一致確認）を行う
- 手順6（再起動）： 運営チャネルからのみ実行できる試験用フックで DO を強制的に再起動し、起動識別子の変化と、資格状態・再登録拒否・セッション拒否が維持されることを確認する
- 手順7（後片付け）： 順序は「（変形Aの場合）workers.dev の無効化 → 到達不能の確認 → 受付機能なしのコードへ復帰 → 全シークレットの削除 → 削除後の拒否確認」とする。各段で失敗した場合は代替経路（Codex のダッシュボード／Wrangler）で1回だけ再試行し、それでも失敗したら状態を記録して即座に開発者へ上げる。終了時に Worker コード・ルート・workers.dev・シークレット一覧を Muse と Codex が独立に照合する。`mtrial_*` テーブルは第2節の扱いに従う

## 7. 中止条件

- 対象（アカウント・Worker 名・名前空間 ID・インスタンス）の照合が一致しない
- 本番 Worker や本番データへの到達が疑われる事象が出た
- シークレットの値がチャット・文書・記録へ漏れた疑いがある
- 開発者の承認なしに公開先を作る必要が生じた
- 計画にない操作が必要になった（その時点で止めて記録し、判断を仰ぐ）

## 8. 分担

- Muse： ハーネスとログイン画面・中継の作成、手順1 の模擬試験、手順2 のデプロイ、手順3〜6 の実行（API 側と Worker 側の観測）、記録と報告書の作成。復旧キーの値は保持しない
- Codex： 本計画と結果の設計レビュー、手順0・7 の独立照合、初回用シークレットと復旧キーの生成・設定と復旧時の提示、PC 側でのログイン画面と中継の実行、2つのテストアカウントでのログイン、Data Studio での記録件数の独立確認
- 開発者： 判断事項のみ（変形A／変形B の選択、方式の確定、フェーズ2 の開始、本番に関わる事項）

3. 変形Bの edge-preview セッション取得を、準備・照合とは別の関門として手順2に明記した。拒否や権限不足は回避せず事実として記録する
4. 配置前のコード共有を手順2に明記し、ハーネス一式を `docs/prototypes/stage1-next-prototype/` に置いた。コードに実装された条件と手順1の29項目の対応は、手順1の記録に追記した

v0.2（1回目のレビューへの対応）：

1. workers.dev の一時有効化を、開発者の明示的な承認を要する変形Aと、現行条件を維持する変形Bに分離した（第3節）

5. 後片付けの順序、失敗時の代替経路と上限、終了時の独立照合、試験テーブルの扱いを明記した（手順7、第2節）
