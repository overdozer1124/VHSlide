# 段階① フェーズ1 次期独立試作の実施計画（A と C の組み合わせ案）v0.1

根拠： 実装設計書 v2.10 第3節、段階①検証計画 v0.4（A1〜A7）、候補比較（中間、7826fa3 反映済み）。これは独立試作の計画であり、製品実装の承認や本番方式の確定ではない。実施は検証専用環境に限る。

## 1. 目的

候補比較で残った不足のうち、次の4点を実証の対象とする。

- A4： 実 Cloudflare の運用経路そのものでの Origin／CSRF の拒否（従来はローカル模擬のみ）
- A5： 運営者認可と対象の証明の分離を、実際に別主体・別経路で実施する（従来は同一ローカルプロセスが2つのキーを保持していた）
- A2・A7 の記録： 完了記録・復旧記録に、対象環境の識別子、対象の識別子、登録日時（復旧では旧新の対応と日時）を、後から照合できる形で残す
- A6： 実行先の照合を、実施者（Muse、API 経由）と独立した確認者（Codex、ダッシュボード／Data Studio）の双方で行う

## 2. 識別子の記録方法（解釈の明記）

- 設計書第3節は完了フラグに「対象環境・sub・登録日時」の記録を求め、user_id は sub から決定的に導出される（第2.2節）。現行コードでは user.id は sub そのものである。
- 本試作では、生の sub を検証用 DO に保存せず、sub の SHA-256 ハッシュを対象識別子として記録する。導出が決定的であるため、提示された sub を同じ方法で変換すれば事後の照合が可能であり、塩を削除した HMAC（照合不能）とは異なる。
- 本番で生の sub を記録するか導出済み ID とするかは、フェーズ1最終報告で解釈として明記し、方式確定時の確認事項とする。本試作の記録方法はその判断を先取りしない。

## 3. 構成

検証用 Worker `vhslide-stage1-verify-20261101-a`、DO 名前空間 `ef29957c85744eccaea6db64af433868`、インスタンス `stage1-verification-only-20261101` を使う。試作用テーブルは新しい接頭辞 `mtrial_*` とし、既存の `gtrial_*` 等の記録には触れない。

試験の時間帯に限り、検証用 Worker に受付経路を開く（workers.dev を一時的に有効化し、終了時に無効化して受付機能なしのコードへ戻す）。経路は次の要素で守る。

- 案A の要素（一時性）： 経路は試験時間帯だけ有効。登録は本人の Google セッション（ID トークン、aud は検証用 OAuth クライアント）と初回用シークレットの提示の両方を要求する。完了後は経路を停止し、シークレットを除去する
- 案C の要素（運営の独立認可）： 経路の有効化・停止とシークレット類の設定・削除は、運営チャネル（Muse の Cloudflare API トークン）からのみ行う。復旧は運営キーと復旧キーの提示を要求し、対象の新しい Google ログインと組み合わせる。旧アカウントのセッションは要求しない
- ブラウザーからの変更要求には、正規 Origin の一致と、検証用セッションに結びついた CSRF トークンを要求する
- 登録と完了記録は DO の1トランザクションで記録する。復旧は旧資格の失効・新資格の付与・復旧記録を同一の原子的更新で行う
- 検証用セッションは登録後に発行し、管理操作の判定では毎回現在の資格を照合する

PC 側には、検証用 OAuth クライアントの生成元 `http://localhost:8787` で動くログイン画面と中継を用意する（Muse が作成し、Codex が PC で実行する）。ID トークンの検証は Worker 側で行う（tokeninfo による検証項目は Codex の前回試作と同じ： aud・iss・exp・nonce・email_verified・sub の存在）。

鍵の所在（値はチャット・文書・GitHub に残さない）：

- 運営キー・復旧キー： Muse が生成し、Worker シークレットとして設定する。提示は Muse の実行環境からのみ行う
- 初回用シークレット： Codex が PC 側で生成し、Wrangler から Worker シークレットとして設定する。提示はログイン画面経由で行う
- どの鍵も単独では登録も復旧もできないことを試験項目に含める

## 4. 手順

- 手順0（照合）： Muse が API で検証用 Worker の設定と連携（VERIFY_ONLY のみ、名前空間 ID 一致）を読み取り、Codex がダッシュボードで独立に照合する。DO 内の既存テーブル一覧を取得し、開始時点の状態として記録する。対象が一致しなければ中止する
- 手順1（ローカル模擬）： Muse の環境でハーネス一式を作成し、Miniflare の模擬 DO と模擬 ID トークンで全フローを試験する。結果は模擬層として区別して記録する
- 手順2（配置）： Muse が API 経由でハーネスを検証用 Worker へデプロイする（API デプロイ自体の可否確認を含む）。Codex が初回用シークレットを設定し、Muse が運営キー・復旧キーを設定する。シークレットの一覧に想定外の項目があれば中止する
- 手順3（登録の試験）： 通常登録、再登録の拒否（409）、並行登録（成功1・拒否1）、登録途中の意図的失敗後の資格なし、誤った初回用シークレットの拒否、Origin 不一致・CSRF 欠落／不一致の拒否（いずれも状態変更なし）
- 手順4（セッションの試験）： 登録後に発行した検証用セッションで操作が通り、復旧を挟むと旧セッションが拒否され、新セッションが通ること
- 手順5（復旧の試験）： 誤った復旧キー・運営キーの拒否、復旧途中の意図的失敗で旧資格が維持されること、正常な復旧で旧 ID トークンの拒否・新 ID トークンの許可、復旧記録が旧新の対応を含むこと。復旧後に両アカウントで再ログインし、完了記録・復旧記録との事後照合（ハッシュの再計算による一致確認）を行う
- 手順6（再起動）： 運営チャネルからのみ実行できる試験用フックで DO を強制的に再起動し、起動識別子の変化と、資格状態・再登録拒否・セッション拒否が維持されることを確認する
- 手順7（後片付け）： workers.dev を無効化し、受付機能なしのコードへ戻す。全シークレットを削除し、一覧が空であることを Muse（API）と Codex（Wrangler）の双方で確認する。最終状態を読み戻して記録する

## 5. 受入条件への対応

- A1： 手順2・3 で実経路の到達と登録を確認する。Data Studio の直接操作（案B）の実証とは混同しない
- A2： 手順3 の競合・再実行拒否・途中失敗のロールバックと、手順6 の再起動後の保持、完了記録の必須項目（環境識別子・対象識別子・登録日時）で判定する
- A3： 手順2 の生成・設定、手順7 の削除と削除後の拒否で判定する。実運用の保管・ローテーション手順そのものは本試作の対象外と明記する
- A4： 手順3 の Origin／CSRF 拒否を実経路で確認する
- A5： 運営チャネル（Muse の API）と対象の証明（PC 側の Google ログイン）が別主体・別経路であること、各鍵の単独使用では登録・復旧ができないことで判定する
- A6： 手順0 と手順7 で、Muse と Codex が独立に照合する
- A7： 手順5 の復旧の実演（旧セッション・旧トークンの拒否、記録の事後照合を含む）で判定する。製品セッションの失効を示すものではない

## 6. 中止条件

- 対象（アカウント・Worker 名・名前空間 ID・インスタンス）の照合が一致しない
- 本番 Worker や本番データへの到達が疑われる事象が出た
- シークレットの値がチャット・文書・記録へ漏れた疑いがある
- 計画にない操作が必要になった（その時点で止めて記録し、判断を仰ぐ）

## 7. 分担

- Muse： ハーネスとログイン画面・中継の作成、手順1 の模擬試験、手順2 のデプロイと運営側シークレットの設定、手順3〜6 の実行主体（API 側）、記録と報告書の作成
- Codex： 本計画と結果の設計レビュー、手順0・7 の独立照合、初回用シークレットの生成と設定、PC 側でのログイン画面の実行と2つのテストアカウントでのログイン、Data Studio での記録件数の独立確認
- 開発者： 判断事項のみ（方式の確定、フェーズ2 の開始、本番に関わる事項）

## 8. 対象外

製品コードの変更、本番環境へのアクセス、main 統合、本番デプロイ、方式の確定は含まない。
