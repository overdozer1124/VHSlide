## 1. 設計の進め方

- 段階①〜④（第10節）の順に実装する。各段階は独立して成立し、レビュー・検証できる単位とする。前の段階の成果だけでは基本方針に違反する中間状態を、本番環境に置かない
- 認可は Cloudflare 側と Node 側の両方に同じ方針で実装する。画面はサーバーが返す操作資格を表示に反映する（画面側だけで判断しない）
- 作品本文の保存形式は変更しない。追加するのはサーバー管理データ（所属・役割・スペース・状態）と認可処理である

## 2. データモデル

いずれもサーバー管理データとし、作品 JSON / ZIP には含めない（含めて復元できてはいけない）。

### 2.1 役割モデル（分離が前提）

- organization_members の区分は **teacher / student** とし、**学校管理者資格は別のフラグ** `is_school_admin` で持つ。教師でもある学校管理者を正しく表せるようにするためである
- **教師資格を持たない学校管理者も表現できるよう、`role` は NULL を許可する**（管理者のみの所属）。`is_school_admin=true` でも、教師資格や作成許可がなければ作品作成・本文編集は認めない
- 学校管理者への任命だけでは、作品作成・本文編集の権限は増えない（基本方針の分離解釈をモデルで保証する）
- **複数校への所属は許可する**（決定済み）。その場合、作品の作成先の学校は作成時に選択し、作品の organization_id は選択した学校になる。学校をまたいだ管理操作はできない
- スペース作成権限は所属とは別の `can_create_space` で持つ。**作成権限と管理権限は別フラグ**であり、解除はどちらを外すかを指定する（C案）

### 2.3 既存テーブルへの変更

- users: スーパー管理者フラグ `is_super_admin`（bool）を追加する。学校役割は users に持たせない。現行には `SELECT users.*` があるため、追加後は**取得列・返却項目を明示し、内部フラグが既存の参加者向け応答へ混入しない**ようにする
- 作品（decks）: 次を追加する
  - `organization_id`（NULL 可）: 学校管理対象かどうか。学校所属アカウントが作った作品は、スペース未所属でも作成時点でセットする（第8節）
  - `space_id`（NULL 可）: 所属スペース。NULL は一般作品または取り込み前の学校作品
  - `provisional_manager_user_id`（NULL 可）: 暫定作品（space_id が NULL の学校作品）の管理担当（第2.6節）。サーバー管理データであり、作品 JSON / ZIP には含めない
  - 既存の owner は「作成者記録」として残す。学校作品では owner 一致による無条件のホスト判定を行わない
- 復元タスク: 復元先の管理区分（organization_id / space_id）をサーバー側に保持するカラムを追加し、再開・確定時にも検証できるようにする

### 2.4 移行の注意（レビューで確認された現行実装）

- 現行コードには、列名を省略した `INSERT INTO users VALUES(...)` と `INSERT INTO decks VALUES(...)` が両サーバーにある。**列追加だけでは既存のログイン・作品作成が壊れる**ため、スキーマ移行と同時に、対象の INSERT を列名指定へ変更する
- 既存作品は organization_id / space_id ともに NULL のまま = 一般作品として従来どおり扱う（自動で学校作品へ変えない）
- 教師の試作品の取り込みでは、作品の移行とあわせて、古い owner 権限の扱い、既存の招待・共有設定、接続中セッションの扱いを確定してから実行する

### 2.5 生徒作品の管理主体

- 生徒が作った作品の管理者は、作成時点の管理者を複写して固定しない。**認可のたびに、現在のスペース管理者（space_members）から導出する**。これにより移管・解除時の同期漏れを防ぐ
- 制作者には本文編集権限のみを付与し、参加承認・共有範囲設定・削除などの管理操作は管理者に帰属させる

### 2.6 暫定作品の管理担当（指定方式の具体化）

段階②の暫定作品は、スペースの管理者モデルがまだ存在しないため、作品ごとに管理担当を持つ（決定済みの「指定方式」の具体化）。

- 保存先： decks.provisional_manager_user_id（第2.3節）。認可のたびに現在の値を参照し、複写した権限を固定しない
- 選出： 作成時に指定できる。指定できるのは、その学校の学校管理者または教師。**未指定の場合は、その学校の学校管理者のうち、最初に登録された有効な学校管理者を担当とする**（開発者が 2026-10-31 に確定。学校管理者全員が自動で管理者になる形にはしない）。「最初に登録された」とは、学校管理者資格の付与が確定した順（school_admin_applications の確定順）を指す。同時刻の場合は、所属（organization_members）の作成順、それも同じ場合は user_id の順で tie-break する。既定の担当は、認可のたびに現在の有効な学校管理者から導出するため、管理者の任命・解除がそのまま反映され、作品側に古い担当が残ることはない。対象校は作品の organization_id で判定する
- **管理主体の常時存在**： 学校には必ず管理主体が存在する状態を保つ（管理主体がいないと、教師・生徒アカウントの設定自体ができないため）。学校管理者が1名もいない学校では、**スーパー管理者が暫定の管理主体となる**（決定済み）。学校管理者が任命された時点で、その学校の管理主体は学校管理者側へ移る
- 変更（移管）： 現在の担当者、学校管理者、スーパー管理者が変更できる。変更は作品レコードへの直列化された更新とし、確定した時点で旧担当者の管理権限は失われる。並行した変更は、後から確定した方を有効とする
- 失効時： 担当者の所属が無効化される・資格を失った場合は、管理担当は自動で既定の選定（最初に登録された有効な学校管理者、いなければスーパー管理者）に戻り、その旨を記録する
- 権限の範囲： 管理担当の権限は管理操作のみであり、**スーパー管理者が管理主体となっても、作品の本文編集権限は自動では付与されない**（第2.1節・第4.2節の分離どおり）
- スペースへの取り込み後： 作品がスペースへ取り込まれた時点で暫定作品の管理担当は役割を終え、以後はスペースの管理者モデル（space_members）で判定する

## 3. 初代スーパー管理者の初期登録（方式は未決・確定条件を定義）

「申請を受けて登録」は学校管理者の任命手順であり、初代（荒木本人）の登録は別途決める。登録方式は**未決**とする。v2.3 で具体化した運営用経路は、常設の管理ルート＋シークレットという構成が実質的に案Aへ近づいており、現行に実在する運用経路とも確認できていないため、確定形としては扱わない。候補は次の3つとし、段階①の着手時に確定条件（後述）をすべて満たす形で選ぶ。

- 案A： 初期登録シークレットによるブートストラップ（認証済み POST で、ログイン中の sub ＋シークレットの提示により登録。登録後はエンドポイントを無効化し、シークレットを環境から除去する）
- 案B： 運営操作による直接登録（常設の受付経路を持たず、デプロイ側の運営操作で Directory DO の保存先へ直接記録する）
- 案C： 運営用経路（Directory Worker の管理ルート＋運営用シークレット＋本人セッション。v2.3 で具体化した構成）

いずれの案でも不変とする条件：

- 前提： Cloudflare 側の保存先は Directory Durable Object である。D1 向けの一般的な SQL 操作を前提にしない
- user_id は Google の sub から決定的に導出される（第2.2節）。「sub から既存 user_id への対応」は導出規則そのものであり、別途の対応表は持たない
- 登録と**登録完了フラグ**（対象環境・sub・登録日時）の記録は原子的に行い、並行実行で二重登録されないようにする。完了フラグがある場合は再登録を拒否し、通常起動で権限を再付与しない
- 対象環境（本番／検証）の識別子を手順と記録に含め、別環境への誤登録を防ぐ確認を入れる

確定条件（採用する案について、段階①の着手時に具体化して確認する）：

- 認証情報の渡し方（シークレットの生成・保管・提示経路）と、秘匿・無効化・ローテーションの手順
- HTTP 経路を使う案では Origin／CSRF の検証と、経路の有効期間（常設しない場合は有効化と停止の手順）
- 運営者の認証と、登録対象アカウントの証明（対象 sub が本人のものであることの確認方法）
- 対象環境の独立した確認（操作対象の環境を、操作者の申告以外でも照合できること）
- 事故時の復旧が、後述の復旧手順で実際に回ること

復旧手順（誤登録・アカウント喪失時。初期登録とは別の手順として分ける）：

- **復旧の認可は、喪失した旧アカウントのセッションを要求しない**（アカウント喪失の復旧では成立しないため）。復旧の認可は、運営チャネル自体への権限（デプロイ・運営操作を行えること）と、対象環境の識別子の再入力で構成する
- 新しい登録の対象 sub は、新アカウントで通常ログインして確認する（新アカウントの証明はそのセッションで行い、旧アカウントの証明は求めない）
- 復旧は「既存のスーパー管理者権限の失効」と「新しい登録」を、**同一の原子的更新**で行う。失効だけ・付与だけの中間状態を作らない
- 復旧の実行記録（日時・対象環境・旧 sub と新 sub の対応）は必須として残す（第2.2節の監査ログ任意とは別扱いとする）。復旧後は、旧アカウントの権限が残存していないことを資格照会で確認してから完了とする


## 4. 認可設計

### 4.1 認可の分岐（基本方針 第2節の実装形）

認可は単純な直列判定にしない。**対象の区分ごとに必要条件を分ける**（スペース未所属の暫定作品や一般作品まで一律に拒否しないため）。

- 一般作品（organization_id が NULL）： 従来の判定のまま
- 学校の暫定作品（organization_id あり、space_id が NULL）： 組織所属の有効性と、組織側の管理主体・参加資格で判定する
- スペース所属作品： 組織所属 → スペースの参加資格・状態 → スペース管理者（管理操作）→ 作品別の参加資格と編集範囲（EditAccess）の順に判定する

アプリ全体の管理操作はスーパー管理者のみ。通常の作品操作では、スーパー管理者でも対象区分の判定を通す。

### 4.2 操作の分類（host 一括りにしない）

- 新しい管理権限を既存の `host: boolean` に詰め込まない。**操作ごとに「管理操作」か「作品操作（本文編集など）」かを定義する**。管理者に本文編集権限まで誤って付与しないためである
- クライアント側の owner 比較による操作表示も、サーバーが返す操作資格に置き換える

### 4.3 チェックを入れる箇所

基本方針 第6節の表に加え、レビューで確認された対象を含める。

- 作品の作成／コピー／取り込み／復元（復元タスクの一覧・再開・取消・画像アップロード・確定を含む。再開・確定時にも再検査し、持ち込まれた共有設定で権限を拡大しない）
- 招待・参加申請・承認／取り込み申請・移管申請・削除申請の確定操作（対象スペースの管理資格と、同一スペースの申請 ID であることを確認）
- 一覧・作品・画像・付箋・履歴の取得（履歴一覧・取得・履歴からの復元を含む）。URL や作品 ID の提示だけでは許可しない
- ゴミ箱の一覧・削除・完全削除・削除取消
- バックアップの取得と整合性検証（backup/verify）。所属・権限・表示名の変更も検証の対象に含める
- 共有先・参加者・行担当アカウント・参加申請の取得
- 集合（追従）の開始・終了・制御などのホスト操作
- 画像の取得・アップロードと容量予約
- ページ編集系の更新（Cloudflare 側の既存の再認可・編集検査にスペース条件を追加。Node 側も同一方針）

### 4.4 WebSocket と失効の伝播

- 接続時と更新時に認可を評価する。資格を失った接続が、他人の更新や presence を受け取り続ける問題は、更新送信者の再認可とは別に対処する
- **失効は送信だけでなく受信にも適用する**： 正の方式は「失効通知のプッシュ」と「短い期限つきの配信許可（リース）」の併用とする。配信ごとの資格照会は行わない。Directory DO は、失効（所属の無効化・権限解除・スペースの状態変更）を確定したとき、その利用者が接続している SlideRoom へ失効通知を送る。SlideRoom は通知を受けたら、その利用者への配信を直ちに止め、接続を切断する（または操作種別ごとの扱いに従う）。通知が届かない場合に備え、SlideRoom が保持する受信者ごとの配信許可には短い有効期限（設計値60秒、許容上限5分）を設け、期限の更新は Directory（正本）への認可確認で行う（資格版数の照合は補助とする）。失効した利用者の許可は更新されないため、**配信は失効の確定から最大でリース期間以内に必ず止まる**。負荷は接続中の受信者数とリース期間で決まり、配信量には比例しない
- 非同期処理をまたぐ操作（画像・バックアップ・復元確定など）は、処理開始時の資格だけを使わず、**取得・確定の途中でも再検査する**
- 権限解除・スペース終了／削除時の扱い（即時切断か、読み取り専用への降格か）は操作種別ごとに決める
- **再確認のタイミング**： 資格の再確認は次の時点に限る。(i) 接続の開始時（初期同期の前） (ii) 接続の休眠・復帰時 (iii) SlideRoom が休眠から目覚めたとき、その時点で接続している受信者について一括で（配信ごとではなく、目覚めごとに1回） (iv) 送信・編集などの操作時（従来どおり送信者側を検査） (v) リースの期限更新時。Directory は利用者ごとの**資格版数**（単調増加）を保持する。再確認で配信の継続・再開を許可する場合は、正本（Directory）への認可確認を必須とし、資格版数の照合は、変化の検知と確認の間の失効の検出に用いる
- **保証と限界（仕様として明示する）**： 失効通知が到達すれば、その時点で配信は止まる。通知が到達しない場合でも、リースの期限切れにより、新規の送信は失効の確定から最大でリース期間（設計値60秒）以内に必ず止まる。期限は認可要求の送信時刻を起点として数えるため、この上限は DO 間の時計差や応答の遅延に依存しない（失効より前に送られた要求には失効前の資格で許可が出得るが、その期限も失効からリース期間を超えることはない。失効より後に送られた要求は、正本の確認で拒否される）。リース期間の範囲内で既に始まっていた配信が完了することは許容するが、それは個々の送信処理のタイムアウト（実装で定める短い上限）までに限られ、超える送信は中断する。この上限つきの遅延は、基本方針メモの「資格を失った人には許可しない」の実装上の具体化として、Codex の指摘を受けて開発者が 2026-10-31 に明示的に判断した。判断の内容は、(i) 失効確定後も最大リース期間の間は新規受信があり得ること、(ii) 削除猶予中の作品の配信もこの対象に含むこと、の2点であり、基本方針メモ（v3.7）にも注記として記録した。数値の範囲（通常時60秒・許容上限5分・期限内に開始した送信の完了の許容）は、開発者が 2026-10-31 に明示的に確定した。更新の確認ができない場合（Directory へ届かない等）は、許可は期限で失効して配信は止まり、再開は再接続時の初期同期でのみ行う（フェイルクローズ）。受信者自身の取得・送信の操作は従来どおりその都度検査される
- **リース期限の基準（上限が時計差・応答遅延に依存しない定め方）**： 配信許可は認可要求に紐づける。SlideRoom は、認可要求を送る直前の単調時計の時刻を記録し、その受信者についての使用期限を「要求送信時刻＋リース期間」とする。許可は要求より前に発行されることはないため、この期限は、Directory と SlideRoom の時計の差や、応答の遅延の影響を受けない。応答には要求ID・資格版数・発行順序番号を含め、対応する要求のない応答、期限を過ぎて届いた応答、順序番号の古い応答は捨てる。SlideRoom は送信のたびに期限を評価し（DO への照会を伴わないローカルな確認）、期限を過ぎた受信者へは送信しない。期限内に開始した送信の完了は許容する。単調時計が利用できない、または期限を評価できない許可は、受け入れずに配信を止める（フェイルクローズ）。休眠・再起動の際に SlideRoom が保持する許可はすべて破棄され、再開は再確認から行う。単調時計の挙動（休眠・再起動・長時間停止を含む）が実行環境で確認できない場合は、この方式を前提にせず、設計へ差し戻す
- **停止後の遅延応答で再許可しない**： 失効通知で停止した受信者については、その後に届いた、失効前に発行された許可応答（古い資格版数・順序番号のもの）では配信を再開しない。再開は、再接続時の初期同期における正本確認でのみ行う。この扱いは、削除猶予中の作品の配信にも同じく適用する
- **同期の欠落を作らない**： 配信を止めた受信者への配信再開は、再接続時の初期同期（資格の再評価を含む）でのみ行う。止まっていた間の更新を後から補完しない
- 対象は全配信経路とする： 通常の更新配信、presence、接続時の同期初期データ、ブロードキャスト。接続の休眠・復帰時も、配信再開前に再評価する
- **実測を公開ゲートとする**： 失効通知の到達性（休眠中のルームを含む）、リース更新の負荷、目覚め時の一括再確認と再接続時の初期同期の遅延を、代表的な接続数・作品数・利用条件で段階③に実測し、結果を記録する。判定基準は、他のアプリと共有する Workers Free の枠の中で、想定する接続数・利用頻度・時間帯に対して余裕を持って収まることとし、満たさない場合は公開せず設計へ差し戻す。リース期間の確定値はこの実測で決める（許容上限5分の範囲内。段階②で学校作品を公開する場合は、失効・漏えい・負荷の試験をその時点の受入へ前倒しする。第9節）。通知が構造的に届かない経路が見つかった場合でも、保証はリースで担保される

### 4.5 作成条件の分離

`can_create_space` を作品作成の許可に流用しない。作成条件は分けて定義する。

| 作成の種別 | 条件 |
|---|---|
| スペースの作成 | 対象校の所属が有効で、role=teacher かつ can_create_space=true（学校管理者資格だけでは不可。スーパー管理者はアプリ全体の権限で可） |
| 学校作品の作成（暫定作品を含む） | 対象校の所属が有効で、role が teacher または student（生徒の作品作成は許可が決定済み）。作成先の学校は、複数所属の場合は作成時に選択する |
| 一般作品の作成 | 従来どおり。ただし学校所属アカウントのクラウド作成は学校管理対象として扱う（下記の区分ルール、第8節） |

学校所属者の区分ルール（コピー・復元・派生を含む）：

- 学校所属アカウントがクラウドで作成した作品は、コピー・復元・既存作品からの派生作成を含め、すべて学校管理対象として作成される（第8節）。区分の判定はログイン種別ではなく、アカウントの所属と作成経路で行うため、一般用ログインを選んでも学校制限は回避できない
- 学校作品のコピー・復元・派生で、一般作品（organization_id が NULL）を作ることはできない。学校区分から一般区分への変換経路は設けない（取り込みの逆方向は不可）
- 学校所属者が所属登録前から持っていた一般作品は、一括移行せず一般作品のまま扱う（第2.4節）。その作品を学校で使う場合は、制作者の申請と管理者の承認による取り込み（第4.6節）を通す
- 複数校に所属する場合は、作成時に作成先の学校を選択する。無効化された所属の学校は選択できない。権限変更・所属変更の処理中は、確定するまで作成を保留し、確定後の資格で再検査する

### 4.6 取り込み・ZIP復元の順序とロールバック

取り込みと ZIP 復元は性質が異なるため、分けて定義する。

**既存の一般作品の取り込みは「移管」である**（コピーではない）。deck_id は変わらず、制作者記録もそのまま引き継がれる。変わるのは区分（organization_id／space_id）だけである。

1. 移管の開始時に、作品を作業状態にする。作業状態は第4.3節の全経路（取得・配信・更新・共有操作）に適用する。あわせて、その作品の SlideRoom へ停止を指示し、接続中の参加者への配信と更新の受付を止めたことを確認する（確認できない間は次の段階へ進まない）。停止の確認とは、その時点で接続している参加者がおらず、進行中の配信がない状態をいう。状態変更の直前に SlideRoom が許可していた接続・配信も、この停止確認の中で終了させる。移管の操作状態（操作ID・現在の段階）は作品レコードに記録し、通知の失敗や再起動があっても、記録された段階から冪等に再開できる。作業状態の間は、その作品への新規接続と、休眠復帰後の配信再開も SlideRoom 側で拒否する（接続・復帰は認可の確認点であり、作品の操作状態を正本（Directory）で確認する）
2. 区分のフリップ（organization_id／space_id の設定）は、作品レコードへの単一の更新を確定点とする。区分は Directory 側の作品レコードだけが持ち、SlideRoom 側のデータは区分を持たないため、フリップ自体に DO 間の部分失敗は生じない
3. 氏名等の変換は、保存データを書き換えるのではなく、第6節の配信時変換で行う。したがって**フリップ前であれば、作業状態を解除するだけで元作品は無傷で戻る**（ロールバック）。**フリップ後に一般作品へ戻すことはしない**（第4.5節の変換禁止どおり）。誤った取り込みへの対処は、学校管理対象のまま共有を止めた状態で管理者が行う（作品の削除は削除申請の手続きによる）
4. フリップと旧権限の無効化は、作業状態のもとでまとめて確定し、最後に作業状態を解除して公開する。一般作品時代の招待リンクは無効とする（参加の可否は現在の区分で判定し、旧リンクでは学校区分の作品へ参加できない）。既存の共有設定は学校区分では引き継がず、管理者が再設定する。履歴は作品に付随して移管されるが、配信時は第6節の変換を通す。容量予約は同じ deck のため二重に計上しない
5. フリップと旧権限の無効化は Directory 側のデータに対する操作であり、公開（作業状態の解除）は全段階の完了を確認してから行う。途中で失敗した場合は作業状態のまま、記録された段階から再開し、中途半端な状態で公開しない。停止できない場合・再起動・一部だけ変更された場合の再開とロールバックは、段階③の受入試験に含める。あわせて、停止確認後から公開までの間の再起動・重複した指示でも二重にフリップしないこと、変換不能な場合は非公開のまま維持されることを、同試験で確認する

**ZIP 復元は「新規作成」である**（新しい deck_id を持つ別の作品を作る。招待・参加者・履歴の移管は起きない）。

1. 復元先は、最初から学校区分（学校作品への復元の場合）として、参加者に見えない作業状態で作成する（復元タスクの状態で管理し、一覧・取得・配信の対象にしない）
2. 共有設定は復元しない（学校作品の復元では共有設定を破棄する。第6節）。ZIP 内の投稿者名等のシステム由来データは、配信時変換（第6節）で安全な表示名に置換されるため、そのまま再配信されることはない
3. 変換と検証がすべて完了した時点で初めて、作品を通常状態へ移し、参加資格のある利用者へ見えるようにする
4. 途中で失敗した場合は、作業状態の作品と持ち込んだ画像等を破棄してロールバックする。中途半端な状態の作品を参加者へ見せない。旧形式の ZIP も同じ順序で処理し、形式の互換は読み取り側で保つ
5. 上記の順序と、氏名・メールが各配信面・書き出しに混入しないことは、両サーバー（Node／Cloudflare）で検証を受入条件とする

## 5. アカウント設定フロー（登録制の実装形）

1. 学校管理者が、自校の教師・生徒をメールアドレスで事前登録する（preregistrations）
2. 本人が Google ログインした時点で事前登録と結びつけ、sub 由来の user_id で organization_members を生成する。以後の判定は user_id で行う
3. 一般用・学校用のどちらのログインでも、同じ登録資格へ結びつくこと（ログイン種別は資格判定に使わない）
4. 役割（teacher／student）と作成権限（can_create_space）は学校管理者が設定・変更できる。ただし**学校管理者資格（is_school_admin）の付与・解除を確定できるのはスーパー管理者のみ**とし、事前登録に planned_is_school_admin が含まれる場合もスーパー管理者の承認なしに確定しない。事前登録の取消・重複・別校への操作は拒否する
5. 所属の無効化（退職・転校）は status=無効 とする。学校管理対象の作品には引き続き学校側の認可を適用する

事前登録の状態遷移と競合（第2.2節の補足）：

- 状態は 有効／結びつけ済み／取消 の3つ。遷移は 有効→結びつけ済み（ログイン時の結びつけ）と 有効→取消（登録した学校管理者またはスーパー管理者）のみで、結びつけ済み・取消からは遷移しない
- 一意性： 有効な事前登録について (email, organization_id) を一意とする。同じメールでも学校が異なれば別の事前登録を持てる（複数校所属の許可と整合）
- 結びつけと取消の競合： どちらも事前登録レコードへの原子的な状態遷移とし、先に確定した方を有効とする。取消後にログインしても結びつけは起きない
- 無効化された所属との関係： (user_id, organization_id) の所属が無効の場合、事前登録による結びつけでは所属を復活させない。その事前登録は結びつけずに取消（理由：所属無効）へ遷移させる。再度所属させる場合は事前登録ではなく、学校管理者による所属の再有効化として別途行う（**スーパー管理者の確認は必須としない**。開発者が 2026-10-31 に確定）。再有効化で復活する要素は後述のとおり個別に定める
- メールアドレスの変更： 事前登録は登録時のメールに結びつく。本人が別のメールでログインした場合は結びつかず、学校管理者が旧登録を取り消して新しいメールで登録し直す
- 管理者資格の独立性： planned_is_school_admin は結びつけで効力を持たない。結びつけで生成される所属の is_school_admin は常に false とし、学校管理者資格は school_admin_applications に対するスーパー管理者の確定だけで付与される（事前登録の作成・変更の経路からは付与できないことを不変条件とする）

所属の再有効化で復活する要素（個別定義）：

- 再有効化は学校管理者が行い、スーパー管理者の確認は必須としない（決定済み）
- 復活するのは所属そのもの（organization_members の status と role）のみとする。role は再有効化の時点で学校管理者が確認して設定する
- is_school_admin は復活しない。学校管理者資格は、school_admin_applications に対するスーパー管理者の確定でのみ、改めて付与される
- can_create_space は復活しない。再有効化の時点では false とし、学校管理者が必要に応じて改めて設定する
- space_members（スペース参加・管理者）は復活しない。スペース管理者による再承認・再招待による
- 作品の共有・参加資格（EditAccess 等）は復活しない。作品の管理者が改めて付与する。本人が作成した作品の制作者記録は作品に残っており、区分ごとの判定（第4.1節）は現在の所属で改めて行う

所属の無効化時の波及（再有効化で復活しないことの実装）：

- 所属を無効化する操作の中で、その利用者の当該校に関わる space_members（参加・管理者）と、学校作品への共有・参加資格（EditAccess 等）を「解除」状態へ遷移させる。レコード自体は履歴として残るが、認可では常に解除状態として扱う。波及の対象は当該校（organization_id）の範囲に限る。順序は、所属の無効化を先に確定させ（新しい認可はこの時点で失敗するようになる）、波及はその後に冪等に行う。波及の途中で失敗しても所属の無効化は維持し（安全側）、残りの波及は再開できる
- 再有効化は organization_members の status と role だけを対象とし、上記の解除済みレコードには触れない。再付与は各付与主体が、対象レコードを明示的に有効へ戻す（または新規に作る）操作でのみ行われる
- **世代番号による恒久的な無効化**： organization_members に世代番号を持たせ、無効化のたびに増やす。space_members と学校作品への共有・参加資格のレコードは、付与時点の世代番号を保持し、認可では現在の所属の世代番号と一致するレコードだけを有効とする。したがって、波及が未完了のまま再有効化しても、旧世代のレコードは認可で常に無効であり、復活しない。再有効化は世代番号を戻さない。再付与は、新しい世代のもとで明示的に行う
- **世代の確認は全経路で行う**： 認可判定、配信リースの発行・更新、作成・復元の確定、管理者による代行操作は、対象校の現在の所属世代を前提とする。無効化の後に残った非同期処理（復元の確定、波及の残り等）は、対象の世代が既に進んでいる場合、その世代の付与・資格には触れない（旧世代向けの解除が、新世代で再付与された資格を消すことはない）。複数校に所属する場合は、学校ごとに世代を独立に扱う
- **既存行の移行**： 世代番号の導入時点で既に存在する space_members・共有資格のレコードには、導入時点の世代番号を一括で付与する。付与漏れのレコードは無効として扱い、必要なものは再付与する
- 受入条件として、解除済みレコードが残った状態で再有効化しても、スペース参加・作品共有が復活しないことを、複数校所属・旧管理担当・制作者としての権限を含む形でテストで確認する（第9節）

メールアドレスと結びつけの補足：

- 事前登録との照合に使うメールは、Google の認証応答で検証済み（email_verified）のものとし、照合は小文字化した値で行う
- 所属の正本は sub 由来の user_id であり、メールは結びつけの補助である。本人の Google アカウントのメールが変わっても、sub が同じであれば所属は維持される
- 別の人が同じメールアドレスを使うようになった場合でも、消費済み・取消済みの事前登録は再び結びつかない。新しい事前登録が作られた場合は、その時点でログインした本人（sub）に結びつくため、学校管理者は不要になった事前登録を取り消しておく運用とする

## 6. 表示名と共有データの分離

必須方針： **システムが保持する実名・メールアドレス等を、参加者（生徒）へ配信しない**。表示用番号も個人と対応するため、匿名化とは扱わない。

- 参加者向けデータは、共通の変換処理を通して生成する。対象は presence（利用者名の配信）、コメント（投稿者名）、履歴、バックアップまで含める。画面の名前差し替えだけでは不十分である
- 変換後の識別子は、スペース単位の表示用データ（display_labels.label、例： 学籍番号・出席番号）または代替表示にする。表示用データ未設定の参加者は実名ではなく代替表示（例： 「参加者」＋連番）にする
- 教師向けの氏名対応は、管理者専用の別経路（API）で提供する。このとき「管理者なら閲覧可」では不十分であり、**対象校・対象スペースについて氏名対応を閲覧できる資格**を明示する（学校管理者資格と教師資格は別であるため）
- ZIP 書き出し： 現行形式では authorName が必須項目のため、項目の削除ではなく**値を安全な表示名（表示用データ）へ置換**して形式の互換性を保つ。氏名・共有先メールアドレスも同様に除外または置換する。学校作品の復元では共有設定を復元せず、復元後に再設定する仕様とする（一般作品は従来どおり）。形式自体を更新する場合は、旧形式も読める互換を保つ
- 古い ZIP を学校作品へ復元する場合も、ZIP 内のシステム由来の投稿者名をそのまま再配信しない変換を行う
- JSON 書き出し： 個人情報を含めない
- 作品本文・写真に利用者自身が入れた情報は自動除去しない
- **出口の列挙と未検証面の扱い**： 個人情報を含み得る出口は、WebSocket 配信（更新・presence・同期初期データ）、取得 API（作品・画像・付箋・履歴）、書き出し（JSON／ZIP／PDF）、バックアップの取得と検証、とする。学校作品については、変換を通せることが確認できた出口だけを公開し、未検証の出口は公開ゲート（第9節）を満たすまで参加者へ開かない
- **識別・変換できない旧データの扱い**： 旧形式のデータ（Yjs の保存データ、コメント、履歴、画像以外の共有データ等）で、システム由来の氏名・メールを含むかどうか識別できないものは、含むものとして扱い、参加者向けの配信からは除外する。教師・管理者向けの経路では、資格のある場合に限り扱える。分離できない一体のデータ（Yjs の文書・履歴等）で分離が実現できない場合は、その作品全体を参加者へ公開しない（安全側）。各出口（JSON／ZIP／履歴／取得 API／presence）について、氏名・メールが混入しないことの漏えい試験を公開ゲートの条件とする
- ZIP 復元についての用語の整理： 第4.6節の「履歴の移管は起きない」とは、既存作品のサーバー側の招待・参加者・履歴レコードを復元先へ引き継がないという意味である。バックアップ ZIP のファイル内に含まれる履歴データは、ファイルの内容として取り込まれるデータであり、参加者への配信は変換を通した場合に限る

## 7. スペースの状態機械

| 状態 | 遷移元 → 先 | 閲覧 | 編集 | 書き出し | 備考 |
|---|---|---|---|---|---|
| 運用中 | （作成） | 参加資格による | 許可範囲による | 可 | 通常状態 |
| 終了 | 運用中 → 終了（管理者） | 管理者の設定による | 管理者の設定による | 管理者の設定による | 設定は現在の管理者が変更できる。再開も管理者が行える |
| 削除猶予中 | 終了／運用中 → 削除（管理者） | 削除時点で権限を持っていた者、**かつ現在も資格を失っていない者** | 不可 | 削除時点で権限を持っていた者、**かつ現在も資格を失っていない者**（通知は新たな権限を与えない） | 削除時点で該当アカウントへ通知し、保存を促す。起算は削除操作時点。削除時点の資格は deletion_snapshots に保存し、現在の資格と両方で判定する |
| 削除済み | 猶予期間経過 → 完全削除 | 不可 | 不可 | 不可 | データを完全削除する |

- 「最大1か月」の具体化（暦月か30日か）は未確定であり、実装時に確定する。本書の30日案は提案である
- 削除の取り消し（猶予中の復旧）を認めるかは、認める場合は管理者のみ・猶予期間内に限る。実装時に確定する
- スペース削除の対象確定： 削除の開始時に、Directory 側で対象作品の一覧と deletion_snapshots を、削除操作IDのもとで一貫した時点で確定する。確定後はスペースが削除猶予中となり作品の追加はできないため、対象集合はその後変わらない。各 SlideRoom への通知が失敗した場合は、削除操作の記録から冪等に再開する。対象が0件の場合も削除はそのまま進める
- 個別作品の削除との競合： 作品単位の削除とスペース削除は、作品レコード側で直列化する。先に確定した方を有効とし、後から来た方は「処理済み」として対象から外す（deletion_snapshots は削除操作IDごとに分かれるため、記録が混ざることはない）
- 既に個別削除の手続き中（削除猶予中）の作品がスペース削除の対象になった場合： その作品については個別削除の操作を正とし、猶予の起算・通知・完全削除の期限は個別削除のものを維持する（二重に起算・通知しない）。スペース削除の deletion_snapshots には、その作品について個別操作への参照を記録し、資格行を重複して作らない。逆に、スペース削除が先に確定した作品については、個別の削除申請を受け付けない（処理済みとして扱う）。作品ごとに有効な削除操作は常に1つだけとする
- 先行する個別削除が先に完全削除へ進んだ場合： スペース削除側の参照は「対象は完全削除済み」として解決し、その作品については再通知・再起算をしない。deletion_snapshots の参照行には最終状態を記録し、スペース削除の再試行でも冪等に扱う。対象作品が0件のスペース削除、および個別削除とスペース削除の並行操作について、状態遷移の試験を段階④の受入条件に含める

## 8. 段階②の暫定作品（学校管理対象の保持）

- 学校所属アカウント（organization_members が有効）がクラウド作品を作成した場合、スペース未所属でも作成時点で decks.organization_id をセットし、学校管理対象として保持する。取り込み前でも、所属解除や旧所有者権限による回避はできない
- ローカルのみで作られた作品はサーバー管理外であり対象外（クラウドへ保存・取り込みする時点で学校管理対象になる）

## 9. 段階別の実装タスクと受け入れ条件（再構成）

段階②が段階③のスペースモデルに依存しないよう、各段階が独立して成立する範囲に切り直した。

**公開ゲート（各段階共通）**： 学校利用を本番で公開する条件は、次のすべてを満たすこととし、段階②の本番有効化（段階①と同時）をはじめ、段階③・④の公開判定はこのゲートで一括して行う。(1) 学校作品についての情報分離（第6節の該当面）が完了している (2) 既存の共有経路・復元経路でも制限が効く（第4.3・4.6節） (3) 作品の管理主体が区分ごとに定義どおり動く（スペース管理者、暫定作品の管理担当（第2.6節）） (4) 失効が受信・配信に反映される（第4.4節。実測結果を含む） (5) 初代登録と復旧の運用手順（第3節）が実施可能な形で用意されている (6) 段階ごとの受入条件をすべて満たす。段階②を段階③の完了前に公開する場合は、(4) の実測と、第6節のうち学校作品に関わる情報分離を、段階②の受入条件へ前倒しする

### 段階① 認証・役割の土台

- organizations / preregistrations / organization_members / school_admin_applications / users.is_super_admin の追加とスキーマ移行（列名指定 INSERT への変更を含む）
- 初代スーパー管理者の登録（第3節。方式は未決であり、確定条件を満たす形で段階①の着手時に決める）
- 学校管理者による事前登録と、ログイン時の結びつけ。資格照会（サーバーが操作資格を返す仕組み）
- **本番有効化の条件（決定済み）**： 段階①は検証環境でのみ有効にし、学校利用の本番有効化は段階②と同時に行う。所属だけが登録されて制限が効いていない中間状態を本番に置かないため
- 受け入れ：
  - 学校管理者だけでは作品作成・本文編集の権限が増えない
  - **教師資格のない学校管理者を登録でき、その場合も作品権限が増えない**
  - **学校管理者が、未許可の学校管理者任命を行えない**
  - 一般用・学校用のどちらでログインしても、同じ登録資格へ結びつく
  - 事前登録の取消・重複・別校への操作を正しく拒否する
  - **事前登録の二重消費、取消後の結びつけ、所属解除後の自動復活が起きない**
  - **既存セッションにも資格変更が反映される**
  - **移行の再実行で、データや権限が変わらない**
  - **内部管理フラグが既存の参加者向け応答へ混入しない**
  - 初代登録の競合・再実行を拒否する
  - 移行後も、既存のログイン・一般作品の作成・共有・復元が維持される
  - Node／Cloudflare で同じ資格判定になる
  - **初代登録について、並行実行・失敗後の再試行・対象環境の取り違え・誤登録からの復旧（第3節の復旧手順）が、手順どおり安全に行える**
  - **事前登録について、同時消費・取消との競合・複数校への登録が、第5節の状態遷移どおりになる**

### 段階② 学校管理区分と作成制限

- decks への organization_id 追加と、学校作品の作成・コピー・復元制限（UI と両サーバー）
- 暫定作品の管理主体（決定済み）： **管理担当を指定する方式**とし、選出・変更・失効時の扱いは第2.6節に定義する
- **学校作品についての owner 例外の除去**（段階③まで待たない）
- 学校作品を利用可能にするなら、必要な情報分離（第6節のうち学校作品の作成・共有に関わる部分）も段階②までに前倒しする。あるいは、段階②は検証環境だけで有効にし、段階③完了後に学校作品の利用を公開する
- 受け入れ： 一般用ログインを選んでも制限される／復元経由で回避できない／権限を解除された旧所有者が管理できない

### 段階③ スペースと参加の接続、情報分離

- spaces / space_members / 各種申請テーブル / display_labels の追加
- スペース参加・作品参加の接続。取得・配信・更新の認可（第4.3・4.4節）
- 表示情報の分離（第6節）の完成
- 受け入れ（境界ケース）： スペース未承認×事前共有あり／スペース承認済み×作品の参加資格なし／解除後の古い参加情報の残存／接続中 WebSocket での権限解除
- **失効通知が到達した場合は即時に配信が止まること、通知が届かない場合でもリースの期限切れにより最大でリース期間以内に必ず止まること（通知喪失・休眠・再起動、更新応答の遅延・逆順・重複、時計のずれ、認可照会の失敗を含む）を、実測で確認する（結果を記録する）**
- **第4.4節の障害注入試験： 失効確定直前の認可、長時間遅延した応答、通知の喪失、時計の不明・逆行、休眠、同時更新、削除猶予中の配信について、上限どおりに止まることを決定的な試験で確認する（実測の成功だけをもって上限の証明とはしない）**
- **所属世代の移行と競合（既存の共有行への世代付与、複数校、古い非同期処理と再有効化の競合）を両サーバーで確認する。取り込みは、停止確認後から公開までの、接続・休眠復帰・再起動を通じたフェンスを試験し、検証できないデータは非公開のままであることを確認する**
- **旧 ZIP の学校作品への復元で、氏名・共有先メールが全配信面・書き出しに混入しない（第4.6節）。あわせて、各出口（JSON／ZIP／履歴／取得 API／presence）の漏えい試験を行う**

### 段階④ 運用と移行

- 終了・移管・削除猶予・通知・完全削除（第7節）
- 教師試作品の取り込み。一般利用の回帰確認
- 受け入れ： 削除後は、条件を満たす人は閲覧・書き出しが可能で編集は不可（第7節と一致させること）／通知が該当アカウントに届く／猶予期間の経過後に完全削除される
- **移行の再実行で結果（データ・権限）が変わらない／一般作品の利用に回帰がない**
