# 段階① フェーズ2（製品実装）実施計画 v0.2

作成: Muse（2026-11-05、Codex レビュー反映版）。根拠: 実装設計書 v2.10 第9節（段階①のタスクと受け入れ条件）、検証計画 v0.4 のフェーズ2、フェーズ1最終報告書（確定版）。v0.1 からの変更は Codex レビューの5点への対応です。

## 1. 確定事項（前提）

- **初代登録方式は A＋C の組み合わせで確定**（開発者、2026-11-05）。一時経路は案A（使い捨てシークレット＋一時経路、登録後に無効化）、運営・復旧の認可は案C の独立認可として設計・実装する。
- 段階①は**検証環境でのみ有効**とし、学校利用の本番有効化は段階②と同時に行う（決定済み）。
- フェーズ1最終報告書の条件を引き継ぐ: 独立認可の設計と実証、旧セッション拒否の実証は、本計画の受入条件に含める（第5節）。

## 2. 独立した運営者認可の設計（着手前に確定する）

共有シークレットと同一の管理権限を持つ仕組みは、独立認可とは見なしません。次を設計の確定事項として、初回登録と復旧の双方に適用できることを、製品実装に先立って検証環境で確認します。

- **認可主体**: 運営者（スーパー管理者）自身の Google アカウント。対象アカウント（登録・復旧される側）の証明とは別の検査として扱う。
- **認証経路**: 常設の管理ルートで、運営者の Google ID トークンを検証し、その主体がサーバー側の運営者登録簿に含まれる場合にのみ通す。登録簿への初回登録は、案A の一時経路（使い捨てシークレット）を使って行い、登録後は一時経路を無効化する。
- **権限境界**: 運営者認可でできるのは、初回登録・復旧・運営者登録簿の管理（追加・失効・ローテーション）に限る。作品の本文編集や学校内の管理操作は、この認可では行えない。
- **失効と回復**: 運営者の失効は登録簿からの除去で行う。運営者自身がアクセスを失った場合の回復は、案A の一時経路を再度使う手順（使い捨てシークレットの再発行と登録簿の原子的入れ替え）とする。
- **障害時の扱い**: 認可の照会が失敗した場合は拒否する（fail-closed）。推測で通さない。
- **先行確認**: この設計が初回登録と復旧の両方に適用できることを、製品実装の前に検証環境で確認し、結果を記録する。

## 3. 実施範囲と順序

検証計画フェーズ2の順序に従います。

1. **移行（C4・C5）**: organizations / preregistrations / organization_members / school_admin_applications / users.is_super_admin の追加とスキーマ移行（列名指定 INSERT への変更を含む）。具体化は第4節。
2. **認可基盤（C1〜C3）**: 資格照会（サーバーが操作資格を返す仕組み）、既存セッションへの資格変更の反映、Node／Cloudflare で同一の資格判定。
3. **登録制フロー（B群）**: 学校管理者による事前登録とログイン時の結びつけ、学校管理者の申請・任命フロー。事前登録の状態遷移（取消・重複・二重消費・複数校）は実装設計書 第5節どおり。
4. **初代登録の受け入れ（A群）**: A＋C 組み合わせによる初代スーパー管理者の登録と復旧手順の製品実装。独立認可は第2節の設計どおりとし、認可・無効化・ローテーション・回復の各経路を実装する。
5. **回帰（D群）**: 移行後も既存のログイン・一般作品の作成・共有・復元が従来どおり動くこと（D1）、学校所属のないアカウントへの非干渉（D2）。

## 4. 移行の進め方（具体化）

- **既存データの保全**: 移行は追加のみ（列・テーブルの追加と、データを書き換えない形の変更）とし、破壊的な変更は含めない。
- **再実行**: 移行は冪等にし、移行状態を記録する。失敗の途中から再実行しても、済んだ部分を二重に適用せず、データと権限が変わらない。
- **両サーバー**: Node と Cloudflare の両方に同じ移行を適用し、適用順序と、各サーバーでの確認結果を記録する。
- **失敗時の復旧**: 各移行ステップに復旧方法（巻き戻し、または移行前の状態への復元）を対応づけてから実施する。復旧できないステップは実施しない。
- **直後の回帰確認**: 移行の直後に、既存ログイン・一般作品の作成・共有・復元が従来どおり動くことを検証環境で確認する（最終の回帰（手順5）とは別に、移行直後にも行う）。

## 5. 受入条件

実装設計書 第9節の段階①の受け入れ一覧（学校管理者だけでは作品権限が増えない／教師資格のない学校管理者でも同様／未許可の任命ができない／一般用・学校用のどちらのログインでも同じ登録資格に結びつく／事前登録の取消・重複・別校操作の拒否／二重消費・取消後の結びつけ・所属解除後の自動復活が起きない／既存セッションへの資格変更の反映／移行の再実行で不変／内部管理フラグの混入なし／初代登録の競合・再実行の拒否／既存機能の維持／両サーバーで同じ資格判定／初代登録の並行・失敗後の再試行・環境の取り違え・誤登録からの復旧が手順どおり安全／事前登録の同時消費・取消との競合・複数校が状態遷移どおり）に加えて:

- **独立認可の実証**: 運営・復旧の認可が第2節の独立認可として働くこと（認可・無効化・ローテーション・回復の各経路を含む）。
- **旧セッション拒否の実証**: 復旧後に、旧アカウントの保持済みセッションから管理操作が拒否されること（フェーズ1で未実施だった項目）。
- **フェーズ1で実証できなかった項目の個別条件**: 次の4件は、フェーズ1では実環境で実証できていないものとして、それぞれ個別の実環境受入条件として残す。(i) A2／A7 の原子性（途中失敗時のロールバック）、(ii) 同一 nonce の再送の拒否、(iii) 並行初回登録での一回性、(iv) 保持済み旧セッションの拒否（上記と重なるが、復旧以外の資格変更でも確認する）。
- 検証は検証環境で行い、本番には段階①の変更を有効化しない。

## 7. 検証環境の識別・本番遮断・終了手順

- **環境の識別**: 書き込みの前に、対象（アカウント・Worker 名・名前空間・バインディング・有効なバージョン）と環境 ID を両者が独立に照合する（フェーズ1と同じ手順）。
- **本番遮断**: 段階①のコードは環境フラグで検証環境でのみ有効にし、本番では有効化しない。本番 Worker への書き込みは本計画の範囲外。
- **終了手順**: 検証で使うシークレットは、生成・保管・設定・除去をフェーズ1と同じ分担（値は PC 側で生成・暗号化保管し、関係者のみに共有しない）で行い、工程の終了時に有効版・最新版から除去し、一覧が空であることを確認する。過去バージョンに残り得る点は、フェーズ1報告書の観測範囲の記述を引き継ぐ。
- **トークン**: Muse が検証用 Worker の操作に使うトークンが必要になった場合は、**開発者が発行**します（権限は対象を絞った最小限、工程終了時に開発者が失効）。
