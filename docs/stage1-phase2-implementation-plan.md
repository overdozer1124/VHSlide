# 段階① フェーズ2（製品実装）実施計画 v0.3

作成: Muse（2026-11-05、Codex レビュー反映版）。根拠: 実装設計書 v2.10 第9節（段階①のタスクと受け入れ条件）、検証計画 v0.4 のフェーズ2、フェーズ1最終報告書（確定版）。v0.3 の主変更は第2節（独立認可）の再設計です： v0.2 の方式では登録簿の初期登録と全面入替が使い捨てシークレットだけで行え、独立認可の迂回になるという指摘を受け、承認主体と実行手段をプラットフォーム経路に分離しました。

## 1. 確定事項（前提）

- **初代登録方式は A＋C の組み合わせで確定**（開発者、2026-11-05）。一時経路は案A（使い捨てシークレット＋一時経路、登録後に無効化）、運営・復旧の認可は案C の独立認可として設計・実装する。第2節のプラットフォーム経路は、この組み合わせの実現方法の具体化であり、方式の変更ではない（レビューで確認済み： 実現方式の再検討に追加承認は不要）。
- 段階①は**検証環境でのみ有効**とし、学校利用の本番有効化は段階②と同時に行う（決定済み）。
- フェーズ1最終報告書の条件を引き継ぐ: 独立認可の設計と実証、旧セッション拒否の実証は、本計画の受入条件に含める（第5節）。

## 2. 独立した運営者認可の設計（着手前に確定する）

### 2.1 チャネルの分離

運営に関わる操作を、承認主体と実行手段の異なる2つのチャネルに分けます。共有シークレットだけで完結する経路は、どちらのチャネルにも置きません。

- **プラットフォーム経路（登録簿の初期投入と全面復旧のみ）**: 承認主体は **Cloudflare アカウントの保有者（開発者）** で、認証はアプリの外（Cloudflare 自身のログイン）で行われます。実行手段はデプロイです。登録簿の初期作成、全運営者喪失時の全面入替、全運営者の緊急失効は、この経路でしか行えません。具体形はフェーズ1で実証した一時ビルドの方式です： 操作専用のビルド（専用経路はそのビルドにだけ存在する）を配置し、操作の直後に通常ビルドへ戻し、専用経路が消えていることを確認します（404 の確認までを手順に含める）。
- **アプリ内管理ルート（通常の運営操作）**: 常設の管理ルートで、運営者自身の Google アカウントの ID トークンを検証し、その主体がサーバー側の**運営者登録簿**に含まれる場合にのみ通します。できるのは、初代登録の対象結びつけ、スーパー管理者の復旧、登録簿の変更（追加・失効・ローテーション、既存の運営者の認可が必要）に限ります。

### 2.2 運営者とスーパー管理者の区別

運営者は「運営チャネルの主体」、スーパー管理者は「製品内の役割」であり、権限の出所が異なります。初期設定では開発者が両方を担いますが、同一人物であることに依存した設計にはしません。運営者認可は製品内の権限（作品の本文編集や学校内の管理操作）を一切与えず、逆にスーパー管理者の製品セッションは運営操作の認可にはなりません。登録簿は users.is_super_admin とは別に保持します。

### 2.3 初期登録と全面復旧の結びつけ

プラットフォーム経路の操作では、次を完了記録として不変に保存します： 対象環境の識別子（env_id）、対象の Google 主体のハッシュ、用途（初期投入／全面復旧）、実施時刻。使い捨ての値はアカウント保有者がデプロイ時に生成し、デプロイされたビルドのバインディングの中にだけ存在します（チャット・Issue・文書には出しません）。専用経路には有効期限（配置時刻からの上限つき）を持たせ、期限切れは拒否します。初期投入の再実行は、完了記録が存在すれば拒否します。

### 2.4 再発行・紛失・侵害への対処

- 紛失: 値を知らなくても、通常ビルドへの再配置で専用経路ごと消えるため、やり直しができます。
- 侵害の疑い: 直ちに通常ビルドへ戻して経路を消し、値を再生成してから再実施します。完了記録の有無で、侵害が成立したかどうかを照合できます。
- 再発行: 同じ値の再利用はせず、実施のたびに新しい値を生成します。

### 2.5 失効中セッションと同時更新の拒否

- 登録簿の変更は Directory DO の単一トランザクションで直列化し、登録簿の世代番号を進めます。運営者セッションは発行時の世代を持ち、管理操作のたびに「登録簿に現に含まれること」と「世代が現行であること」を再確認します。失効された運営者の保持済みセッションは、次の操作で拒否されます。
- 同時更新は、世代の照合をトランザクション内で行うため、古い世代に基づく更新は拒否されます。
- 認可の照会が失敗した場合は拒否します（fail-closed）。

### 2.6 先行確認

この設計が初回登録と復旧の両方に適用できることを、製品実装の前に検証環境で確認し、結果を記録します。プラットフォーム経路の一時ビルド方式そのものは、フェーズ1の手順6（中断専用版）で実施済みの型です。

## 3. 実施範囲と順序

検証計画フェーズ2の順序に従います。

1. **移行（C4・C5）**: organizations / preregistrations / organization_members / school_admin_applications / users.is_super_admin の追加とスキーマ移行（列名指定 INSERT への変更を含む。対象箇所は Node の server/app.ts と Cloudflare の cloudflare/directory.ts の users INSERT）。具体化は第4節。
2. **認可基盤（C1〜C3）**: 資格照会（サーバーが操作資格を返す仕組み）、既存セッションへの資格変更の反映、Node／Cloudflare で同一の資格判定。
3. **登録制フロー（B群）**: 学校管理者による事前登録とログイン時の結びつけ、学校管理者の申請・任命フロー。事前登録の状態遷移（取消・重複・二重消費・複数校）は実装設計書 第5節どおり。
4. **初代登録の受け入れ（A群）**: A＋C 組み合わせによる初代スーパー管理者の登録と復旧手順の製品実装。独立認可は第2節の設計どおりとし、認可・無効化・ローテーション・回復の各経路を実装する。
5. **回帰（D群）**: 移行後も既存のログイン・一般作品の作成・共有・復元が従来どおり動くこと（D1）、学校所属のないアカウントへの非干渉（D2）。

## 4. 移行の進め方（具体化）

- **既存データの保全**: 移行は追加のみ（列・テーブルの追加と、データを書き換えない形の変更）とし、破壊的な変更は含めない。
- **再実行**: 移行は冪等にし、移行状態を記録する。失敗の途中から再実行しても、済んだ部分を二重に適用せず、データと権限が変わらない。
- **両サーバー**: Node と Cloudflare の両方に同じ移行を適用し、適用順序と、各サーバーでの確認結果を記録する。
- **失敗時の復旧**: 各移行ステップに復旧方法（巻き戻し、または移行前の状態への復元）を対応づけてから実施する。復旧できないステップは実施しない。
- **直後の回帰確認**: 移行の直後に、既存ログイン・一般作品の作成・共有・復元が従来どおり動くことを検証環境で確認する（最終の回帰（手順5）とは別に、移行直後にも行う）。

## 5. 受入条件

実装設計書 第9節の段階①の受け入れ一覧（学校管理者だけでは作品権限が増えない／教師資格のない学校管理者でも同様／未許可の任命ができない／一般用・学校用のどちらのログインでも同じ登録資格に結びつく／事前登録の取消・重複・別校操作の拒否／二重消費・取消後の結びつけ・所属解除後の自動復活が起きない／既存セッションへの資格変更の反映／移行の再実行で不変／内部管理フラグの混入なし／初代登録の競合・再実行の拒否／既存機能の維持／両サーバーで同じ資格判定／初代登録の並行・失敗後の再試行・環境の取り違え・誤登録からの復旧が手順どおり安全／事前登録の同時消費・取消との競合・複数校が状態遷移どおり）に加えて:

- **独立認可の実証**: 運営・復旧の認可が第2節の独立認可として働くこと。特に、使い捨ての値だけでは登録簿の初期投入・全面入替ができないこと（プラットフォーム経路を経ない操作が拒否されること）、失効した運営者の保持済みセッションが次の操作で拒否されること、古い世代に基づく同時更新が拒否されることを含む。
- **旧セッション拒否の実証**: 復旧後に、旧アカウントの保持済みセッションから管理操作が拒否されること（フェーズ1で未実施だった項目）。
- **フェーズ1で実証できなかった項目の個別条件**: 次の4件は、フェーズ1では実環境で実証できていないものとして、それぞれ個別の実環境受入条件として残す。(i) A2／A7 の原子性（途中失敗時のロールバック）、(ii) 同一 nonce の再送の拒否、(iii) 並行初回登録での一回性、(iv) 保持済み旧セッションの拒否（上記と重なるが、復旧以外の資格変更でも確認する）。
- 検証は検証環境で行い、本番には段階①の変更を有効化しない。

## 7. 検証環境の識別・本番遮断・終了手順

- **環境の識別**: 書き込みの前に、対象（アカウント・Worker 名・名前空間・バインディング・有効なバージョン）と環境 ID を両者が独立に照合する（フェーズ1と同じ手順）。
- **本番遮断**: 段階①のコードは環境フラグで検証環境でのみ有効にし、本番では有効化しない。本番 Worker への書き込みは本計画の範囲外。
- **終了手順**: 検証で使うシークレットは、生成・保管・設定・除去をフェーズ1と同じ分担（値は PC 側で生成・暗号化保管し、関係者のみに共有しない）で行い、工程の終了時に有効版・最新版から除去し、一覧が空であることを確認する。過去バージョンに残り得る点は、フェーズ1報告書の観測範囲の記述を引き継ぐ。
- **トークン**: Muse が検証用 Worker の操作に使うトークンが必要になった場合は、**開発者が発行**します（権限は対象を絞った最小限、工程終了時に開発者が失効）。
