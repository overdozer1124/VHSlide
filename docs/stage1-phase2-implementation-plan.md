## 2. 独立した運営者認可の設計（着手前に確定する）

### 2.1 チャネルの分離

運営に関わる操作を、承認主体と実行手段の異なる2つのチャネルに分けます。共有シークレットだけで完結する経路は、どちらのチャネルにも置きません。

- **プラットフォーム経路（登録簿の初期投入と全面復旧のみ）**: 承認主体は **Cloudflare アカウントの保有者（開発者）** で、認証はアプリの外（Cloudflare 自身のログイン）で行われます。実行手段はデプロイです。登録簿の初期作成、全運営者喪失時の全面入替、全運営者の緊急失効は、この経路でしか行えません。具体形は一時ビルドの方式です： 操作専用のビルド（専用経路はそのビルドにだけ存在する）を配置し、操作の直後に通常ビルドへ戻します。フェーズ1の手順6（中断専用版）はこの型の参考であり、本方式の独立認可の実証ではありません。実証は 2.7 の先行検証で行います。
- **アプリ内管理ルート（通常の運営操作）**: 常設の管理ルートで、運営者自身の Google アカウントの ID トークンを検証し、その主体がサーバー側の**運営者登録簿**に含まれる場合にのみ通します。できるのは、初代登録の対象結びつけ、スーパー管理者の復旧、登録簿の変更（追加・失効・ローテーション、既存の運営者の認可が必要）に限ります。

### 2.2 運営者とスーパー管理者の区別

運営者は「運営チャネルの主体」、スーパー管理者は「製品内の役割」であり、権限の出所が異なります。初期設定では開発者が両方を担いますが、同一人物であることに依存した設計にはしません。運営者認可は製品内の権限（作品の本文編集や学校内の管理操作）を一切与えず、逆にスーパー管理者の製品セッションは運営操作の認可にはなりません。登録簿は users.is_super_admin とは別に保持します。

### 2.3 事前に固定した承認内容への照合（プラットフォーム経路）

一時ビルドを配置する前に、アカウント保有者は承認内容を固定し、ビルドのバインディングとして埋め込みます： **対象環境の識別子、用途（初期投入／全面復旧）、対象主体のハッシュ、有効期限、使い捨ての値**。専用経路は、提示された ID トークンの主体ハッシュ・環境・用途が固定値とすべて一致する場合にだけ動作し、不一致は拒否します。値が漏れても、固定された対象以外の主体は登録できません。

- 消費は**操作IDごと**に原子的で一度だけです： アカウント保有者は承認のたびに操作IDを発行し、固定内容・有効期限・消費を操作IDに結びつけます。登録簿への投入と完了記録の作成を単一トランザクションで行い、消費済みの操作IDは二度目を拒否します。用途だけで一意にはしません（全面復旧を繰り返せるようにするため）。
- 初期投入は、用途ではなく「初期化済み」という状態で再実行を拒否します。全面復旧は、新しい操作IDによる新しい承認がある場合に限ります。過去の操作IDは、旧い一時ビルドが再配置されても再利用できません（消費済み操作IDはサーバー側の状態で照合します）。
- 完了記録には、操作ID・対象環境・対象主体のハッシュ・用途・実施時刻を不変に保存します。
- 拒否の確認項目： 主体の不一致、環境の不一致、用途の不一致、期限切れ、二重実施、並行実施（正確に1件だけ成功）。これらは 2.7 の先行検証で確認します。

### 2.4 侵害時の封じ込め・確認・復旧

完了記録は実施の有無を示すだけで、承認されていない登録を無害化しません。また、記録がないことは侵害がなかった証明にはなりません。そのため、操作の終了条件は記録ではなく**登録簿の読み戻し**とします。

- 一時ビルドの操作後は、プラットフォーム経路（Data Studio 等）で登録簿の内容を読み戻し、承認内容と一致することを確認してから終了します。
- 想定外の登録簿の状態が見つかった場合の封じ込め： 直ちに通常ビルドへ戻して経路を消し、登録簿の全面入替（新たなプラットフォーム経路の操作）で正しい内容に置き換え、関係するセッションを失効させます。経緯は記録します。
- 有効期限が切れた一時ビルドは、専用経路への状態変更を行う要求（apply）を拒否します。なお、nonce の発行自体は期限切れ後も行われ得ますが、発行された nonce は期限切れの承認では消費できず、状態は変更されません。

### 2.5 トークンと世代の扱い（アプリ内管理ルート）

- 運営者セッションは発行しません。管理操作のたびに新しい Google ID トークンの提示を求め、その都度検証します（署名・有効期限・発行先）。トークンの再利用は、その有効期間内に限られますが、操作のたびに登録簿の在籍を照合するため、失効した運営者のトークンは次の操作で拒否されます。
- 登録簿の在籍・世代の照合と、変更の適用は、**同一トランザクション**で行います。登録簿の変更は Directory DO の単一トランザクションで直列化し、世代番号を進めます。古い世代に基づく同時更新は拒否されます。
- 認可の照会が失敗した場合は拒否します（fail-closed）。

### 2.6 運用失敗時の手順（プラットフォーム経路）

- **誤った一時ビルドを配置した場合**: 操作を実行せず、通常ビルドへ戻し、値を再生成してからやり直します。
- **通常ビルドへの復帰が失敗した場合**: 別経路（API と Wrangler／ダッシュボード）で1回だけ再試行します。それでも戻せない場合は、状態を記録して直ちに開発者へ上げます。戻せない間も、専用経路は有効期限の経過後に状態変更を行う要求（apply）をすべて拒否します（nonce は発行され得ますが、期限切れの承認では消費できません）。ただし、これは経路の消滅の代わりにはならないため、期限切れに依存して復帰を先送りしません。
- **応答が失われた場合**: 同じ操作を再送しません。先に状態（完了記録と登録簿）を読み戻してから、次の判断をします。
- **旧版が再配置された場合**: 旧い一時ビルドが再配置されても、その固定値（対象・用途・期限）と完了記録の照合が効くため、別の主体の登録や期限切れ後の実施はできません。操作の終了時には、配置が通常ビルドであることを読み戻して確認します。なお、経路の消滅の確認（404 等）は、特定の要求条件のもとでの観察として記録します（条件を添えて記録する）。

### 2.7 先行検証（製品実装の前に行う）

第2節の設計が初回登録と復旧の両方に適用できることを、検証環境で先行して確認します。この先行検証は手順4（初代登録の受け入れ）の着手のゲートであり、先行検証の結果が受入条件を満たすまで手順4には着手しません。手順1（移行）の準備は独立に並行して進められます。対象は検証専用の試作実装であり、結果は「実測／ローカル模擬／未実施」を分けて記録します。次の各項目は、検証環境での実測を必須とし、未実施は合格としません。受入条件は次をすべて満たすことです。

1. 固定値との照合： 主体・環境・用途の各不一致が拒否される。
2. 原子的な一回消費： 二重実施が拒否され、並行実施で正確に1件だけ成功する。
3. 値の漏洩を想定した試験： 値を知っていても、固定された対象以外の主体は登録できない。
4. 期限切れの拒否。
5. 終了手順： 通常ビルドへの復帰、特定の要求条件での経路消滅の観察、登録簿の読み戻しが承認内容と一致する。
8. トークン検証とリプレイ対策： 検証済み Google トークンの発行者・audience・有効期限・nonce と主体の照合、CSRF／リプレイ対策、環境識別の信頼できる根拠を確認する。
9. 途中失敗時のロールバック、固定対象と異なる主体の拒否、並行消費（正確に1件だけ成功）を、検証環境の実環境で確認する。
6. 失効と世代： 失効した運営者の次回操作の拒否、古い世代に基づく同時更新の拒否、失効後の同一トークンの拒否。
7. 失敗手順の実施： 応答喪失時に再送せず読み戻しで判断できること、復帰失敗時の別経路での再試行手順が回ること。

## 3. 実施範囲と順序

検証計画フェーズ2の順序に従います。手順4の着手は、2.7 の先行検証が受入条件を満たしてからとします（手順1の移行準備は独立に並行して進められます）。

1. **移行（C4・C5）**: organizations / preregistrations / organization_members / school_admin_applications / users.is_super_admin の追加とスキーマ移行（列名指定 INSERT への変更を含む。対象箇所は Node の server/app.ts と Cloudflare の cloudflare/directory.ts の users INSERT）。具体化は第4節。
2. **認可基盤（C1〜C3）**: 資格照会（サーバーが操作資格を返す仕組み）、既存セッションへの資格変更の反映、Node／Cloudflare で同一の資格判定。
3. **登録制フロー（B群）**: 学校管理者による事前登録とログイン時の結びつけ、学校管理者の申請・任命フロー。事前登録の状態遷移（取消・重複・二重消費・複数校）は実装設計書 第5節どおり。
4. **初代登録の受け入れ（A群）**: A＋C 組み合わせによる初代スーパー管理者の登録と復旧手順の製品実装。独立認可は第2節の設計どおりとし、認可・無効化・ローテーション・回復の各経路を実装する。
5. **回帰（D群）**: 移行後も既存のログイン・一般作品の作成・共有・復元が従来どおり動くこと（D1）、学校所属のないアカウントへの非干渉（D2）。

## 4. 移行の進め方（具体化）

- **既存データの保全**: 移行は追加のみ（列・テーブルの追加と、データを書き換えない形の変更）とし、破壊的な変更は含めない。
- **再実行**: 移行は冪等にし、移行状態を記録する。失敗の途中から再実行しても、済んだ部分を二重に適用せず、データと権限が変わらない。
- **両サーバー**: Node と Cloudflare の両方に同じ移行を適用し、適用順序と、各サーバーでの確認結果を記録する。
- **失敗時の復旧**: 各移行ステップに復旧方法（巻き戻し、または移行前の状態への復元）を対応づけてから実施する。復旧できないステップは実施しない。
- **直後の回帰確認**: 移行の直後に、既存ログイン・一般作品の作成・共有・復元が従来どおり動くことを検証環境で確認する（最終の回帰（手順5）とは別に、移行直後にも行う）。

## 5. 受入条件

実装設計書 第9節の段階①の受け入れ一覧（学校管理者だけでは作品権限が増えない／教師資格のない学校管理者でも同様／未許可の任命ができない／一般用・学校用のどちらのログインでも同じ登録資格に結びつく／事前登録の取消・重複・別校操作の拒否／二重消費・取消後の結びつけ・所属解除後の自動復活が起きない／既存セッションへの資格変更の反映／移行の再実行で不変／内部管理フラグの混入なし／初代登録の競合・再実行の拒否／既存機能の維持／両サーバーで同じ資格判定／初代登録の並行・失敗後の再試行・環境の取り違え・誤登録からの復旧が手順どおり安全／事前登録の同時消費・取消との競合・複数校が状態遷移どおり）に加えて:

- **独立認可の実証**: 2.7 の先行検証が受入条件を満たし、製品実装でも運営・復旧の認可が第2節の独立認可として働くこと。
- **旧セッション拒否の実証**: 復旧後に、旧アカウントの保持済みセッションから管理操作が拒否されること（フェーズ1で未実施だった項目）。
- **フェーズ1で実証できなかった項目の個別条件**: 次の4件は、フェーズ1では実環境で実証できていないものとして、それぞれ個別の実環境受入条件として残す。(i) A2／A7 の原子性（途中失敗時のロールバック）、(ii) 同一 nonce の再送の拒否、(iii) 並行初回登録での一回性、(iv) 保持済み旧セッションの拒否（上記と重なるが、復旧以外の資格変更でも確認する）。
- 検証は検証環境で行い、本番には段階①の変更を有効化しない。

## 7. 検証環境の識別・本番遮断・終了手順

- **環境の識別**: 書き込みの前に、対象（アカウント・Worker 名・名前空間・バインディング・有効なバージョン）と環境 ID を両者が独立に照合する（フェーズ1と同じ手順）。
- **本番遮断**: 段階①のコードは環境フラグで検証環境でのみ有効にし、本番では有効化しない。本番 Worker への書き込みは本計画の範囲外。
- **終了手順**: 検証で使うシークレットは、生成・保管・設定・除去をフェーズ1と同じ分担（値は PC 側で生成・暗号化保管し、関係者のみに共有しない）で行い、工程の終了時に有効版・最新版から除去し、一覧が空であることを確認する。過去バージョンに残り得る点は、フェーズ1報告書の観測範囲の記述を引き継ぐ。
- **トークン**: Muse が検証用 Worker の操作に使うトークンが必要になった場合は、**開発者が発行**します（権限は対象を絞った最小限、工程終了時に開発者が失効）。
