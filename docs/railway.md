# Railwayへの公開と共同編集

この構成は、アプリ配信・Googleログインの確認・共同編集を1つのNode.jsサービスで実行します。作品・参加権限・ログインセッションは永続VolumeのSQLite、写真はRailway Storage Bucketsに保存します。Buckets未設定時はVolumeに写真を保存するため、小さな検証もできます。

利用者はGoogleアカウントでサインインします。Railwayのアカウントを用意するのは運営者だけです。Hobbyの月5ドル分は他のサービスと共用の利用枠であり、利用料が5ドルを超えると差額が発生します。

## 1. 新しいプロジェクトを作る

1. Railwayで **New Project → Deploy from GitHub repo** を選び、`overdozer1124/VHSlide` の `main` を接続します。
2. リポジトリ直下の `railway.json` を使用します。ビルドは `npm run build`、開始は `npm start`、ヘルスチェックは `/healthz` です。`package.json` でNode.js 24を指定しています。
3. アプリに **Volume** を追加し、マウント先を **`/data`** にします。`DATA_DIR=/data` を設定します。
4. **Networking → Generate Domain** でHTTPSの公開URLを発行します。
5. **Variables** に `PUBLIC_ORIGIN=https://発行されたドメイン` を設定します。末尾のスラッシュやパスは付けません。`NODE_ENV=production` も設定します。

**Volumeは必須です。** 普通のコンテナ内ディレクトリだけでは、再デプロイ時に作品が失われます。Bucketsを利用する場合も、SQLiteのためにVolumeが必要です。

この初期構成は **1レプリカ** 用です。複数レプリカ・複数リージョンへの拡張には、PostgreSQLへの移行とサーバー間の編集配信を追加する必要があります。

Railwayのダッシュボード・API・ビルドが障害で停止している間は、新規プロジェクト作成や公開を待ちます。コード・ローカルテストは先に準備できます。状態は [Railway Status](https://status.railway.com/) で確認します。

## 2. Googleログインを設定する

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作成し、Google Auth Platformのアプリ名・サポートメール・対象ユーザーを設定します。
2. OAuthクライアントを **ウェブアプリケーション** として作成します。
3. **承認済みのJavaScript生成元** に、RailwayのHTTPS URLを登録します。`https://example.up.railway.app` の形式で、パスは付けません。
4. 作成されたクライアントIDを、Railwayの **`GOOGLE_CLIENT_ID`** に設定します。
5. アプリを再デプロイし、「クラウド」からGoogleログインを試します。

Google Identity ServicesのIDトークンをサーバーで検証する方式です。この実装では **クライアントシークレット・OAuthのリダイレクトURI・Googleドライブの権限は使いません**。クライアントIDは公開設定ですが、BucketsのシークレットなどはGitHubにコミットしないでください。

テスト公開ではGoogle側の対象ユーザー・テストユーザー設定を確認してください。学校の管理対象アカウントは、管理者によるアプリの利用許可が必要な場合があります。Googleアカウントの本人確認と作品の編集権限は別で、作品ごとの招待・参加権限をサーバーが確認します。

ID未設定でもアプリは起動し、端末だけでの編集・JSON保存は利用できます。クラウド画面は準備中と表示されます。

## 3. 写真用のRailway Bucketを作る

同じプロジェクトにBucketを追加し、名前を例えば `photos` にします。アプリ側に以下のVariablesを設定します。値はRailwayの変数参照から挿入してください。

| アプリの変数               | Bucketの参照元                  |
| -------------------------- | ------------------------------- |
| `BUCKET_ENDPOINT`          | `${{photos.ENDPOINT}}`          |
| `BUCKET_NAME`              | `${{photos.BUCKET}}`            |
| `BUCKET_ACCESS_KEY_ID`     | `${{photos.ACCESS_KEY_ID}}`     |
| `BUCKET_SECRET_ACCESS_KEY` | `${{photos.SECRET_ACCESS_KEY}}` |
| `BUCKET_REGION`            | `${{photos.REGION}}`            |

最初の4変数はまとめて設定します。写真はサーバーで形式・大きさ・容量を確認してアップロードします。閲覧時は参加権限を確認したうえで、60秒の期限付きURLでBucketから直接配信します。ブラウザにBucketの認証情報を渡しません。アップロードとJSONへの書き出しはアプリ経由なので、その通信にはサービス側の送信量が発生します。

**写真保存先は運用開始前に決めてください。** Volumeに保存した既存写真は、Bucketの変数を追加しただけでは移りません。保存先の変更時は、写真ファイルの移行が必要です。

Bucketの自動バックアップはこの実装にはありません。RailwayのBucketにも自動バックアップ／バージョニングはないため、誤削除対策として写真を定期的に別途保管してください。

## 4. 使い方

1. 「クラウド」でGoogleログインします。
2. 現在の作品を「この作品をクラウドに保存」で保存します。端末の作品とは別の作品として作成します。
3. 作品を開いた状態で「クラウド → 共同編集の招待リンクを作る」を選びます。
4. 参加者がリンクを開き、Googleログインすると、その作品を共同編集できます。
5. 作成者は招待リンクの更新・無効化と、参加者の解除ができます。リンクの無効化だけでは、すでに参加した人の権限は解除されません。
6. 「保存」は写真を埋め込んだJSONをダウンロードします。JSONの従来上限は25MBです。クラウドの写真が多い作品では、この上限を超えることがあります。
7. 「端末の作品へ戻る」で、クラウドを開く前の端末の作品に戻れます。

同じ文字ボックスへの入力はYjsで統合し、図形の位置・色などはプロパティごとに共有します。同じプロパティの同時変更はYjsの規則でどちらかに確定します。グリッドの同じマスへの同時追加は、固定マスの空き位置へ整列して両方を保持します。

縦の連動設定・各段のサムネイル選択は利用者の端末ごとに保持します。参加者がページを切り替えても、自分の編集ページは勝手に切り替わりません。「もとに戻す」は自分の変更を対象にします。

通信切断時もブラウザ内で編集を続け、再接続時に変更を統合します。共有データはIndexedDB、表示中の作品はLocalStorageにも一時保存します。端末側の保存容量が足りない場合は通知します。写真の新規アップロード・未取得の写真の表示・写真付きJSON保存には接続が必要です。参加権限の解除や不正な更新などで共有が停止した場合は、自動で再送せず、JSON保存と作品の開き直しを案内します。

## 5. 初期の運営上限とバックアップ

| 変数                    | 省略時の値                       |
| ----------------------- | -------------------------------- |
| `MAX_CONNECTIONS`       | サーバー全体で200接続            |
| `MAX_ROOM_CONNECTIONS`  | 1作品50接続                      |
| `MAX_DECKS_PER_USER`    | 作成者1人40作品                  |
| `MAX_USER_ASSET_BYTES`  | 作成者1人250MB                   |
| `MAX_TOTAL_ASSET_BYTES` | Bucket使用時5GB、Volume保存時1GB |

ブラウザの複数タブも接続数に数えます。写真の容量は作品の作成者に計上し、共同編集者のアップロード分も含みます。削除したスライドの写真は、取り消し・再接続のため作品内に残します。作品をクラウドから削除すると、その作品の写真も削除します。

この上限は料金を5ドルに固定するものではありません。RailwayのCPU・メモリ・通信・ストレージの利用状況と請求額を確認してください。Hobbyの5GB VolumeにはDBとバックアップ用の空きも必要です。写真をVolumeに保存する場合、`MAX_TOTAL_ASSET_BYTES`を5GBいっぱいまで引き上げないでください。

RailwayでVolumeの定期バックアップを有効にし、復元の手順も確認してください。作品・セッション・招待・写真の対応表が `vhslide.sqlite` に入っています。SQLiteはWALを使用します。稼働中の `.sqlite` だけをファイルコピーすると不整合が起き得るため、Volumeの整合したバックアップまたは停止中のディレクトリ全体を保管します。写真をBucketsに置く場合は、写真のバックアップも別途必要です。

## ローカルでの確認

Node.js 24で実行します。

```sh
npm ci
npm test
npm run build
npm start
```

Googleログインを試す場合は、起動前に `GOOGLE_CLIENT_ID` と `PUBLIC_ORIGIN=http://localhost:3000` を環境変数に設定し、Google側にもその生成元を登録します。既定のデータ保存先は `./data`（Git管理対象外）です。`.env.example` は設定項目の説明用で、`npm start`が自動で読み込むファイルではありません。

開発時は `npm run dev:server` と `npm run dev` を別ターミナルで起動できます。Viteは `/api` とWebSocketを3000番へ転送します。Google側と `PUBLIC_ORIGIN` は、ブラウザで実際に開く生成元に合わせてください。

```sh
npm run test:cloud
```

クラウドのブラウザテストは本番ビルドを配信し、テスト専用のGoogle ID検証関数を注入します。本番の `server/index.ts` にはテストログインの仕組みはありません。実Googleアカウント・実Buckets・Railway公開後の確認は、設定後に別途必要です。
