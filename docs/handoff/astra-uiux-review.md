## 3. 製品の前提・利用者

- 名称：VHSlide。正式名称候補Matlidea（マトライディア、Matrix × Slide × Idea）。名称変更は未実施。
- コンセプト：「スライドを、線から面へ。アイデアを、次の次元へ。」
- 固定マスの`(x,y)`にスライドを配置する。元の意味は横が話題、縦が掘り下げ。ただし授業では行を個人・グループ、列を課題・観点にする用途もある。
- 表示のページ番号は「行.列」。3行目の2枚目なら3.2。データ座標は0始まりであり、表示順と混同しない。
- 児童・生徒と教師、Chromebook・iPad・Windows。マウスだけでなく、1本指でのページスワイプとタッチパッドの2本指操作を重視。
- 1授業40人程度を想定してきた。最大1000スライド、400枚のサンプルがある。実環境の多人数負荷や実機性能をすべて保証済みではない。
- 教師の単元設計、個人に行を割り当てる制作、グループに行を割り当てる共同制作が主な検討フロー。
- 原則として無料・広告なし。アカウントなしの端末編集・JSON保存を残し、Googleログインによるクラウド共同編集も提供。
- 行・列・スライド・シートの構造、安定IDに基づく担当権限、本人だけのUndo、保存・復旧の安全性は変更案でも維持すべき制約。

## 6. ローカルで再現する

### 準備・端末編集

Node **24.x**、npmを使用。ZIP展開先のプロジェクト直下で：

```bash
npm ci
npm run build
npm run preview -- --port 5174 --strictPort
```

`http://127.0.0.1:5174/` を新しいブラウザプロファイルで開く。サンプルは`src/model.ts/sample()`。既存の個人ブラウザのLocalStorageを消さない。大きいサンプルは「開く」から`public/samples/vhslide-10x40.json`を選ぶ（10列×40行）。

Vite previewはバックエンドがないため、`/api/config`等の接続拒否やクラウド機能の利用不可は起こり得る。UIの不具合と、試験構成の制限を分ける。共有を評価するときは下の独立サーバーを使う。

### 対象ブラウザ試験

Chromiumがなければ、環境のネットワーク規則に従って`npx playwright install chromium`。管理環境ではスキルのネットワーク設定に従う。既存の`/usr/bin/chromium`や`CHROMIUM_PATH`も設定で使用できる。

previewを手動起動していない状態で：

```bash
npm run build
npx playwright test --config playwright.preview.config.ts tests/e2e/editor-inspector-ux.spec.ts --workers=1
```

Playwrightが5174を起動する。既存プロセスとのポート競合を避ける。ビルド済みdistへ固定するため、試験中にソースを変更しても画面へ反映されない。今回はソース変更をしない。

### 共同編集の独立試験

実Googleアカウント・OAuthシークレット・Cloudflareトークンは不要。

```bash
npm run build
npx playwright test --config playwright.cloud.config.ts tests/cloud/content-editing.spec.ts tests/cloud/objects.spec.ts tests/cloud/structure-editing.spec.ts tests/cloud/tables.spec.ts --workers=1
```

`tests/cloud/server.ts`がlocalhost:3187に独立サーバーを起動し、一時ディレクトリを使用。名前は英小文字とハイフンで構成した合成ユーザー。`tests/cloud/objects.spec.ts`等の`login`ヘルパーで別ブラウザコンテキストを認証する。手動確認なら、ビルド後に`node tests/cloud/server.ts`を起動し、同じローカルページのブラウザコンテキストで`POST /api/auth/google`へ`{"credential":"review-host"}`（Content-Type: application/json）を送る。APIRequestContextを使う場合はOriginを`http://127.0.0.1:3187`にする。ホスト／生徒を別コンテキストで作る。テスト認証を本番に持ち込まない。

Cloudflareの代替実行は`playwright.cloudflare.config.ts`で同じ対象を実行。`tests/cloudflare/browser-server.ts`とMiniflareの独立Room／Directoryを使用する。Node版と同じ3187なので**同時実行しない**。保管パスの制限がある管理環境では`XDG_CONFIG_HOME=/tmp/vhslide-config WRANGLER_LOG_PATH=/tmp/vhslide-wrangler.log`をコマンドに限定して付ける。認証のために本番へ接続する必要はない。

### データを保護する

- 元のブラウザ状態、作品、クラウド保存先を使わない。
- 既存の学校・生徒のルームID・招待URLを探索・再利用しない。
- 公開先で参加申請・招待・共有解除・画像操作などをしない。
- `npm run cf:deploy`、`wrangler deploy`、GitHubへのpushを実行しない。
- 試験データと画像は合成のものだけを使用。画面資料はテスト用作品で、学校の個人情報を含む実作品の資料ではない。

## 7. レビューする代表フロー

1. **初見の児童**：説明を読み込まず、話題を右に追加、下に詳細を追加、文字・写真・表を入れる。自分がどのモードか、何が選択されているか、どこで入力するか分かるか。
2. **表を作る**：空白を押して入力→複数セル選択→書式→行列挿入→TSV貼付→整列→Undo。セル・表全体・スライド・設定欄の境界で誤操作しないか。長文・12×12も確認。
3. **図解を整える**：図解挿入→グループ移動→中の文字を編集→コネクタ接続→個別移動／削除→戻す。クリック、ダブルクリック、ドラッグの使い分けは発見できるか。
4. **大量の作品から探す**：400枚サンプル、名前付き行列、行番号一覧、自分の担当フィルタ、マップ番号表示。目的の作品を探して編集し、戻ったとき現在地を保てるか。
5. **タッチで往復する**：オブジェクト上からの1本指スワイプ、枠からの移動、ピンチでマップ⇄編集、タッチのサムネイル移動。意図した動作を選べるか。慣性・終端・途中の反転も見る。
6. **教師が準備する**：複数シート、メールの貼付による共有追加と順番の行割当、権限変更、参加申請の一括承認。設定の完了・未完了が分かるか。
7. **生徒が参加する**：承認待ち、閲覧のみ、担当範囲外、通信の切断・再接続、付箋。できない理由や次の行動が伝わるか。
8. **比較して発表する**：列フィルタ→比較→PDF→発表ルート→全画面→ページ内リンクと戻る。準備と開始、画面上で隠れる操作が分かるか。
9. **授業を終える／回復する**：端末保存、クラウド保存、JSON、ZIP、保存した版、ごみ箱、復元ジョブの違いと状態が理解できるか。独立サーバーでのみ失敗・復元を確認する。

画面サイズの目安：1366×768、ブラウザ上下領域を見込んだ1366×610、1024×640、タッチ端末、390×844。200%ブラウザ拡大・キーボードのみも候補。画面サイズを変えたLinux Chromiumを、実Chromebook／iPad Safari／Windowsでの動作と混同しない。

## 9. 既知の候補と、レビューの自由度

前回に残した候補は、長文がセルやPDFからはみ出す案内、最大12項目のグラフのラベル、複数セルの書式混在表示、小画面下部の設定欄、マップ・クラウド・編集の一貫性。ただし、**このリストからだけ探さない**。現在の3タブ構成や自動切替も、必ず良いと仮定しない。隠れた機能の増加や選択状態の喪失など、新しい問題がないか調べる。

本番データを保護する前提で、以下を独立に分けて評価する：

- 初めて見た人が目的の操作を見つけられるか。
- 分かった後に少ない手順で繰り返せるか。
- 誤ったときに気づき、戻せるか。
- 操作の見た目が実際の挙動と一致するか。
- 共同編集の権限・担当・保存状態が読み取れるか。
- 2次元構造を使う価値を、操作体系が支えているか。

## 10. 報告の形式

保存先：`docs/astra-uiux-review.md`（既存なら別名）。各指摘に次を含める。

- ID／重大度P0〜P3／対象利用者／画面・操作段階。
- 再現手順と期待すること、実際の挙動。
- 利用上の影響。好みだけか、操作上の障害かを区別。
- 実動作・コード・仮説・未確認の区分。
- ファイル、関数、行番号、画面証拠。行番号は実際の対象ソースから採る。
- 具体的な改善案、短期修正か再設計か、既存操作・権限・互換性への注意。

全体評価、優先10件程度の問題、フローごとの評価、情報設計案、改善順をまとめる。設計図は具体的な構成を示すために使い、見た目だけの完成案を根拠なしに良いとしない。レビュー終了時には追加実装やデプロイを行わない。
