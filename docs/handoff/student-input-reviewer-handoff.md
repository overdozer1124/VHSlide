# 引き継ぎ：生徒の入力機能の拡張 — レビュー担当（Claude）

- 作成：2026-11-16。クラウドの Claude セッションから、利用者の PC で動く Claude へ引き継ぐ。
- 引き継ぎ先の役割：**レビュー担当**。実装は Muse が行う。
- 正式な計画書：`docs/student-input-plan.md`（PR #11 のブランチ `claude/student-input-plan` にある）。この文書は、計画書にない経緯と作業の手順を補う。

## 1. 最初にすること

1. PR #11 を読む：https://github.com/overdozer1124/VHSlide/pull/11
   - `git fetch origin claude/student-input-plan` のあと、`docs/student-input-plan.md` を全部読む。特に第1節（使い方の前提）、第7節（利用者の判断）、第9節（PR 運用）。
2. リポジトリの `AGENTS.md` を読む。
3. GitHub に接続できるかを確かめる（`gh auth status` など）。
4. **SwarmChat に新しいチャンネルを作る**（利用者の依頼。第4節）。
5. PR #11 のコメントと、Muse の段階 PR（`muse/` で始まるブランチ）ができていないかを確かめる。
6. 利用者に、日本語で一言、引き継ぎが終わったことと、今の状況を伝える。

## 2. 利用者について（必ず守る）

- **英語は読まない。** 利用者への説明は、すべて日本語で、専門用語を避けて書く。PR のコメントも日本語で書く。
- 判断を求めるときは、**一問一答で、ボタンで答えられる形**（選択肢を示す質問）にする。推奨の選択肢を先頭に置き、「（推奨）」と付ける。
- 利用者は小中学校の授業で VHSlide を使う先生。生徒は Chromebook や iPad で操作する。
- **授業での使い方**：シートの**1行＝1時間の授業**。列はその時間のスライドの流れで、2行目が次の時間。1行を1人の生徒に割り当てる使い方はしていない。生徒の入力は、スライドに置いたワークシート・アンケート・ウェビングマップで受け取る。この前提に反する設計を通さないこと。

## 3. これまでの経緯

1. 利用者が「生徒が入力する機能に、授業で使える機能を追加したい」と依頼した。
2. Claude が提案し、利用者の補足（1行＝1時間）を受けて考え直した。
3. 利用者の発案で**思考ツール**（先生が配置し、生徒が書き込む）、**座標の場面ごとの履歴**（考えの変化が残る）、**感情メーター**（道徳）を加えた。
4. Claude の案（学びの記録、フィードバック、正解、タイマー、反応、班のワークシート）も含めて、計画書にまとめた。
5. 利用者が8項目の判断に答えた（計画書の第7節）。推奨と違う回答が2つある。
   - 感情を扱うツールは**特別扱いしない**（匿名の強制や、CSV の前の確認はしない）。
   - 共有した回答への反応で、**先生には誰が反応したかも見せる**（生徒には人数だけ）。
6. 利用者が次のことを決めた。
   - 実装は Muse、レビューは Claude が担当する。
   - GitHub の PR で共通理解を取りながら進める。
   - 土台のブランチは `codex/single-activity-entry-0.70.1` にする。
   - 承認後のマージとデプロイは Muse が行う。
   - SwarmChat に新しいチャンネルを作り、利用者がやり取りを見られるようにする。
7. Claude が計画書を PR #11（draft、取り込み先 `codex/single-activity-entry-0.70.1`）として出した。2026-11-16 の時点では、Muse の書き込みと段階 PR はまだない。

## 4. SwarmChat

- SwarmChat は利用者の PC で動いているチャットサーバー。過去の作業では `#general` が使われていた（例：「SwarmChat #general seq 691」）。使い方（起動方法、投稿の API やコマンド）は、PC の SwarmChat のフォルダーや、利用者に確認すること。
- **新しいチャンネルを作る**。名前の案：`#vhslide-student-input`。
- **投稿する時点**：段階 PR の作成、レビューの結果（🔴の件数と要点）、Muse の対応、承認、マージ、デプロイ。リンクと、日本語の短い要点を書く。正式な記録は GitHub の PR に残す。
- 秘密の情報（トークン、鍵、利用者のメールアドレスなど）は、SwarmChat にも PR にも書かない。
- 過去の記録には、PC のスリープで SwarmChat が止まったことがある。投稿できないときは利用者に伝える。

## 5. PR 運用（計画書の第9節の要点）

- Muse は段階ごとに PR を作る（ブランチ例：`muse/stage1-thinking-point`）。取り込み先は `codex/single-activity-entry-0.70.1`。
- Muse は、段階 PR の作成やレビューの依頼を、**PR #11 にコメントして知らせる**。PC のセッションには自動の通知が届かないことがあるため、利用者か Muse から声をかけてもらう。あるいは、作業の区切りで PR #11 と `muse/` ブランチを確かめる。
- 指摘には印を付ける：🔴 必ず直す／🟡 提案／💬 質問。Muse は指摘ごとに返信する。
- **すべて同じ GitHub アカウント（overdozer1124）で投稿される。** そのため、正式な「Approve」は使えない。「✅ 承認」と書いたコメントで承認する。コメントの末尾には「— Claude（レビュー担当）」と署名する。
- GitHub のコメントに `@名前` を書くと通知が飛ぶ。実在の利用者名以外には `@` を付けない。
- 🔴 がすべて解決し、承認したら、Muse がマージ・デプロイ・公開後の確認をする。**レビュー担当はマージもデプロイもしない。** 実装のコードを Muse のブランチへ直接 push しない（直してほしい点は指摘として書く）。
- 計画書と違う作り方が必要なときは、PR で相談する。利用者の判断が必要なことは、ボタンで答えられる質問で利用者に確認する。

## 6. レビューの観点（チェックリスト）

各段階の PR で、少なくとも次を確かめる。

**計画と前提**
- [ ] 第1節の前提（1行＝1時間）に反していない。生徒ごとの行を前提にしていない。
- [ ] 第7節の利用者の判断どおりになっている（特に、カードの移動は誰でもできるが、文字の変更と削除は本人と先生だけ。点は先生の共有時だけ匿名の分布で見える。感情ツールは特別扱いしない。部分点なし。反応した人の名前は先生には見えるが、生徒には見えない）。
- [ ] 計画書との違いが PR 本文に書かれ、理由が納得できる。

**権限とデータ（最重要）**
- [ ] 権限が、画面だけでなく **Node（`server/app.ts`）と Cloudflare（`cloudflare/directory.ts`）の両方**で強制されている。共通の処理は `src/*.ts` の `*Command` 関数にあり、両方から呼ばれている。
- [ ] 他人の個人の書き込み、他の班への書き込み、ホスト専用の操作が、両方のサーバーで拒否され、その試験がある。
- [ ] ホスト以外への応答に、渡してはいけない情報が入っていない。例：答え合わせ前の正解、反応した人の ID と名前、他人の個人の回答、書いた人の ID。**フォームの定義は参加者全員に配られる**ことに注意する。
- [ ] 既存の作品・回答・JSON がそのまま開ける。表の追加は `CREATE TABLE IF NOT EXISTS`、列の追加は起動時の移行。
- [ ] 要素の新しい結び付け（例：`thinking`）が、`src/model.ts` の解析と排他チェック、JSON の入出力、作品コピー（`formAdoption.ts`）、サムネイル、発表、集合、印刷で正しく扱われている。古い版のアプリで開いてもエラーにならない。

**負荷（Cloudflare の無料枠）**
- [ ] フォームのデータは、Cloudflare では**全作品分が単一の Directory（`directory-v1`）**に入る。1回の操作での書き込み行数、`deck` の索引を使った読み取り、全件の走査をしていないことを確かめる。
- [ ] 自動更新は、既存の `/api/decks/:id/poll` に版番号を加える形で統合され、問い合わせ数を増やしていない（0.113.1〜0.113.2 で減らした水準を保つ）。
- [ ] 回数制限（`this.rate(...)`）が両方のサーバーでそろっている。

**画面と操作**
- [ ] AGENTS.md の「UI/UX改善で維持するユーザー要件」を壊していない（発表の上下左右の2次元ナビゲーションなど）。
- [ ] タッチ（Chromebook・iPad）とキーボードだけで操作できる。小さい画面で切れない。
- [ ] 文言は、子どもと先生に分かる日本語になっている。

**公開の手順**
- [ ] `src/releaseHistory.ts` の先頭に、利用者向けの日本語の説明が加わっている（新機能は minor、修正は patch）。過去の履歴は書き換えていない。
- [ ] `package.json` と `package-lock.json` の版が、履歴とそろっている。
- [ ] 試験が加わっている：単体（`*.test.ts`）、Node API（`tests/server`）、Cloudflare（`tests/cloudflare`）、ブラウザー（`tests/cloud`、desktop と touch）。PR 本文に、試験のコマンドと結果がある。既存の失敗と新しい失敗が区別されている。
- [ ] 未検証の事項（実機の iPad・Chromebook など）を、検証済みと書いていない。

可能であれば、PR のブランチを取り込んで `npm test`、`npm run build`、`npm run test:cloudflare` を自分でも実行し、結果をレビューに書く。
