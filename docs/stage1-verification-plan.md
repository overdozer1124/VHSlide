# VHSlide スペース権限 段階① 検証計画

- 対象: VHSlide 学校向けスペース権限の段階①（認証・役割の土台）に関する検証
- 版: v0.1（2026-10-31、ドラフト。Codex のレビューを受ける）
- 根拠文書: 基本方針メモ v3.7、実装設計書 v2.10（いずれも `docs/`、Issue #3 で共有済み）
- 状態区分: **本書は計画であり、実装の開始を許可するものではない。** 検証の実施（試作を含む）と段階①の実装は、それぞれ開発者の指示があってから行う

## 1. 目的と範囲

段階①の検証は、次の2つを、検証環境だけで確認することを目的とする。

- (a) 初代スーパー管理者の登録方式（案A／案B／案C）について、実装設計書 第3節の確定条件を満たせるかを実証する。本番の登録方式の確定は、検証結果をもって開発者が別途判断する（検証と確定を混同しない）
- (b) 認証・役割の土台（所属の登録制、事前登録と結びつけ、資格照会、スキーマ移行）が、実装設計書 第9節の段階①受入条件を満たす形で実現できるかを確認する

範囲外： 本番環境への一切の変更、学校利用の本番有効化（段階②と同時が決定済み）、段階②以降の機能（作成制限・スペース接続・情報分離の本実装）。

## 2. 前提の再確認（着手時に最初に行う）

- 着手時点の最新版（`work` ブランチと公開版の版数）で、設計の前提（現行の認証・users テーブル・共有経路の実装）が変わっていないかを確認し、差分があれば計画へ反映する
- 保存先の前提： Cloudflare 側は Directory Durable Object であり、D1 向けの一般的な SQL 操作を前提にしない
- 両サーバー（Cloudflare／Node）で同じ資格判定になることが段階①の前提である

## 3. 環境と安全条件

- 対象は検証環境のみとする。手順と記録には対象環境の識別子を含め、本番と取り違える操作をしない
- 検証は一段ずつ、結果を確認してから次へ進める。失敗した場合は、その項目で止めて原因と影響を記録する（無制御な再試行をしない）
- 認証情報（シークレット類）は、値そのものをチャット・文書・記録に残さない。渡し方と無効化の手順だけを検証対象とする
- 検証で作った登録・データは、検証終了時に扱い（破棄／保持）を記録する

## 4. 検証項目

### A. 初代登録の候補実証（案ごとに実施）

各案について、次を確認する。結果は案ごとの比較表にまとめる。

| # | 項目 | 合格条件 |
|---|---|---|
| A1 | 到達方法 | Directory DO の保存先へ、その案の経路で実際に到達し、登録を記録できる |
| A2 | 原子性と一回性 | 登録と登録完了フラグ（対象環境・sub・登録日時）が原子的に記録され、並行実行・再実行で二重登録されない。完了後の再登録は拒否される |
| A3 | 認証情報の扱い | シークレットを使う案では、生成・保管・提示の経路と、登録後の無効化・除去が手順どおり行える |
| A4 | 経路の保護 | HTTP 経路を使う案では Origin／CSRF の検証が効き、経路の有効化と停止が手順どおり行える（常設にならない） |
| A5 | 運営者の認証と対象の証明 | 登録対象の sub が本人のものであることを、新アカウントの通常ログインのセッション等で確認できる |
| A6 | 環境の独立確認 | 対象環境を、操作者の申告以外でも照合できる（環境識別子の再入力等） |
| A7 | 復旧の実演 | 誤登録・喪失を想定し、復旧手順（旧アカウントのセッションを要求しない認可、失効と新規登録の原子的入れ替え、実行記録の保存、旧権限が残っていないことの資格照会での確認）が実際に回る |

### B. 登録制フロー

| # | 項目 | 合格条件 |
|---|---|---|
| B1 | 学校管理者の任命 | 学校管理者資格は、school_admin_applications に対するスーパー管理者の確定でのみ付与される。事前登録の作成・変更の経路からは付与できない（不変条件） |
| B2 | 教師資格のない学校管理者 | role を持たない学校管理者を登録でき、その場合も作品の作成・本文編集の権限が増えない |
| B3 | 事前登録の状態遷移 | 有効→結びつけ済み／取消 が設計どおりに遷移し、二重消費が起きない。同時消費・取消との競合でも一貫する |
| B4 | 結びつけの条件 | 照合は検証済みメール（email_verified、小文字化）で行われ、別メールでのログインでは結びつかない。所属が無効な利用者への結びつけでは所属が復活せず、その事前登録は取消（理由：所属無効）へ遷移する |
| B5 | ログイン種別の独立性 | 一般用・学校用のどちらのログインでも、同じ登録資格へ結びつく |
| B6 | 複数校への登録 | 複数校への事前登録・所属が、学校ごとに独立して扱える |

### C. 認可基盤と移行

| # | 項目 | 合格条件 |
|---|---|---|
| C1 | 資格照会の一貫性 | サーバーが返す操作資格が、Cloudflare／Node の両方で同じ判定になる |
| C2 | 既存セッションへの反映 | 資格の変更（付与・解除）が、接続済みの既存セッションにも反映される |
| C3 | 内部フラグの非混入 | is_super_admin 等の内部管理フラグが、既存の参加者向け応答へ混入しない（`SELECT users.*` の見直しを含む） |
| C4 | スキーマ移行 | organizations／preregistrations／organization_members／school_admin_applications の追加と、列名指定 INSERT への変更が、両サーバーで完了する |
| C5 | 移行の冪等性 | 移行の再実行で、データや権限が変わらない |

### D. 回帰

| # | 項目 | 合格条件 |
|---|---|---|
| D1 | 既存機能の維持 | 移行後も、既存のログイン・一般作品の作成・共有・復元が従来どおり動く |
| D2 | 一般利用への非干渉 | 学校所属のないアカウントの利用に、段階①の変更が影響しない |

## 5. 合格条件の集約と失敗時の扱い

- 上記の全項目に合格することが、段階①の検証完了の条件とする（実装設計書 第9節の段階①受入条件と対応づけて記録する）
- 項目が不合格の場合は、その項目で止める。設計の前提に関わる不合格（例： 案A／B／C のいずれでも A1・A2・A7 を満たせない、単調時計等の前提が崩れる）は、方式の確定を急がず、設計へ差し戻して開発者の判断を仰ぐ
- 検証結果は、項目ごとに「実施内容・結果・根拠（ログや画面の記録）」を残す。模擬的な確認だけで合格としない

## 6. 成果物と、その先の判断

成果物：

- 検証報告書（項目ごとの結果と根拠）
- 初代登録の候補比較表（案A／B／C × 確定条件）と、推奨案およびその理由

報告書の後に残る判断（いずれも開発者）：

1. 本番の初代登録方式の確定
2. 段階①の実装開始の可否

## 7. 実施順序の提案

1. 前提の再確認（第2節）
2. C4・C5（スキーマ移行と冪等性）→ C1〜C3（認可基盤）
3. A（初代登録の候補実証）
4. B（登録制フロー）
5. D（回帰）
6. 報告書と比較表の作成

## 付録: Codex へのレビュー依頼

本計画はドラフトです。次の観点でレビューをお願いします。

- 検証項目の不足（特に、段階①の受入条件に対応していない項目、検証環境で再現できない項目の有無）
- 案A／B／C の実証方法の実現性（Directory DO への到達方法を含む）
- 合格条件の測定可能性（曖昧な条件があれば指摘してください）
- 実施順序と安全条件の妥当性

アプリ実装・main統合・デプロイは引き続き保留です。
