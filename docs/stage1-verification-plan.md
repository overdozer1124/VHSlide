# VHSlide スペース権限 段階① 検証計画

- 対象: VHSlide 学校向けスペース権限の段階①（認証・役割の土台）に関する検証
- 版: v0.4（2026-10-31、Codex の v0.3 レビュー（条件付き賛成）を受けて改訂。中止と模擬試験の区別、移行のリリース単位を明確化。検証計画として実施手順を準備する基礎になると確認された）
- 根拠文書: 基本方針メモ v3.7、実装設計書 v2.10（いずれも `docs/`、Issue #3 で共有済み）
- 状態区分: **本書は計画であり、実装の開始を許可するものではない。** 各作業は、下記の区分ごとに開発者の指示があってから行う

## 1. 目的と、作業の区分

段階①の検証は、次の2つを、検証環境だけで確認することを目的とする。

- (a) 初代スーパー管理者の登録方式（案A／案B／案C）について、実装設計書 第3節の確定条件を満たせる候補があるかを実証する。本番の登録方式の確定は、検証結果をもって開発者が別途判断する（検証と確定を混同しない）
- (b) 認証・役割の土台（所属の登録制、事前登録と結びつけ、資格照会、スキーマ移行）が、実装設計書 第9節の段階①受入条件を満たす形で実現できるかを確認する

作業は次の3区分に分け、区分ごとに開発者の指示を得てから行う。区分を混同しない。

| 区分 | 内容 | 成果の扱い |
|---|---|---|
| 読取調査 | 既存コード・設定・保存先の読み取りによる確認（経路の有無、現行の到達方法など）。外部環境への変更を伴わない | 結果は記録のみ |
| 独立試作 | 隔離された検証環境でのみ動く、使い捨ての試作・スタブによる実証 | 試作のコードは製品へ持ち込まない。結果（証拠）だけを報告書へ残す |
| 製品実装 | 段階①そのものの実装（新テーブル、資格照会、認可処理など） | 別途の実施指示が必要。本計画の B／C／D 群の受入検証は、この実装を対象に行う |

検証は2フェーズに分ける。

- **フェーズ1（候補の実証）**： 読取調査と独立試作で、第4節 A群（初代登録の候補）を評価する。あわせて、C群の実現可能性に関わる読取調査（現行 INSERT の実態、保存先の構造）を行う
- **フェーズ2（受入検証）**： 製品実装（別途指示）の後に、検証環境で B／C／D 群と、A群の採用候補の受け入れを実施する。独立試作での確認は「模擬試験」として区別し、製品実装に対する合格とは扱わない

範囲外： 本番環境への一切の変更、学校利用の本番有効化（段階②と同時が決定済み）、段階②以降の機能の本実装。世代番号や学校作品の旧共有の復活防止は段階③の試験であり、段階①の合格項目には含めない（未実装の条件を合格済みとしない）。

## 2. 前提の再確認（着手時に最初に行う）

- 着手時点の最新版（`work` ブランチと公開版の版数）で、設計の前提（現行の認証・users テーブル・共有経路の実装）が変わっていないかを確認し、差分があれば計画へ反映する
- 保存先の前提： Cloudflare 側は Directory Durable Object であり、D1 向けの一般的な SQL 操作を前提にしない
- 両サーバー（Cloudflare／Node）で同じ資格判定になることが段階①の前提である

## 3. 環境隔離と中止条件

- 検証の実行先は、ローカルの Miniflare と Node のローカル保存先を基本とする。実 Cloudflare が必要な場合は、本番とは別の検証用 Worker・DO・認証設定・デプロイ先を用い、その実体（Worker 名、DO の名前空間と識別子、保存先）を計画の実施記録に特定する
- 検証用の試作・機能は、本番の Worker／DO／保存先へ接続できない形にする（本番の識別子・資格情報を検証環境へ渡さない。本番のバインディングを持たない）
- **実施前の照合（中止条件）**： 各回の実施前に、実際の実行先（Worker 名、名前空間、DO 識別子、保存先の識別子）を実行環境から読み取り、検証用として記録した対象と一致することを確認する。本番の識別子と一致する、または実行先を確認できない場合は、その回を実施せず中止する。識別子を操作者が入力し直すことは、独立した確認とはみなさない
- 環境ごとの読み取り方法： ローカル（Miniflare／Node）では、起動したランタイムが実際に読み込んだバインディングと保存先を、設定ファイルの記述ではなく実行状態から確認する。実 Cloudflare の検証環境では、アカウント側（ダッシュボードまたは API）から Worker 名と DO の名前空間を読み取り、デプロイに使った設定とは別経路で照合する。設定ファイルや環境変数を同じ出所から読み返すだけの確認は、独立した確認とはみなさない。実行先そのものを安全に確認できない場合は、その回の実施を中止する（模擬としても実施しない）。隔離された検証先は確認できるが、そこで実 Cloudflare の運用経路までは証明できない場合に限り、ローカルの結果を模擬試験として記録する（受入の根拠には使わない）。ローカルの試作で到達できたことは、実 Cloudflare での運用経路の実証とは区別する
- 検証は一段ずつ、結果を確認してから次へ進める。失敗した場合は、その項目で止めて原因と影響を記録する（無制御な再試行をしない）
- 認証情報（シークレット類）は、値そのものをチャット・文書・記録に残さない。渡し方と無効化の手順だけを検証対象とする
- 検証で作った登録・データは、検証終了時に扱い（破棄／保持）を記録する

## 4. 検証項目

### A. 初代登録の候補実証（フェーズ1。案ごとに評価する）

候補の評価方法： 各候補は「実現可／不可／未検証」を、証拠と理由つきで記録する。**全候補の合格は検証完了の条件としない**。検証の完了は、安全に実証できる候補が評価され、採用候補となり得るものが下記の必須条件をすべて満たすことである。実現の経路が確認できない候補（例： 案Bの DO 直接操作）は、作れると仮定せず「不可／未検証」として記録し、他の候補の選択を妨げない。

| # | 項目 | 合格条件（必須条件） |
|---|---|---|
| A1 | 到達方法 | Directory DO の保存先へ、その案の経路で実際に到達し、登録を記録できる（読取調査で経路の有無を確認してから試作する） |
| A2 | 原子性と一回性 | 登録と登録完了フラグ（対象環境・sub・登録日時）が原子的に記録され、並行実行・再実行で二重登録されない。完了後の再登録は拒否される |
| A3 | 認証情報の扱い | シークレットを使う案では、生成・保管・提示の経路と、無効化（案Aでは登録後の除去、案Cではローテーションを含む）が手順どおり行える |
| A4 | 経路の保護 | HTTP 経路を使う案では Origin／CSRF の検証が効く。有効期間の扱いは案別条件（下記）に従う |
| A5 | 運営者の認証と対象の証明 | 運営者の認証と、登録対象の sub の証明は、別の検査としてそれぞれ確認する。対象の証明は、新アカウントの通常ログインのセッション等で行える |
| A6 | 環境の確認 | 対象環境を、実行先の実体（第3節の照合）で確認できる |
| A7 | 復旧の実演 | 誤登録・喪失を想定し、復旧手順（旧アカウントのセッションを要求しない認可、失効と新規登録の原子的入れ替え、実行記録の保存）が実際に回る。復旧後は、旧アカウントの資格照会だけでなく、**旧アカウントの既存セッションから管理操作が拒否される**ことまで確認する |

案別条件： 案Aは「登録後に経路を無効化し、シークレットを除去する」ことを条件とする。案Cは常設の管理ルートを前提とする候補であり、常設を許容しない判断であれば条件不一致として「採用不可」と記録する。許容する場合は、認可・無効化・ローテーション・回復の経路を案C専用の条件として別途設計し、候補評価に含める（全候補へ一律の条件を当てて、満たせない案を無理に合格させない）。案Bは受付経路を持たないため、A3・A4 は適用外とする

A群の負のケース（期待結果を定めて実施する）： 未認証での登録試行の拒否、誤った対象 sub の拒否、環境違いの拒否、再実行の拒否、並行実行での二重登録の防止、処理途中の失敗・再起動後の状態の一貫性、旧アカウント喪失時の復旧、旧セッションの残存時の拒否。

### B. 登録制フロー（フェーズ2。B2のみフェーズ1の独立試作でも測定可）

| # | 項目 | 合格条件 |
|---|---|---|
| B1 | 学校管理者の任命 | 学校管理者資格は、school_admin_applications に対するスーパー管理者の確定でのみ付与される。事前登録の作成・変更の経路からは付与できない（不変条件）。スーパー管理者以外による任命・解除、自己昇格、他校への操作は拒否される |
| B2 | 教師資格のない学校管理者 | role を持たない学校管理者を登録できる。段階①では学校制限はまだ有効化されていないため、合格条件は「学校管理者フラグの追加により、既存の一般作品の権限を超える新たな権限を得ない」ことに限る（段階②以降の制限の効き方とは区別する） |
| B3 | 事前登録の状態遷移 | 有効→結びつけ済み／取消 が設計どおりに遷移し、二重消費が起きない。同時消費・取消との競合でも一貫する |
| B4 | 結びつけの条件 | 照合は検証済みメール（email_verified、小文字化）で行われ、別メールでのログインでは結びつかない。所属が無効な利用者への結びつけでは所属が復活せず、その事前登録は取消（理由：所属無効）へ遷移する。同じ sub のままメールが変わった場合は所属が維持される |
| B5 | ログイン種別の独立性 | 一般用・学校用のどちらのログインでも、同じ登録資格へ結びつく |
| B6 | 複数校への登録 | 複数校への事前登録・所属が、学校ごとに独立して扱える。同一メールでの複数校登録と、取消／二重消費の競合を含む |
| B7 | 所属の無効化と再有効化 | 既存の所属を無効化でき、再有効化は明示的な操作でのみ行われる（自動では復活しない）。再有効化の権限は学校管理者にあり、スーパー管理者の確認は必須としない |

### C. 認可基盤と移行（フェーズ2。C4 の実態確認はフェーズ1の読取調査で行う）

| # | 項目 | 合格条件 |
|---|---|---|
| C1 | 資格照会の一貫性 | サーバーが返す操作資格が、Cloudflare／Node の両方で同じ判定になる |
| C2 | 既存セッションへの反映 | 資格の変更（付与・解除）が、接続済みの既存セッションの**次の、認可チェックを伴う操作**に反映される（反映の時点を操作単位で定義する）。なお、接続中の WebSocket の受信失効の保証は段階①の合格項目ではなく、段階③の公開ゲートに残す |
| C3 | 内部フラグの非混入 | is_super_admin 等の内部管理フラグが、参加者向けの全応答（HTTP 応答と WebSocket のメッセージを含む）へ混入しない（`SELECT users.*` の見直しを含む） |
| C4 | スキーマ移行 | organizations／preregistrations／organization_members／school_admin_applications の追加と、既存の列名省略 INSERT の列名指定への変更が、既存行のある状態で、両サーバーで完了する |
| C5 | 移行の冪等性と再開 | 移行の再実行で、データや権限が変わらない。2回目の起動・移行でも同じ結果になる。移行の途中で失敗した場合は、ロールバックできるか、冪等な再実行で完了まで進められるかのいずれかが、サーバーごとに成立すること（実施手順で具体化する）。移行が完了するまでは、新しい列を使うアプリ側の変更を有効化しない。列の追加と INSERT の変更は整合した1つのリリース単位として扱い、途中状態で新旧どちらのコードを起動してよいかと、ロールバック後に旧コードが使えるかを、両サーバーで確認する |

### D. 回帰（フェーズ2）

| # | 項目 | 合格条件 |
|---|---|---|
| D1 | 既存機能の維持 | 移行後も、既存のログイン・一般作品の作成・共有・復元が従来どおり動く。旧 ZIP の復元は、検証対象の実データ形式で確認する |
| D2 | 一般利用への非干渉 | 学校所属のないアカウントの利用に、段階①の変更が影響しない |

## 5. 合格条件の集約と記録の方法

- フェーズ1の完了条件： A群について、採用候補となり得るものが必須条件をすべて満たし、各候補の評価（実現可／不可／未検証と証拠）が記録されていること
- フェーズ2の完了条件： B／C／D 群の全項目への合格（実装設計書 第9節の段階①受入条件と対応づけて記録する）
- 記録では、各項目を「対象」（独立試作／製品実装／実 Cloudflare 等）と「結果」（合格／不合格／未実施／適用外）の2軸で記録する。模擬的な確認だけで合格としない。実 Google ログイン・実 Cloudflare が未確認の項目は、その旨を明記する。フェーズ1の合格は候補試作の合格であり、製品の受入や本番方式の決定ではない
- 前提に関わる不合格（例： どの候補でも A1・A2・A7 を満たせない）は、方式の確定を急がず、設計へ差し戻して開発者の判断を仰ぐ
- 実施手順では、独立確認の具体的な取得方法（環境ごとに、何をどの経路で読み取るか）と、実 Cloudflare・実 Google を使わない項目の限界を、項目ごとに落とし込む

## 6. 成果物と、その先の判断

成果物：

- 検証報告書（フェーズごと。項目ごとの結果・根拠・記録区分）
- 初代登録の候補比較表（案A／B／C × 確定条件）と、推奨案およびその理由

報告書の後に残る判断（いずれも開発者）：

1. 本番の初代登録方式の確定
2. 段階①の実装開始の可否（フェーズ2は、この判断の後に行う）

## 7. 実施順序の提案

フェーズ1（読取調査・独立試作。実施指示が必要）：

1. 前提の再確認（第2節）と、環境隔離の準備・照合手順の確認（第3節）
2. 読取調査： A1 の経路の有無、C4 の既存 INSERT と保存先の実態
3. 独立試作： A群の候補評価（A1〜A7 と負のケース）、必要に応じて B2 の測定

フェーズ2（製品実装の後。実装の実施指示が別途必要）：

4. C4・C5（移行）→ C1〜C3（認可基盤）
5. B（登録制フロー）と A群の採用候補の受け入れ
6. D（回帰）
7. 報告書と比較表の作成

## 付録: Codex へのレビュー依頼

本計画はドラフトです。次の観点でレビューをお願いします。

- 検証項目の不足（特に、段階①の受入条件に対応していない項目、検証環境で再現できない項目の有無）
- 作業区分（読取調査／独立試作／製品実装）とフェーズ分けの妥当性
- 環境隔離と中止条件の具体性
- 案A／B／C の評価方法の実現性（Directory DO への到達方法を含む）
- 合格条件の測定可能性（曖昧な条件があれば指摘してください）

アプリ実装・main統合・デプロイは引き続き保留です。
