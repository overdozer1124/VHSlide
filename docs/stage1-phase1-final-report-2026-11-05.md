### 3.2 デプロイと到達（実測）

- ハーネスを API で配置し、シークレット付きバージョン ba920e0d を有効化（バインディング7件の読み戻し一致、workers.dev は無効）。

### 3.3 故障版に対する観察（実測、実証範囲の限定つき）

- 故障版R（登録のトランザクション途中で例外を起こす版）: /register が 500。資格・完了記録とも 0 件で、途中まで書かれた内容は観察されませんでした。

- 限定: どちらの 500 も汎用エラーであり、**指定した例外への到達自体は未特定**です。したがって「途中書込み後のロールバックが実環境で起きた」ことの実証にはなりません。確認できたのは処理前後の状態が一致していたという観察までであり、原子性の実証は 3.1 のローカル模擬に限ります。

### 3.4 通常登録と負のケース（実測）

- 通常登録: /register 201。資格・完了記録が各1件、完了記録の env_id が対象環境と一致しました。
- 誤った初回シークレット → 403。異なる Origin → 403。誤った復旧キー → 403。
- 再登録 → 409（already_registered）。一回性は実測で確認しました。
- nonce 取得から操作まで約20分空けた試行が 403（nonce_context_mismatch）になりました。nonce 文脈 Cookie の有効期間（5分）を超えたことが**有力な仮説**ですが、実測で期限切れそのものを確認したわけではありません。同一 nonce の再送の拒否も、実環境では未実施です（3.6）。
- /login（アカウントA）200、登録直後のセッションで /operate 200。
- ページ再読み込み後の /operate は 403（csrf_missing）。CSRF はメモリ上にのみ保持される実装のため、再読み込みで欠落の拒否になることを確認しました。これは CSRF **不一致**の拒否とは別物です（不一致は未実施）。

### 3.5 通常復旧（実測）

- アカウントB で /recover 201。資格・完了・復旧の記録が各1件になりました。
- 復旧記録の旧主体は完了記録の主体（A）、新主体は現在の資格（B）と一致し、env_id も一致しました。
- 復旧後: B の /operate 200、/login 200。A の新規 Google 認証による /login は 403（not_current_subject）でした（実測）。
- **旧アカウントの保持済みセッションからの拒否は未確認**です（復旧前のセッションを保持した画面が残らず、直接は試せませんでした。A7 の合格条件に含まれる要素のため、第4節で未実施として扱います）。
- 復旧の入れ替えの原子性については 3.3 と同じ限定がかかります（手続きが回り記録が保存されたことは実測、原子性の実証はローカル模擬のみ）。

### 3.6 復旧の再実行について（設計解釈の確定）

- 同一 nonce＋同一トークンの再送は、nonce の一回限り消費（consumeNonce）で拒否される設計であり、ローカル模擬で確認済みです。実環境での実演は行いませんでした（当初の ID トークンが失効しており、再送してもトークン検証で止まって帰属が取れません）。
- 新しい nonce と再認証で同じ主体（B）へ再度復旧することに、拒否条件は設計上存在しません。復旧は運営キーの操作であり、現アカウントの喪失時に再び結び直せる必要があります。実データでは試行していません（不要な復旧記録とセッション入替を生むため）。これを禁止したい場合は製品設計の変更であり、本検証の範囲外です。

### 3.7 再起動と状態保持（手順6、実測、留保つき）

- Data Studio のブラウザ操作がタイムアウトし続けたため（2026-11-04）、中断専用版 v1 では基準値が取れませんでした。開発者の承認を得て、診断読み取り（/test/state、/test/boot）を DIAG_KEY でゲートした v2 で実施しました。

- 留保: 増加が +2 であり、**因果と増分内訳は未確定**です（偶発的な自然再生成と区別できません）。状態保持は前後の件数とハッシュ対応の一致で確認しました。

## 5. 候補比較の更新（2026-11-01 版からの更新）

- **案A（使い捨てシークレット＋一時経路）**: 到達・一回性は実証の蓄積がある。到達経路の無効化は版の切替で確実に行える。一方で (1) 運営者認証が共有シークレットであり独立認可にならない、(2) 「登録後のシークレット除去」は今回の操作の範囲では有効版・最新版からの一覧上の除去までが達成でき、過去バージョンからの完全消去は確認できていない。単独では A5 の運営者認証が弱い。
- **案B（外部 CLI／SQL 直接投入）**: 受付経路を持たないため A3・A4 は適用外。前回記録の実操作は D1 の SQL コンソールであり、当初想定の CLI 経路そのものではない。原子性・並行・運営者認証・復旧はいずれも未検証のまま。今回は何も追加されていない。最も証拠が薄い。
- **案C（常設の管理ルート）**: 常設を許容しない判断であれば条件不一致として採用不可。許容する場合も、独立認可の実証は今回・前回ともなく未検証であり、認可・無効化・ローテーション・回復は案C 専用条件として別途設計が必要。
- **A＋C の組み合わせ（推奨構成）**: 実証があるのは一時経路（A）による初回登録と復旧の実演までで、運営・復旧の独立認可（C）は未検証のまま設計要件として段階②へ送る構成です。第4節のとおり未実施・未検証の要素は残りますが、致命的な前提不合格（どの候補でも A1・A2・A7 を満たせない等）は生じていません。

## 6. 推奨案と理由

**推奨: A＋C の組み合わせを本番の初代登録方式の土台とする。** ただしこの推奨は、**案C の独立認可が未検証であることを前提**とし、段階②で次の受入条件を満たすことを条件とします: 独立認可の設計と実証（認可・無効化・ローテーション・回復の各経路）、および旧セッション拒否の実証。理由:

1. 初回登録の到達・記録の保存・一回性・復旧手続きの一連が、実 Cloudflare・実 Google ログインで確認できたのは案A 相当の構成だけである（原子性の実証はローカル模擬の範囲）。
2. 一時経路は、使わない期間に受付面を持たないという案A の利点を保てる（無効化は版の切替で確実）。
3. 案A 単独の弱点（運営者認証）は、案C の独立認可を段階②の設計要件と受入条件として明示することで補う計画にできる。未検証であることは隠さない。
4. 案B は証拠がなく運用が重く、案C 単独は常設の可否判断と未検証の認可設計を同時に抱える。
