# ホストの操作停止に関する調査

> 追記：本書は0.43.1の調査記録。確認した経路への修正と修正後の回帰試験は [0.43.2の記録](connection-recovery-uiux-0.43.2.md) を参照。`tests/audit/host-freeze.ts` は旧版の固定ビルドを対象にした再現用であり、修正後の合格試験ではない。

2026-10-26（日本時間）。対象：公開版 0.43.1 相当の固定済み `dist`。調査依頼は「ホストが突然操作不能になり、画面更新まで復帰しなかった」。進行中の UI/UX 改修とは分けて検証した。

## 結論

**偶発的な端末不調と決めつけられない。ホスト権限が正常でも、一時的な更新エラーをきっかけに編集停止状態から自動復帰しなくなる経路を再現した。**

ただし、今回の利用中に発生した事象そのものの原因は未確定。当時の接続エラー・終了コード・直前の操作記録がなく、今回の再現では「編集停止」は確認したが、「全ボタンを含む画面全体の無反応」は再現していない。

アプリ実装の修正とデプロイは本調査では行っていない。追加したものは独立した調査スクリプト・報告・証拠のみ。進行中の UI 改修差分は破棄していない。

## 環境・安全条件

- Linux Chromium 154、1366×768。実 Chromebook / Windows 端末の試験ではない。
- Node と Miniflare（Cloudflare Durable Objects）の独立したローカル環境。架空のテストアカウント・一時ディレクトリを使用し、終了後にストレージを削除。
- 故障注入・大量通信はローカルの WebSocket に限定。本番の作品・共有ルーム・利用者データは読み取りも変更もしていない。
- 公開サイトには未認証でトップページとそこから参照される JS/CSS だけを GET し、固定 `dist` と SHA-256 が一致することを確認した。公開バックエンドの実行バイナリ全体がローカルと同一であることまで証明するものではない。
- `dist` を再ビルドせず利用し、未完成の UI 改修を混ぜていない。全アセットのローカルハッシュも保存。

証拠：[`public-build-check.json`](audit-evidence/host-freeze-2026-10-26/public-build-check.json)、[`dist-hashes.json`](audit-evidence/host-freeze-2026-10-26/dist-hashes.json)。

## 再現できた編集停止の仕組み

1. クライアントがサーバーの `type: "error"` を受信。
2. エラー種別を問わず `stopped = true` になる。
3. `canEdit()` はホストでも `stopped` なら false を返す。編集ツールが無効になり、変更処理 `apply()` も拒否する。
4. WebSocket が閉じると、`stopped` が true のため再接続タイマーを開始しない。オンライン復帰イベントも同じ条件で接続しない。
5. 画面更新・作品の開き直しで状態を初期化するまで、同じセッション内では停止したままになる。

根拠：

- `src/cloud.ts:123` `CloudWorkspace.canEdit()`：ホスト判定の前に停止状態を検査。
- `src/cloud.ts:529` `apply()`：共有停止中の更新拒否。
- `src/cloud.ts:596` `connect()` の `onmessage`：すべてのサーバーエラーで停止。
- `src/cloud.ts:610` `onclose`：4001/4002/4003 は停止、停止中は再接続しない。
- `src/cloud.ts:232` `online`：停止中はオンラインに戻っても再接続しない。
- `src/Editor.tsx:350`：編集権限に従って「文字」などの挿入操作を無効化。

サーバー側では、権限エラー以外の更新失敗を、失敗が一時的かどうかに関係なく `type: "error"` と終了コード 4002 にまとめている。

- `cloudflare/room.ts:719` `webSocketMessage()` の例外処理。
- `server/app.ts:1852` WebSocket 更新の例外処理。
- `cloudflare/room.ts:607`：1分の接続内で1200更新、または8,000,000バイトを超えると429。
- `server/app.ts:235` `rateLimit()`、同 `1764`・`1780`：Node の更新数・通信量制限。

このため、「操作が多いため、少し待ってからお試しください」という表示でも、待つだけでは同一画面の編集停止が解除されない。これは表示と復帰動作の不整合であり、改善対象として明確。

大量通信は意図的な再送であり、通常の操作で1200回に達することを証明していない。今回の実利用で制限に達した証拠もない。100ms の送信待ちを含む通常の UI と、人工的な通信試験は区別する。

停止試験では、停止後3.5秒の観測中に再接続が発生しないことを確認。無期限に復帰しないという判断は、観測時間だけでなく上記の停止ガードにも基づく。

各試験で次も確認した。

- 認証済み API から取得した作品の所有者は同じテストホストのまま。
- `.app-shell.inert` は false。全体マップへのボタン操作は可能。
- ブラウザの `pageerror` は0件。
- 切断試験では、送信途中だったタイトルが再接続後にサーバーへ保存された。

Node と Cloudflare の再読み込み後の差は、Node の制限がアカウント等をキーに持つ一方、Cloudflare の当該制限は接続に保持されることと整合する。単に画面更新を復旧策として案内しても、常に解決するとは限らない。

## 修正する場合の優先順と安全条件

1. **高：一時的な失敗と継続禁止の失敗を識別する。** Node / Cloudflare が機械判定できる原因・待ち時間を返す。429や一時的な保存障害は、未送信データを保ったまま待機・認証済み再接続する。権限剥奪・不正データ・protocol不一致まで無条件に再送しない。
2. **高：停止理由と復旧手段を画面に明示する。** ホスト表示だけでは現在の編集可否が伝わらない。再試行できる状態と、JSON保存・再ログイン・画面更新が必要な状態を区別する。小さな保存表示だけに復旧判断を委ねない。
3. **高：個人情報を含まない原因記録を残す。** アプリ版・時刻・接続状態・終了コード・エラー分類・未送信件数などを限定記録。本文、画像、氏名、メール、作品ID、招待URL、トークンを含めない。次の実発生を原因まで追跡できるようにする。
4. **中：接続・保存応答の監視期限を設ける。** 無応答時も二重接続やデータ破棄を起こさず、再照会・再接続へ進める。ACK消失時の再送・停止中の変更・権限変更・再試行の競合を回帰試験に含める。

既存の「作品を開き直す」は `src/CloudPanel.tsx:451` から `open(id, true)` を呼ぶ。これは未反映データの置き換えを伴うため、**自動復帰にこの処理をそのまま流用してはいけない**。現在の画面のデータを先に保護することが必要。
