# 生徒の入力機能 拡張 実装計画（思考ツール・学びの記録 ほか）

- 作成：2026-11-16（Claude）
- 実装担当：Muse
- 基準ブランチ：`codex/single-activity-entry-0.70.1`（計画作成時は 0.135.0。利用者決定）。着手前に最新を取り込み、各機能の現状を確認し直すこと。

## 1. 前提：授業での使い方

利用者（先生）は、**1行を1人の生徒に割り当てる使い方をしていない**。

- シートの **1行＝1時間の授業**。列は、その時間のスライドの流れ。2行目が次の時間、3行目がその次の時間。マップ全体が単元の流れになる。
- 生徒の入力は、スライドに置いたフォーム（ワークシート・アンケート・ウェビングマップ）で受け取る。回答はスライド本体とは別に、生徒ごとに保存される。
- このため、同じスライドを生徒の人数分複製する必要がない。

この計画のどの機能も、この使い方を前提にする。「生徒ごとの行」や「担当行」を前提にした設計にしないこと。

### 2.1 実装に影響する現状の重要事項

1. **フォームのデータは、Cloudflare では単一の Directory（`directory-v1`）に全作品分が入っている。** Node 版は同じ SQLite に入る。回答が増える機能（点の履歴、カード、反応）は、Directory の書き込み・読み取りの量を増やす。いずれの機能でも、1回の操作で1行を書く形を守る。一覧の取得は作品ID（`deck`）の索引を使い、全件を走査しない。自動更新は既存の `/poll` に版番号を1つ加える形で統合する（0.113.1〜0.113.2で減らした問い合わせ数を増やさない）。
2. **フォームの定義は参加者全員に配られる**（`worksheetList` が定義を返す）。正解など「先生だけが知るべき情報」を定義に入れる場合は、サーバーがホスト以外への応答から必ず取り除く。
3. **完全バックアップ（ZIP）にフォームの回答が含まれているかは要確認。** `src/backup*.ts` の検索ではワークシートなどの記述が見つからなかった。新しいデータの扱いは、少なくとも既存のフォームと同じ方針にそろえる。含まれていない場合は、第5節の「共通課題」として別に扱う。
4. **要素の結び付けは1つの要素につき1種類。** 新しい種類を加えるときは `model.ts` の排他チェックに加える。古い版のアプリで新しい作品を開いたときの挙動（無視するか、エラーになるか）を確かめ、エラーにならないようにする。

## 3. 全体に共通する方針（すべての機能で守ること）

- **AGENTS.md に従う。** 公開のたびに `src/releaseHistory.ts` の先頭へ日本語の説明を加える（新機能は minor、修正は patch）。`package.json` と `package-lock.json` を同じ版にする。過去の履歴は書き換えない。通常は検証のあと Cloudflare 本番へデプロイし、公開後の確認まで行う。
- **権限は画面だけでなく、Node と Cloudflare の両方のサーバーで強制する。** 共通の処理は `src/*.ts` の `*Command` 関数（`HistorySQL` を使う）に置き、両方のサーバーから呼ぶ。既存のフォームと同じ構成にする。
- **後方互換。** 既存の作品・回答・JSON をそのまま開ける。新しい表は `CREATE TABLE IF NOT EXISTS` で作り、既存の表に列を足すときは起動時の移行を入れる。
- **UI/UX の既存要件を守る**（AGENTS.md の「UI/UX改善で維持するユーザー要件」）。発表の上下左右の2次元ナビゲーション、フィルタ後の格子配置などを変えない。
- **子どもの情報の扱い。** 個人の回答は、本人とホストにしか見えないことを標準にする。共有するときは、氏名ありと匿名を選べるようにする（既存の回答スライドの共有と同じ）。
- **入力の保存。** 既存のフォームと同じく自動保存し、未送信の内容は端末に残して、通信が戻ったら送る（0.71.0の仕組み）。
- **タッチと小さい画面。** Chromebook と iPad で、指で操作できる大きさにする。キーボードだけでも操作できるようにする（点の移動は矢印キー、カードはメニューから区切りを選べる）。
- **試験。** 単体（`*.test.ts`）、Node API（`tests/server`）、Cloudflare（`tests/cloudflare`）、共同編集ブラウザー試験（`tests/cloud`、desktop と touch）を加える。権限の拒否（他人の回答・他の班への書き込み・ホスト専用操作）は、両方のサーバーで試験する。

## 4. 機能別の計画

### 4.1 思考ツール（最優先）

#### 4.1.1 考え方

ツールを1つずつ別に作らず、**3つの型**を作り、その上に各ツールを「ひな形」として載せる。先生はひな形を選び、ラベルや区切りを授業に合わせて変えてからスライドに配置する。生徒はスライド上で直接書き込む。

| 型 | 生徒の操作 | ひな形の例 |
|---|---|---|
| **位置型**（point） | 軸や図の上に点を置く | 座標軸（2軸）、数直線（1軸）、感情メーター、心情円、心情曲線 |
| **区切り・カード型**（board） | 区切られた場所にカードを書いて置く | ベン図（2つ・3つ）、Xチャート、Yチャート、Wチャート、Tチャート、PMI、マトリックス（2×2）、KWL、フィッシュボーン、バタフライチャート、クラゲチャート、ピラミッドチャート、くまでチャート |
| **つなぐ・並べる型**（flow） | カードを順につなぐ、枝を伸ばす | ステップチャート、個人用のウェビング（コンセプトマップ） |

全員で1枚に書くウェビングマップは今の機能のまま残し、フォーム画面の「思考ツール」の一覧からも選べるようにする（入口を1つにする）。

#### 4.1.2 書き込みの単位（個人・班・全体）

利用者の希望により、**どの型も「個人」と「班」の両方に対応する**。あわせて「全体」も用意する。

| 単位 | 書き込む場所 | 見える範囲（既定） | 編集できる人 |
|---|---|---|---|
| 個人 | 生徒ごとに1枚 | 本人とホスト | 本人とホスト |
| 班 | 班ごとに1枚（グループの仕組みを使う） | 同じ班とホスト。他の班の閲覧は先生が許可したときだけ（ウェビングと同じ） | 同じ班の全員とホスト（下記） |
| 全体 | 全員で1枚 | 参加者全員 | 参加者全員とホスト（下記） |

- 単位は、ツールを作るときに選ぶ。受付を始めたあとの変更は、回答がない間だけ許可する。
- **班と全体での編集のルール（利用者決定）**：カードを動かす操作は誰でもできる（並べ替えや分類が思考ツールの中心のため）。カードの文字の変更と削除は、書いた本人とホストだけにする。書いている間は、ウェビングと同じ短いロックをかけ、ほかの人が同時に書き換えないようにする。
- 班に入っていない生徒には、班を選ぶ案内を出す（今の join を使う）。

#### 4.1.3 位置型（座標軸・数直線）と「場面ごとの履歴」

**先生の操作**
1. フォーム画面の「思考ツール」から、位置型のひな形を選ぶ。
2. 軸の名前と両端の言葉を入れる（例：横「反対⇔賛成」、縦「自信がない⇔ある」）。目盛りは「なし」「5段階」「10段階」から選ぶ。
3. **場面**を設定する（例：場面1「話を読む前」、場面2「話し合いの後」）。場面は0個（1回だけ置く）でもよい。
4. 「理由を書く」をオン／オフする。
5. スライドに配置し、受付を始める。場面の進め方を「先生が切り替える」と「生徒が自由に選ぶ」から選ぶ。

**生徒の操作**
- 今の場面で、点をドラッグかタップで置く。理由を書く。
- **前の場面の自分の点は薄く表示し、矢印でつなぐ。** 自分の考えの動きが、その場で見える。
- 班の単位では、班で1つの点を置く。点を動かした人と、場面ごとの理由が残る。

**時間（行）をまたぐ履歴：シリーズ**
- 同じ軸のツールを複数の時間（行）のスライドに置いたとき、それらを「同じシリーズ」として結び付けられるようにする（作成時に「前の時間のツールの続き」を選ぶ）。
- シリーズに入れたツールでは、前の時間の自分の点も薄く表示する。単元の初めから終わりまでの考えの変化が残る。
- 軸の名前と目盛りはシリーズ内で共有する（あとから変えたときは、すべての時間に反映する）。

**先生の画面（授業コンソール）**
- 場面ごとのクラス全体の分布（散布図。点が重なるところは濃く表示する）。
- 「再生」で、場面1から順に全員の点がどう動いたかを動きで見せる。
- 生徒を1人選ぶと、その生徒の軌跡と理由を時系列で見られる。
- 分布は、回答スライドの共有と集合で全員に見せられる。氏名ありと匿名を選べる（既存の共有と同じ）。
- **「全体」の単位でも、生徒にはふだん自分の点だけを表示する**（利用者決定）。ほかの人の点は、先生が共有・集合したときに、匿名の分布として見える。
- CSV：生徒×場面の値と理由。

#### 4.1.4 感情メーター・心情円（道徳など）

位置型の仕組みで作る。

| ひな形 | 内容 |
|---|---|
| 感情メーター | 1本の軸。両端と途中に顔のアイコン（5段階）。気持ちの強さを置く。「気持ちの温度計」のように縦置きもできる |
| 心情円 | 2色の円を回して、2つの気持ちの割合（0〜100%）を表す。色ごとの名前を先生が付ける（例：「正直に言いたい」「黙っていたい」） |

- 場面と履歴、シリーズは、座標軸と同じように使える。
- **ほかの思考ツールと同じ扱いにする**（利用者決定）。感情を扱うツールだけの特別な制限（匿名の強制、CSV前の確認など）は設けない。共有の氏名あり・匿名は、先生がその都度選ぶ。

#### 4.1.5 心情曲線

- 横軸を物語の場面（先生が設定）、縦軸を気持ちの上がり下がりにして、場面ごとに点を置き、線で結ぶ。点ごとに一言書ける。
- 登場人物ごとに線を分けられる（最大3本）。
- 先生の画面では、全員の線を重ねた表示と、クラスの平均の線を見られる。
- データは位置型と同じ形（場面ごとの値）で持つ。

#### 4.1.6 区切り・カード型

**先生の操作**：ひな形を選び、区切りの名前（ベン図の円の名前、Yチャートの3つの観点など）を変える。カードの色の意味（例：自分の考え＝黄、友だちの考え＝青）を決めることもできる。単位（個人・班・全体）を選んで配置する。

**生徒の操作**：区切りの中をタップしてカードを書く。カードはドラッグで別の区切りへ移せる。キーボードでは、カードのメニューから移動先の区切りを選ぶ。

**区切りの決め方**：ひな形ごとに、区切りの形（四角・円・扇形・帯など）と、点がどの区切りに入るかの判定を持つ。ベン図の重なりのように、複数の区切りに同時に入る場所も扱う（「AとBの重なり」を1つの区切りとして判定する）。

**先生の画面**
- 生徒（または班）ごとのチャートを並べて見る（「生徒のスライド」と同じ一覧の形）。
- **区切りごとに全員のカードを集める**（例：ベン図の重なりに書かれたことだけを一覧にする）。言葉の分析（0.121）にもかけられる。
- よいチャートを選んで、回答スライドの共有や集合で見せる。

**上限（既定案）**：1枚のチャートにつきカード100枚、1枚80文字。作品全体の上限は第5.2節。

#### 4.1.7 つなぐ・並べる型

- ステップチャート：カードを順に並べ、矢印でつなぐ。並べ替えはドラッグか上下ボタン。
- 個人用のウェビング：今のウェビングマップの描画と操作を流用し、個人や班の単位で使えるようにする。

#### 4.1.8 データの持ち方（案）

新しいモジュール `src/thinkingTools.ts` を作り、既存のフォームと同じ構成にする（定義の表＋書き込みの表、`*List`・`*Command`、版番号のトリガー）。

```text
thinking_tools(
  id TEXT PRIMARY KEY, deck TEXT NOT NULL REFERENCES decks(id) ON DELETE CASCADE,
  kind TEXT NOT NULL,          -- 'point' | 'board' | 'flow'
  template TEXT NOT NULL,      -- 'axis2' | 'axis1' | 'emotion' | 'ratio' | 'curve' | 'venn2' | 'ychart' ...
  unit TEXT NOT NULL,          -- 'individual' | 'group' | 'class'
  definition TEXT NOT NULL,    -- 軸・区切り・場面・色の意味など（JSON）
  series TEXT,                 -- シリーズID（時間をまたぐ履歴）
  status TEXT NOT NULL,        -- 'draft' | 'open' | 'closed'
  scene TEXT,                  -- 先生が切り替える場合の今の場面
  created INTEGER NOT NULL)

thinking_points(               -- 位置型
  tool TEXT NOT NULL REFERENCES thinking_tools(id) ON DELETE CASCADE,
  owner TEXT NOT NULL,         -- 個人：利用者ID／班：班ID／全体：''
  scene TEXT NOT NULL,         -- 場面ID（場面なしは ''）。心情曲線は「場面ID:線ID」
  value TEXT NOT NULL,         -- {x,y} または {v} または {ratio}
  reason TEXT NOT NULL DEFAULT '',
  author TEXT NOT NULL,        -- 最後に書いた人
  updated INTEGER NOT NULL,
  PRIMARY KEY(tool, owner, scene))

thinking_cards(                -- 区切り・カード型、つなぐ・並べる型
  id TEXT PRIMARY KEY,
  tool TEXT NOT NULL REFERENCES thinking_tools(id) ON DELETE CASCADE,
  owner TEXT NOT NULL,         -- 個人：利用者ID／班：班ID／全体：''
  zone TEXT NOT NULL,          -- 区切りID（flow型は ''）
  parent TEXT,                 -- flow型のつながり
  sort INTEGER NOT NULL DEFAULT 0,
  text TEXT NOT NULL, color TEXT NOT NULL DEFAULT '',
  x REAL NOT NULL, y REAL NOT NULL,
  author TEXT NOT NULL, created INTEGER NOT NULL, updated INTEGER NOT NULL)

thinking_locks(...)            -- ウェビングの webbing_locks と同じ形
```

- スライドの要素には、新しい結び付け `thinking: { deckId, toolId }` を加える（`model.ts` の排他チェックに追加）。
- API：`/api/decks/:id/thinking`、`/thinking/:toolId/(status|scene|point|card|lock|edit)`。両方のサーバーで同じルートと同じ回数制限にする。
- 自動更新：`/poll` に `tv`（thinking の版番号）を加える。
- 一覧で返す範囲：ホストには全員分。参加者には、自分（個人）・自分の班（班）・全体（全体）の分だけ。他の班の閲覧を許可したときは読み取り専用で加える。**書いた人の名前とID**は、ホストと同じ班の人以外には返さない。
- 作品コピー（`formAdoption.ts`）：定義を引き継ぎ、書き込みは引き継がない。シリーズは、コピー先の作品内で付け直す。

#### 4.1.9 完了の条件（思考ツール）

- 3つの型と主なひな形が、個人・班・全体のそれぞれで、PC とタッチの両方で使える。
- 他人の個人の書き込み、他の班の書き込み、ホスト専用の操作（場面の切り替え・受付の状態・削除）が、Node と Cloudflare の両方で拒否される。
- 場面ごとの履歴と、シリーズによる時間をまたぐ履歴が、生徒の画面と先生の画面の両方で見える。
- 40人が同時に点を動かしても、自動更新の問い合わせ数が既存の機能と同じ水準に収まる（計測して記録する）。

### 4.2 学びの記録（時間をまたぐ見方）

行が授業の1時間ずつに並ぶ使い方を活かし、**単元全体での一人ひとりの学び**を見られるようにする。

1. **生徒別のタイムライン（先生）**：生徒を1人選ぶと、その作品にあるすべてのフォームとツール（ワークシート・アンケート・思考ツール）の回答を、マップの順（シート→行→列）に並べて表示する。行の見出し（例：「第3時 ○○について」）を時間の名前として表示する。印刷・PDF・CSV に対応する。
2. **自分の記録（生徒）**：自分の回答だけを同じ形で見られる。4.3節の先生からのコメントもここに表示する。
3. **「前の自分の回答」を表示する部品**：スライドに置くと、見ている生徒自身の、指定したフォーム項目の回答（または思考ツールの点）を表示する。たとえば、1時間目の予想を5時間目のスライドに出して比べさせる。ホストの画面には、部品の場所と元の項目名だけを表示する。サーバーは本人の回答だけを返す。
4. **単元の回答状況**：生徒×時間（行）の表で、回答済み・未回答を示す。欠席した生徒が、後から取り組むべき場所がわかる。セルを押すと、そのスライドを開く。

**データと API**
- 新しい表は不要（既存の回答の表を読む）。生徒別・単元別の集計用の読み取り API を1つ加える。
  - 例：`GET /api/decks/:id/record?user=` はホスト用（全員分）。`GET /api/decks/:id/record/me` は本人用。
- スライドの位置と行の対応は、安定した行ID（`axes.ts`）で取る。行を並べ替えても、記録の順番が追従するようにする。
- 回答の多い作品でも重くならないよう、サーバー側でまとめて計算する。その時間（行）のスライドだけを取り出すなど、件数を絞れるようにする。

### 4.3 先生から生徒へのフィードバックと差し戻し

- 授業コンソールの回答一覧・生徒のスライド・思考ツールの一覧から、生徒（または班）の回答ごとに、**短いコメント（200文字まで）とスタンプ**を返せる。スタンプは先生が選べる固定のもの（例：「よくできました」「なるほど」「もう一歩」「すてきな考え」）。
- 見えるのは**本人（班の場合は班の全員）とホストだけ**。
- 先生が送ったら、すぐに生徒に見えるようにする（利用者決定）。
- 生徒は、スライドの回答欄のそばに出る印と、「自分の記録」で確認する。未読の印を付ける。
- **差し戻し**：「書き直してほしい」と返すと、受付が終わったあとでも、その生徒（または班）だけ書き直せる状態にする。書き直して保存すると、先生の一覧に「再提出」と表示される。
- データ（案）：`form_feedback(id, deck, target_kind, target_id, owner, text, stamp, reopen INTEGER, created, read_at)`。`target_kind` は `worksheet` / `survey` / `thinking`。`owner` は利用者IDまたは班ID。
- サーバーは、受付終了後の書き込みを、`reopen` が有効な本人（班）に限り許可する。両方のサーバーで同じ判定をする。

### 4.4 正解のある問題と答え合わせ

- ワークシートの単一選択・複数選択・並べ替えに、**正解**を登録できるようにする。記述には「認める答え」（複数）を登録できる。全角と半角、前後の空白、ひらがなとカタカナの違いをそろえてから比べる。
- 答え合わせのタイミング：「先生が『答え合わせ』を押したとき」（既定）と「回答したらすぐ」から選ぶ。
- **正解は、答え合わせの前にホスト以外へ送らない**（第2.1節の2）。定義を返すときにサーバーが取り除く。答え合わせのあとに、正誤と正解を返す。
- 生徒の画面：答え合わせのあと、自分の回答に○×と正解を表示する。
- 部分点は付けない（利用者決定）。全部合っていれば○、それ以外は×。
- 先生の画面：設問ごとの正答率、選ばれた誤答の内訳、全問正解の人数。CSV に正誤の列を加える。

### 4.5 共有した回答への反応

- 回答スライドを共有したとき、生徒がほかの人の回答に「いいね」「参考になった」「なるほど」を付けられるようにする（1人1回ずつ。付け直せる）。
- 先生が、共有ごとに反応の受け付けをオン／オフする（既定はオフ）。
- 反応の数は、共有の画面に表示する。先生は、反応の多い回答を選んで、集合で紹介できる。
- **匿名の共有を守る**：反応の対象は、利用者IDではなく、共有ごとに作る別のID（その共有の中だけで使う番号）で指す。反応した人の名前は、生徒には見せない（人数だけ）。**先生には、誰が反応したかも見せる**（利用者決定）。ホスト以外への応答に、反応した人のIDや名前を含めないこと。
- データ（案）：`share_reactions(share, item, reactor, kind, created, PRIMARY KEY(share,item,reactor,kind))`。共有を止めたら、反応も読めなくする。

### 4.6 受付時間のタイマー

- ワークシート・アンケート・ウェビング・思考ツールの受付に、終了時刻を付けられるようにする（「あと3分」「5分」「10分」、任意の分数）。
- 全員の画面に残り時間を表示する。延長と、すぐの終了ができる。
- **終了はサーバーが判定する**：終了時刻を表に保存し、書き込みのたびにサーバーの時刻と比べて拒否する。読み取りのときも、終了時刻を過ぎていれば終了として返す。Cloudflare のアラームや常駐タイマーは使わない（休眠を妨げないため）。
- 画面の表示は、`/poll` の応答に入れたサーバーの時刻との差で補正する。
- 終了の直前まで書いていた内容は、送信中のものを受け付けられるよう、数秒の猶予を設ける（既定案：3秒）。

### 4.7 班で1つのワークシート

- ワークシートに「班で回答する」の設定を加える。回答は班IDごとに保存し、班の全員が同じ回答欄に書く。
- 書いている間は、入力欄ごとに短いロックをかけ、誰が書いているかを表示する（ウェビングと同じ方式）。
- 先生の画面では、班ごとに回答を並べて比べる。CSV は班ごとの行にする。
- 既存の個人のワークシートには影響させない（設定がない場合は今までどおり）。

## 5. 共通の課題

### 5.1 班の割り当て
今は参加者が自分で班に入る。**ホストが参加者を班に割り当てる操作**（一覧から選ぶ、名簿の順にまとめて割り当てる）を加える（利用者決定）。生徒が自分で班に入る今の方法も残す。割り当ての変更は両方のサーバーでホストだけに許可する。段階9で実装するが、思考ツールの班の単位（段階1）で必要になれば前倒ししてよい。

### 5.2 容量と負荷の上限（既定案）
| 対象 | 上限 |
|---|---|

| 1枚のチャートのカード | 100（1枚80文字） |

| フィードバック | 1件200文字。作品あたり5,000件 |

### 5.3 バックアップ
既存のフォームの回答が完全バックアップに含まれているかを確かめる。含まれていない場合、思考ツール・フィードバック・反応を含めて「フォームのデータをバックアップに入れる」作業を、別の段階として計画する（この計画の後に行ってよい）。

### 9.2 ブランチと PR
- **土台**：`codex/single-activity-entry-0.70.1`（利用者決定）。各段階の PR はこのブランチへ取り込む。
- **計画・連絡用 PR**：計画書（`docs/student-input-plan.md`）を載せた PR を、連絡の窓口にする。Muse は次の時点で、この PR にコメントする。Claude はこの PR の通知を受け取っている。
  - 段階の PR を作ったとき（リンクを付ける）
  - レビューを依頼するとき・指摘に対応し終えたとき
  - マージ・デプロイを終えたとき（版番号と結果）
- **段階の PR**：段階ごとに1つ作る。ブランチ名の例：`muse/stage1-thinking-point`。前の段階が取り込まれてから、最新の土台から次のブランチを作る。
- **PR の本文に書くこと**：
  1. 段階と、実装した範囲（第6節のどこか）
  2. 計画書との違いと、その理由
  3. 第7節の利用者決定をどう反映したか
  4. 試験のコマンドと結果（成功・失敗の件数。失敗は既存の失敗かどうかも）
  5. 未検証の事項
  6. 版番号と、更新履歴に載せる文
  7. 画面の変更がある場合は、スクリーンショット

### 9.3 レビューの約束
- Claude の指摘には、重さの印を付ける。
  - 🔴 必ず直す（マージの前に対応が必要）
  - 🟡 提案（対応するか、しない理由を返信する）
  - 💬 質問
- Muse は、指摘ごとにスレッドで返信する（直したコミット、または直さない理由）。
- 計画書と違う作り方が必要になったときは、先に PR で相談する。利用者の判断が必要なことは、どちらかが利用者に確認する。勝手に仕様を変えない。
- **承認の方法**：PR はすべて同じ GitHub アカウント（overdozer1124）から作られる。GitHub では自分の PR を正式に「Approve」できないため、Claude は「✅ 承認」と書いたコメントで承認する。
- **署名**：同じアカウントで投稿するため、コメントの末尾に署名を付ける（「— Muse」「— Claude（レビュー担当）」）。
- 🔴 がすべて解決し、Claude が承認したら、Muse がマージする。そのあと AGENTS.md に従ってデプロイと公開後の確認をし、結果を PR に書く。
