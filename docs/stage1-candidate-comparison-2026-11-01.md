# 段階① 初代登録候補の比較（中間、2026-11-01）

根拠：段階①検証計画 v0.4、実装設計書 v2.10、`docs/stage1-google-cloud-recovery-2026-11-01.md`。これは独立試作の中間評価であり、製品実装の承認や本番方式の確定ではない。

| 候補 | 現時点の評価 | 得られた根拠 | 残件 |
|---|---|---|---|
| A：一時的な登録経路とシークレット | 未検証（条件を満たす可能性あり） | 検証専用 Worker／DO に remote service binding で到達。Google ID、別々の検証キー、検証用セッションを組み合わせ、登録競合・途中失敗・復旧・旧セッション拒否・DO 再起動を確認。試験後キーを削除し、受付機能なしへ戻した | 試作は設計書の browser POST そのものではない。実運用での Origin／CSRF、独立した運営者認証と秘密の保管・復旧、完了記録の環境・対象・日時、users 対応と機能停止手順を検証する必要がある |
| B：受付経路なしの直接操作 | 未検証 | Data Studio で検証 DO に単一 SQL を実行可能。Cloudflare の資料では複数 SQL は別の DO 要求となる | 複数レコードの原子性・一回性・復旧を満たす直接操作手順が未確認。Worker 経由の試作成功を B の直接操作の実証とは扱わない |
| C：常設管理経路 | 未検証 | A と同じ独立試作は認証・トランザクションの技術的要素を示す | 常設の可否は未決。常設可能とする場合の権限、キーの保管・ローテーション・失効、監査、復旧と公開面保護が別途必要 |

## A1〜A7 の証拠と不足

- A1：独立した検証 DO への到達と登録は確認。製品 Directory DO と製品コードは対象外。
- A2：実 Google 認証を伴う試作で競合、再実行拒否、途中失敗ロールバックと再起動後の保持を確認。完了記録は設計が要求する環境・対象 sub・登録日時を網羅せず、要件全体は未確認。
- A3：試験用キーの生成・設定・削除と削除後の拒否、受付なしへの復帰を確認。実運用の安全な保管、提示・喪失時の復旧、必要なローテーションは未検証。
- A4：ローカルの別の模擬 HTTP 試験で Origin・CSRF の欠落／不一致拒否を確認。実 Cloudflare 運用経路と統合して検証していない。
- A5：Google ID トークンの対象証明と検証用キーの照合は別処理。２キーは別値だが同じ操作者プロセスが保持したため、現実の運営者認証・権限分離を実証していない。
- A6：検証専用 Worker・名前空間・インスタンスを実行時応答と Cloudflare 画面で照合。製品環境での操作はしていない。
- A7：実 Google 認証に結びついた独立試作セッションを復旧後と DO 再起動後に拒否し、更新を原子的に切替。製品セッション、実運用の復旧認可、実際の運営者による鍵喪失からの復旧は未検証。

## 次に具体化する実証案

案 A を優先して、登録専用経路を期限付きで有効化し、運営者の Cloudflare 権限と初回用秘密値を本人の Google セッションから分けて検査する。ブラウザーの変更要求には正確な Origin とセッションに結びついた CSRF トークンを要求する。登録・完了記録には環境識別子、対象の検証済み sub に対応する ID、登録日時を持たせて１トランザクションで記録する。完了後に受付を停止し秘密値を除去する。

復旧は既存アカウントのセッションを要求せず、通常の初期登録とは別の一時的な運営操作、独立した復旧用認可、新アカウントの通常ログインを組み合わせる。旧資格の失効・新資格・監査記録は原子的に切り替え、既存セッションの管理操作で毎回現在の資格を照合する。運営者認証の具体的な主体と鍵の保管・紛失時の手順は未確定であり、実装可能性・非干渉・実際の復旧を検証する前に採用確定しない。

この案の実装・検証は独立試作の範囲に限る。製品の変更、本番環境へのアクセス、main 統合、本番デプロイは含まない。常設経路を選ぶ場合はユーザーが別途判断する。

参考： [Cloudflare Data Studio](https://developers.cloudflare.com/durable-objects/observability/data-studio/)、[DO Storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)、[DO の権限](https://developers.cloudflare.com/workers/authorization/durable-objects/)。

## Muse の中間レビューへの追記（2026-11-02）

- **識別子と事後照合**：これまでの試作の HMAC と削除済みの塩では、後から元の Google sub や旧新の対応を照合できない。したがって設計書の完了・復旧記録の充足を証明していない。ローカルで確認した work 由来のコードでは Cloudflare／Node とも Google の `payload.sub` をそのまま `user.id` に設定している。よって現行の user_id を記録する場合も実質的に sub を記録することであり、匿名化にはならない。次の試作では、検証用の安定した対象 ID を使い、対象環境・日時・旧新対応を認可された内部記録として照合し、ログや GitHub には値を出さない。保持期間と閲覧権限は実運用設計で明確にする。実際の識別子方式を変更する決定ではない。
- **A と C の要素配分**：一時受付・完了後停止は A、別途の運営者管理認可と復旧認可は C に近い要素であり、提案中の次期試作は A と C の組み合わせである。純粋な A が実証済みという意味ではない。常設の C を採用する判断でもなく、方式の採用は条件確認後に開発者が別途判断する。
- **中継エラー**：実 Cloudflare 経由の 403 時に request stream エラーが発生した。要求本文を先に読む変更後、１回の実環境再確認では再現しなかったが、原因は確定していない。A/C の経路に関連する未解決事象として保持する。
- **限定権限の追加観察**：検証 Worker だけの Individual Workers Editor を持つ期限付きアカウント API トークンは有効で対象設定の読取ができた。一方 Wrangler の remote service binding は認証エラーで開始できず、権限不足か機能上の制限かは未確定。Wrangler の実装は対象 Worker に接続する前にアカウント側 edge-preview セッションを取得しており、検証 Worker 単体の権限だけで全手順が成立するとはまだ言えない。権限を拡大せず調査を続ける。
