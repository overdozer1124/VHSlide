## 1. 目的

学校（組織）利用において、生徒が自由に作品を作って共有できてしまう現行の形では、授業運用上の管理が効かない。そこで、授業や作品を入れる管理単位として「スペース」を新設し、役割に応じた権限の段階を設ける。一般利用（学校組織に属さないアカウント）の使い方は変えない。

構成の方針（レビュー推奨）: **既存の作品単位の権限は作り替えず、その外側に「組織・スペースの利用資格」の層を追加する。**

## 2. 用語と権限の4層

- **組織**: 学校などの所属単位。共通ドメインを複数校で使う場合があるため、ドメインだけでは学校を区別せず、学校ごとの組織 ID と所属の対応を持つ
- **スペース**: 授業・クラス単位で作品をまとめる器。作品（シート／ページ群）の上位レイヤーであり、内部の「ページ」とは別概念
- **スーパー管理者**: アプリ全体の運営者（開発者・荒木本人）。アプリ全体の権限を持ち、学校管理者の任命・登録を行う
- **学校管理者**: スーパー管理者に任命された、学校単位の管理者。その学校の教師アカウント・生徒アカウントを設定し、学校としての運用を行う
- **教師**: スペースの作成・運用者（スペース作成権限は別途判定する）
- **生徒・参加者**: 承認されたスペース・作品に参加する利用者。**生徒も作品を作成できる**（Google スライドや Canva と同様。v3.0 で決定）

権限は次の層に分けて扱う（混同しないこと）。

0. **アプリ運営（スーパー管理者）**: 学校管理者の任命・登録など、アプリ全体の管理
1. **組織の役割**: 組織所属、役割（学校管理者／教師／生徒）、スペース作成権限
2. **スペースの管理権限**: そのスペース内に限った管理操作（参加承認、終了、移管など）
3. **作品の編集範囲**: 既存の作品別権限（閲覧のみ／指定範囲だけ編集／すべてのスライドを編集）をそのまま使う

認可の順序: (0) スーパー管理者はアプリ全体の管理操作が可能 → (1) 組織所属・スペースへの参加資格・スペースの状態を確認 → (2) 学校管理者・教師にはその範囲内に限って管理操作を許可 → (3) 生徒には作品別の参加資格と既存の編集範囲を適用。

## 3. 前提の訂正（レビューで確認された現行実装）

設計の土台として、以下を正として扱う。

1. **招待の承認制には例外がある**。未参加者は申請→ホスト承認が原則だが、教師が事前指定したメールアドレスへの共有（事前共有）は、ログイン時に参加権限を取り込む経路がある。「全員が毎回申請承認を受ける」仕組みではない
2. **24時間の期限は参加申請に対するもの**であり、招待 URL 自体の失効期限ではない
3. **「学校用ログイン」は学校所属・教師権限の判定ではない**。現行のログイン種別は OAuth クライアント ID を切り替えるだけで、サーバーは両方の ID を受け入れ、組織所属や教師役割は保存していない。**一般用ログインを選べば学校制限を回避できる、という設計にしてはいけない**。所属判定はサーバーで確認できる方法（署名済み組織情報、登録済み所属など）で行う（第9節・最優先事項）
4. **シート権限の現行の意味**は「対象シートを選び、その中の行・列・ページを指定する」方式であり、将来追加されるページまで含めた「シート全体」の独立した権限項目はない
5. **「担当のみ表示」はデータ秘匿ではない**。現行は接続した参加者に作品の共有データ全体を送り、表示側で制限している。この前提は維持する。**担当外データを端末へ送らない要件は、本計画の範囲に暗黙に含めない**（必要なら別途、明示的に要件化すること）

また現行にスペース・組織管理の仕組みはなく、DB はユーザー、作品、参加者、作品別権限、事前共有先などで構成されている。

| 作品の作成 | ○（アプリ全体の権限） | △（学校管理者という役割だけでは不可。教師として所属する場合は可） | ○ | ○（決定済み。スペース内・許可範囲で作成できる） |
| ページ作成・編集（許可範囲内） | ○ | △（同上） | ○ | ○ |
| スペース外の作品をスペースへ入れる | ○ | ○（自校内） | ○（自スペースの管理者のみ） | × |
| 作品をスペースへ入れる申請 | ○ | ○ | ○ | ○（作品の制作者が行える。実行は管理者の承認による） |
| 許可されたスペースへの参加 | — | — | — | ○（承認制。事前共有の経路を含む） |

補足:

- **スーパー管理者**はアプリ全体の運営者（荒木本人）であり、アプリ全体の権限を持つ。登録は、申請を受けてスーパー管理者が行う形とする（v3.0 で決定）
- **学校管理者は「全作品でホスト相当」ではない**。学校としての管理操作（アカウント設定、作成権限の付与・解除、スペースの再割り当て・終了など）と、作品の作成・本文編集は別の権限として扱う：
  - 学校管理者という役割だけでは、作品作成・本文編集を許可しない
  - 教師としてのスペースへの所属は、スペース作成権限を自動付与しない。作成権限は別途判定する
- **学校所属の判定は登録制を基本とする**（v3.0 の解釈）： 学校管理者が教師・生徒アカウントを設定することで所属が決まる。ドメイン等の自動判定に寄せる場合は別途決定する
- **スペース承認と作品参加は別**。初期案では、スペース承認は外側の条件であり、作品の参加・編集範囲は現行のまま維持する。スペースを承認しただけで、そのスペースの全作品を閲覧できるようにはしない。承認を一度で済ませたい場合は、承認時にどの作品へアクセスを付与するか明示する設計が別途必要
- **一般アカウントの個人利用の維持と、学校スペースへのアクセス許可は分ける**。学校スペースへの参加は、組織所属・承認を条件とする
- **スペース終了後の操作可否は、現在のスペース管理者が設定する**（v3.0 で決定し、v3.5 で表現を整理）： 終了＝一律ロックではなく、管理者が閲覧・編集・書き出し等の可否を設定できる形にする。移管した場合は、移管先の管理者が設定・変更する（元の作成者ではない。作成者記録と管理権限の分離に揃える）
- **共有は個人情報を含まない形を原則とする**（v3.0 の方針）： 作品の共有・書き出しでは、氏名・メールアドレス等の個人情報を含めない作りにする。具体的な対象範囲（付箋の投稿者名、バックアップの共有先メール等）は第8節で整理する
- **スペースの移管【決定済み】**： 教師は移管先を指定して申請し、対象校の学校管理者／スーパー管理者が確定する。確定の際は、移管先が同じ学校の有効な教師であることを確認し、確定までは現在の管理権限を維持する。移管によってスペース作成権限が自動付与されることはない
- **スペース外の作品の取り込み**（v3.0 で決定）： スペース外で作られた作品を後からスペースへ入れる仕組みを認める。ただし、入れる操作を行えるのはそのスペースを管理しているアカウントのみ。作品の制作者は「入れることの申請」を行え、管理者が承認して取り込む流れとする（参加申請と同様の考え方）。この仕組みにより、段階②〜③の過渡期に作られた未所属作品も吸収できる

## 5. 作品所有者の特権の分離（必須）

現行の「ホスト」は役割ではなく、**作品の所有者との一致**で決まっている（サーバーは所有者を無条件にホスト権限とし、クライアントも所有者一致で判定）。このままでは、教師の管理権限を解除しても、作品所有者として管理を続けられる。既存の生徒所有作品を閲覧専用にする場合も同じ問題がある。

したがって:

- 作品の**作成者記録**と**現在の管理権限**を分離する
- 学校作品では「所有者だから常に許可」という抜け道をなくす。`owner` を残す場合も、学校スペース内では第2節の認可順序を優先する
- 引き継ぎでは管理権限だけでなく、作品数・写真容量が所有者単位で管理されている点もあわせて確認する

### 所属解除の扱い（原則）

退職・転校などで組織所属を無効にすることは、「一般利用への切り替え」とは扱わない。

> 学校管理対象の作品には、利用者の現在の所属状態にかかわらず学校側の認可を適用し、所属解除によって個人作品へ自動転換しない。

これにより、所属解除をきっかけに旧所有者の権限が復活する経路を塞ぐ。この原則は、（学校管理対象ではない）一般アカウントの従来利用を維持する方針とは両立する。

### 生徒が作った作品の初期権限

生徒の作品作成を認めるにあたり、現行の「作成者＝ owner ＝ホスト権限」の扱いは学校作品ではそのまま使わない。

- 制作者（生徒）には、その作品の**本文編集に必要な権限**を付与する
- 参加承認・共有範囲の設定などの**管理操作はスペース管理者に残す**（制作者でも管理者にはならない）
- 作成者記録は残すが、第5節のとおり現在の管理権限とは分離する
- **自作作品であっても、生徒には削除権限を与えない【決定済み】**： 生徒は削除を申請し、スペース管理者が実行する。学校管理対象の作品を保全でき、削除後の猶予・通知のルール（第9節）とも整合する。一般アカウントの個人作品は従来どおり（本制限の対象外）

## 6. サーバー側で強制するチェック

制限は画面とサーバーの両方で強制する（ボタンを隠すだけでは不十分）。作成・編集だけでなく、取得、復元、既存接続にも同じ認可方針を適用する。

| 対象操作 | 必要なチェック |
|---|---|
| 教師権限の付与・解除 | スーパー管理者、または対象校の学校管理者であること。学校管理者による他校への操作・スーパー管理者権限の変更は拒否する。自己昇格も拒否 |
| スペース作成 | 組織所属が有効か。現在の作成権限があるか |
| 作品作成・コピー・クラウドへの取り込み | 作成先スペースと組織が一致するか。その場所で作品を作れるか |
| ZIP 復元・版からの復元 | 復元も新しい作品を作る経路である（現行 `/api/restores`）。作成時だけでなく再開・確定時も権限を再確認。持ち込んだ共有設定で権限を拡大しない |
| 招待・参加申請・承認 | 対象スペースを管理できるか。指定アカウントか。有効な申請か。別スペースの申請 ID を受け付けない |
| 一覧・作品・画像・付箋・履歴の取得 | スペースと作品の閲覧資格があるか。URL や作品 ID だけでは許可しない |
| ページ編集・追加・移動・削除 | スペースが編集可能な状態か。変更前後のページが既存の許可範囲内か |
| 共有設定・表示制限・集合の操作 | その作品を管理できる役割か。本文編集の許可と管理操作を混同しない |
| 終了・削除・移管・再開 | 現在の管理資格、対象組織、状態遷移、移管先の資格を確認 |
| WebSocket 接続・継続中の利用 | 接続時と更新時の認可。権限解除・スペース終了時の通知や切断。DB の役割を変えただけで接続済みユーザーが直ちに停止する、とは扱わない |

実装メモ（レビューより）: 現行の Cloudflare 側は共有更新ごとに再認可し編集内容を検査しているため、この仕組みにスペース条件を接続できる。同じ方針を Node 側にも実装し、画面にはサーバーが返す操作資格を反映する形が推奨される。

## 7. データ構造への影響

組織・役割・スペースの認可情報は、作品本文とは別のサーバー管理データにする。**作品の JSON や ZIP から組織管理権限まで復元できてはいけない。**

| 追加・変更候補 | 主な内容 |
|---|---|
| 組織 | 組織 ID、学校判定に使う設定、有効状態 |
| 組織所属 | ユーザー ID、組織 ID、役割、スペース作成権限、有効状態 |
| スペース | 組織 ID、名称、作成者、運用状態 |
| スペース所属 | ユーザー ID、管理者／参加者、承認・解除状態 |
| スペース参加申請 | 申請者、対象スペース、有効期限、承認状態 |
| 作品との関連 | 作品の `space_id`。既存・一般作品を表すため初期値は NULL を許容 |
| 復元処理との関連 | 復元先スペースを保存し、再開・確定時にも検査できる状態 |

- ユーザーの識別には現在の Google の `sub` 由来の ID を使い、メールアドレスを管理権限の主キーにしない
- 既存の本文・行列 ID・編集範囲は再利用し、スペース所属を理由に作品の全ページを作り直す必要はない。ただし DB の移行と認可処理の変更は必要
- 移行時の切り分け: 一般利用の既存作品は従来どおり／学校アカウントの既存作品は決めた移行方針で明示的に分類する／`space_id` が NULL であることを学校制限の恒久的な回避条件にしない

## 8. 個人情報（氏名・メールアドレス等）の扱い

対象は `users` テーブルだけではない。現行では、付箋に投稿者名が保存され、完全バックアップに氏名・共有先メールアドレスが含まれる。保存期間・削除対象は次の単位で整理すること。

- ユーザー情報、参加記録、付箋、履歴、バックアップ
- サーバー上の削除と、利用者が既にダウンロードしたファイルの扱いは別問題として分ける

決めること: 取得項目と利用目的／削除手順（アカウント削除時・申請時）／スーパー管理者・教師が一覧で見られる範囲。

決定済み: スペース削除時の保存期間は最大1か月とし、該当アカウントへ通知して保存（書き出し）を促す（第9節）。

### 「個人情報を含めない」の具体化

面ごとに対象を分けて指定する（現行の完全バックアップには氏名・共有先メールアドレスが含まれている）。

| 面 | 除外する項目（方針） |
|---|---|
| 学校管理者の内部一覧 | 必要最小限に絞る。具体的な表示項目は実装前に確定する |
| 参加者への共有データ | 氏名・メールアドレス等の個人情報を含めない。参加者の識別はスペース内の表示名等で行う |
| JSON（編集用ファイル） | 個人情報を含めない |
| ZIP（完全バックアップ） | 氏名・共有先メールアドレスを除外する。ただし、共有先メールを除外すると**共有設定をそのまま復元する機能に影響する**ため、復元時の扱い（共有設定は復元しない／再設定する）を実装前に確定する |

### 表示名の差し替え【アイデア・提案（未確定）】

参加者の表示に、アカウントに登録された氏名そのものではなく、学校側が事前に用意したデータ（例： 学籍番号、学級の出席番号など）を「表示用データ」として使えるようにする案。**表示は役割で出し分ける**：

- **生徒・参加者側： 表示用データ（番号）のみ表示する**。実名は表示しない
- **教師・管理者側： 誰の作品かが分かる表示にする**（例： 番号＋氏名の併記、または対応が確認できる表示）。評価や指導のために、教師は対応を把握できる必要がある

ねらいと条件：

- 教室の大型提示や画面共有、書き出しに実名が出なくなり、「個人情報を含めない」原則（本節）と一致する
- 適用先： 参加者表示、「行に名前」、付箋の投稿者名、共有データなど、氏名が表示されるすべての面
- **出し分けはサーバー側で行うこと**： 生徒側のクライアントへは氏名データ自体を送らない。画面表示だけ隠す実装では、共有データ経由で氏名が見えてしまう（第3節の「表示制限は秘匿ではない」と同じ落とし穴）。学校スペースの共有データについては、この機能のために氏名を含めない配信が必要になる
- 区別： これは表示層の差し替えであり、アカウント設定の内部処理（学校管理者のアカウント設定など）で必要な登録名とは分ける
- 注意点： 学籍番号と氏名の対応表そのものは個人情報なので、対応データは教師・管理者だけが参照できる形で保持する。表示用データが未設定の生徒の扱い（実名を出さない代替表示にする等）は実装前に決める

区別しておくこと:

- 適用範囲: **学校作品には必須適用**とする。一般利用への適用範囲は実装前に確認する
- 作品本文や写真に、利用者自身が記入・撮影した個人情報まで自動的に除去する仕様ではない（システム側で自動除去はしない）。対象は、システムが保持・付与する識別情報（氏名・メールアドレス・共有先情報など）である

## 9. 決定事項と未決事項

### 決定済み（v3.0〜v3.4）

- 教師のスペース移管は、移管先を指定して申請し、対象校の学校管理者／スーパー管理者が確定する（v3.4 で採用）
- 生徒には自作作品でも削除権限を与えない。削除は申請し、スペース管理者が実行する（v3.4 で採用。一般アカウントの個人作品は対象外）
- スペース外の作品を後からスペースへ入れる仕組みを認める。実行できるのはスペースの管理者のみで、制作者は申請を行える（管理者が承認）。これにより段階②で作られる作品の扱い（過渡期の問題）も同じ仕組みで吸収する
- 権限解除の範囲は **C案**： 作成権限と管理権限を分離し、解除時にどちらを外すか個別に指定できるようにする（2026-10-31 決定）
- 生徒・参加者も作品を作成できる（スペース作成は不可のまま）
- スーパー管理者はアプリ全体の運営者（荒木本人）。学校管理者はスーパー管理者が申請を受けて任命・登録し、学校管理者が自校の教師・生徒アカウントを設定する
- 学校所属は登録制を基本とする（学校管理者のアカウント設定による）
- 共有・書き出しは個人情報を含まない形を原則とする
- スペース終了後の操作可否は、現在のスペース管理者が設定する

### 実装前に確定する詳細（基本方針は確定済み）

- 「個人情報を含めない」の面ごとの具体的な項目と、ZIP 復元時の共有設定の扱い（第8節）
- 学校管理者の内部一覧で表示する項目の範囲（第8節）
- 「最大1か月」が暦月か30日か（起算は削除操作時点として確定済み。第9節・状態の区別）
- 表示名の差し替え案（第8節）の採否と、表示用データが未設定の生徒への代替表示。なおこの案は匿名化ではなく、「実名・メールを参加者へ配信しない設計」として扱う
- 個人情報の利用目的、削除手順（アカウント削除時・申請時）、一覧の閲覧範囲（第8節の残件）
- 一般利用への「個人情報を含めない」適用範囲

### 実装設計で具体化する事項（基本方針の変更ではない）

1. **初代スーパー管理者の登録方法**： 「申請を受けて登録」は学校管理者の任命手順である。荒木本人を最初のスーパー管理者として安全に登録する方法は、これとは別に、段階①で確定する
2. **表示名と共有データの分離**： 実名・メールを参加者へ送らない方針は**必須**、学籍番号などへの差し替え方式は**未確定**、と区別する。教師向けの氏名対応情報は、参加者共通の共有データから分離して保持・配信する設計とする
3. **段階②の暫定作品の扱い**： 段階②で作られた作品は、後からスペースへ取り込めるだけでなく、**取り込み前も学校管理対象であることを保持する**。所属解除や旧所有者権限によって、学校管理から外れる（回避できる）状態にしない

### 既存作品の移行について（決定済み・運用開始前の扱い）

- まだ実運用前であり、**生徒の作品は存在しない**。存在するのは教師が試しに作成しているもののみ。そのため、制度導入時の一括移行は不要
- 教師の試作品で必要なものは、決定済みの取り込みの仕組み（管理者による取り込み／制作者の申請）でスペースへ入れる

### スペース削除時の保存と通知（決定済み）

- スペースを削除した場合も、データの保存期間は**最大1か月**とする
- 削除時には、その旨を該当するアカウントへ通知し、必要に応じて保存（書き出し）を促す
- 保存期間の経過後に完全削除する。具体的な削除対象の範囲（参加記録、付箋、履歴、バックアップ等）は第8節の整理に従う

### 状態の区別: 「終了」と「削除猶予中」

この2つは別の状態であり、操作規則を分ける。

| 状態 | 閲覧・編集 | 書き出し | 備考 |
|---|---|---|---|
| 終了 | 現在のスペース管理者の設定による（第4節） | 管理者の設定による | 通常の運用状態 |
| 削除猶予中（削除後、最大1か月） | **編集は不可**（保全のため、終了時の設定より優先する）。閲覧は、削除時点で閲覧権限を持っていた者に限る | 削除時点で権限を持っていた者が行える（通知は新たな閲覧権限を与えない） | 起算日時は削除操作時点。「最大1か月」が暦月か30日かは実装時に確定する。削除時点の権限は資格の上限であり、その後に所属・閲覧資格を失った人にはアクセスを許可しない（退職・転校後に閲覧できる解釈を残さない） |

注記（失効反映の遅延についての判断記録、2026-10-31）： ライブ配信における資格失効の反映は、失効通知による即時停止を基本とし、通知が届かない場合でも、短い期限つきの配信許可（リース、設計値60秒・許容上限5分）の期限切れにより、失効から最大でリース期間以内に停止する方式とする。すなわち、失効確定後も最大リース期間の間は新規受信があり得ることを、上記の「資格を失った人には許可しない」の実装上の具体化として、開発者が明示的に判断した。削除猶予中の作品の配信も、この対象に含む。詳細は実装設計書の第4.4節に定める。

## 10. 段階実装の切り方

| 段階 | 内容 |
|---|---|
| ① 認証・役割の土台 | 所属の登録制、役割（スーパー管理者／学校管理者／教師／生徒）、学校管理者の任命・登録方法、共通の認可方針を確定 |
| ② 作成制限の先行 | 学校アカウントの新規クラウド作品・復元について、確定した役割制限を UI と両サーバー（Cloudflare／Node）へ実装 |
| ③ スペースへの接続 | スペース、所属・承認、作品との関連を追加し、取得・編集・管理操作を接続 |
| ④ 運用と移行 | 教師の引き継ぎ、終了・削除、必要な教師試作品の取り込みを整え、一般利用の回帰確認を実施 |

注意: ②だけでは「スペース機能の完成」とは扱えない（既存作品から共有を続けられるなら、新規作成制限だけで目的を達成したことにもならない）。実データへ制限を適用する前に、既存作品の扱いと、教師の異動・スペース終了時の最小限の運用手順を揃えること。

検証項目（最低限）:

- 学校ユーザーが一般用ログインを選んでも制限される
- 権限を解除された旧所有者が管理できない
- 復元経由で回避できない
- 一般アカウントの従来操作が変わらない

3層の境界ケース（追加）:

- スペース未承認だが、作品には事前共有されている
- スペース承認済みだが、その作品には参加資格がない
- 所属・管理権限を解除した後も、古い作品参加情報が残っている
- 権限解除前から接続していた WebSocket で操作を続けようとする
