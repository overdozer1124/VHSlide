# 指導書・教科書から VHSlide の授業スライドを作る

**利用者への回答・報告・質問は、すべて日本語で書く。**

入力（指導書・教科書の画像やPDF）から授業の流れを読み取り、生徒への問いとワークシートの入力欄を含む VHSlide の作品JSONを作る。
組み立ては `scripts/build-deck.mjs` が行う。Claude は **授業の設計（レッスン仕様JSON）と図・イラスト** に集中する。

## 動作環境とスキルの場所

このスキルはどこに置いても動く。以下の `$SKILL` は **このSKILL.mdがあるフォルダ** を指す（例：リポジトリ内なら `.claude/skills/vhslide-lesson`、個人用なら `~/.claude/skills/vhslide-lesson`、claude.ai ならアップロードされたスキルのフォルダ）。最初に実際のパスを確かめて置き換える。

| 環境 | ビルド | 検証 |
| --- | --- | --- |
| VHSlide リポジトリのセッション | ○ | 最新版のアプリで読み込み検査＋全ページ撮影 |
| 個人用スキル（Claude Code） | ○ | VHSlide を GitHub から取得できれば同上。できなければ同梱の検査処理 |
| claude.ai のチャット | ○（Node.js が必要） | 同梱の検査処理（VHSlide の読み込み処理を同梱したもの）。撮影は省略 |

- 図の PNG 化は Chromium（Playwright）→ `rsvg-convert` → Python `cairosvg` の順に使えるものを使う。どれもなければキャラクターは同梱の画像（プリセットテーマの色）を使い、SVG の図は使えないので VHSlide のグラフ・表で表す。
- 撮影できない環境では、ビルドの見切れ推定（文字量から文字サイズを自動調整）に頼ることになるので、文章は短めにし、利用者に「VHSlide で開いて表示チェックを確認してください」と伝える。
- **文字サイズのバランス（deck-core 調整済み）**：項目の少ないページで文字が小さく画面の半分に寄る問題への対応として、`points` は行の高さを画面いっぱいに広げ（上限118px）、行の高さに応じて見出し・本文の字を大きくする（最大24/22px）。利用者の常設の好みは「小さくコンパクト」より「大きく画面いっぱいで読みやすい文字」。
- **Chromium が使えない環境（Muse の VM など）での適応**：スキル直下の `.venv-svg`（cairosvg＋Pillow 入りの venv）で装飾背景（WebP）・SVG の図が描画できるよう、`scripts/render.mjs` を適応済み（venv の Python を優先／Chromium が無い場合は cairosvg で PNG 化してから Pillow で WebP・JPEG に変換／cairosvg が真っ黒に塗ってしまう `feTurbulence` 系フィルタ（grain・parch・cracks）の要素は除去。質感のノイズだけが落ちる）。`.venv-svg` は `scripts/setup.mjs --fix` で作り直せる。撮影（check.mjs のスクリーンショット）ができない環境では、代わりに `scripts/preview.py`（近似描画）で全ページを確認する。

## 初回セットアップ（このスキルを受け取った側が、最初に1回だけ）

スキルフォルダ直下に `.setup-done.json` が無ければ、授業を作る前にセットアップを行う。利用者に特別な操作はさせない。進め方はチャットでのやり取りだけにする。

1. **チェック**：`node scripts/setup.mjs` を実行し、結果を利用者に平たい言葉で伝える（何が使えて、何が足りないか）。
2. **不足分の導入は承認制**：ダウンロードやインストールが要る場合は、実行前に「何を・どこへ・どれくらいの大きさか・パソコンやシステムの設定を変えないこと」を説明し、利用者の承認を得てから `node scripts/setup.mjs --fix` を実行する。`--fix` は描画手段（cairosvg）と画像圧縮（Pillow）をスキル内の `.venv-svg` に閉じて入れる（管理者権限不要、システムには触らない）。
3. **Node.js 自体が無い環境**：このスクリプトも動かない。その場合は、公式配布（nodejs.org）のポータブル版（Windows は zip、macOS/Linux は tar）をダウンロードしてよいか承認を得て、スキル内の `.runtime/node` に展開し、以後はその node のフルパスでスクリプトを実行する（システムへのインストールはしない）。Muse の環境では Node.js は最初から入っているので、通常この手順は不要。
4. **試運転と完了報告**：`setup.mjs` は付属サンプルを組み立てて背景が入るかと読み込み検査まで自動で確かめる。成功したら `.setup-done.json` が書かれる。利用者には「使えるようになりました。あとは指導書の画像を貼るだけです」と伝える。失敗した項目は、何ができて何ができないか（例：背景なしでも作れる）を正直に伝える。
5. 環境が会話ごとにリセットされる場所（claude.ai の実行環境など）では、`.setup-done.json` が残らないため、初回に短いセットアップが毎回走ることがある。その場合も手順は同じ。

## 0. 最初に確認すること（設定カードの型で1回にまとめる）

利用者の指定があれば聞かずに従う。指定がない項目は、まず**設定カード**を出して1回で確認する（項目ごとに何度も聞かない）。

**設定カードの型**：資料の読み取り結果と一緒に、次の形で提示する。各項目には初期値（下表の既定＋利用者の保存済みの好み＋教材に合わせたおすすめ）を入れておく。

```
【設定】この内容で作ります
・配置：1行配置（lesson-rows）
・テーマ：pastel
・キャラクター：ひよこ
・背景：入れる（自動）
・挿絵：入れる（3〜6枚）
・範囲：第2時だけ
```

提示と同時に、選択肢は2つだけ付ける：**「この設定で作る」／「設定を変える」**。「設定を変える」が選ばれたら、変えたい項目だけを1つずつ選択式で聞く（全部を聞き直さない）。利用者が言葉で一部だけ指定してきたら、その項目だけ差し替えて、残りは初期値のまま進める。

| 項目 | 選択肢 | 既定 |
| --- | --- | --- |
| 配置（layout） | `lesson-rows`：1行＝1単位時間。左から右へ授業が進み、次の時間は下の行<br>`phase-grid`：導入・展開・まとめを縦に並べる2次元配置（複数時間ならシートを時間ごとに分ける） | `lesson-rows` |
| トーン（theme） | `natural` ナチュラル／`pop` ポップ／`chic` シック／`chalk` 黒板／`wa` 和／`emaki` 絵巻（国語の古文、社会の日本の江戸期以前の歴史に向き、これらの教材では第一にすすめる）／`kanseki` 漢籍（朱漆・金の雷文・竹簡・落款。国語の漢文、中国の古典・歴史に向き、これらの教材では第一にすすめる。漢文に絵巻は日本風で違和感があるので使わない：利用者の指摘 2026-11-24）／`pastel` パステル／`shokutaku` 食卓／`bento` ボックス／`kukkiri` くっきり／`notebook` ノート／`board` コルクボード／`magazine` マガジン／`minimal` ミニマル（見本：examples/themes-preview.png・patterns-preview-*.png）／Claude Design のデザインシステムから作る（[design.md](reference/design.md)） | 教材に合わせておすすめを初期値にする |
| キャラクター | `onigiri`（食・家庭）／`drop`（理科・水）／`book`（国語・汎用）／`sprout`（生活・生き物）／`kokeshi`（和服・伝統文化）／`hiyoko`（成長・幼児）／`ninjin`（食品・栄養）／`heian`（平安の姫：古文・平安時代の教材に向く。古文の単元では `emaki`＋`heian` を第一にすすめる）／`bunjin`（文人：冠をかぶり竹簡を読む子ども。漢文・中国の古典に向く。漢文の単元では `kanseki`＋`bunjin` を第一にすすめる）／`blob`（汎用）／`none` | 教科に合わせて選ぶ |
| 背景 | 入れる（テーマの装飾背景を自動生成）／入れない | 入れる |
| 挿絵 | 入れる（3〜6枚）／少しだけ（1〜2枚）／入れない | 入れる（3〜6枚） |
| 範囲 | 単元が複数時間にわたる場合に「何時間目まで作るか」 | 資料の時間だけ |

**利用者の保存済みの好み（初期値として使う）**：背景＝入れる、挿絵＝入れる（3〜6枚）。テーマ・キャラクター・配置は固定せず、毎回おすすめを初期値にして設定カードで見せる。好みが変わったら、この行と設定カードの初期値を更新する。

## 1. 最新の VHSlide を把握する（機能改善を取り込む）

VHSlide は頻繁に機能が増える。作る前に、その時点の最新版の仕様を確認する。

- `check.mjs` は VHSlide のソース（いまのリポジトリ、`$VHSLIDE_REPO`、または GitHub から取得してキャッシュ）を探し、全ブランチのうち `package.json` の version が最も新しい版を自動で選んで検証する。同時に同梱の検査処理（`scripts/vendor`）もその版に更新する。
- ソースに届く場合は、新しい版の `docs/deck.schema.json`、`src/model.ts`（`Element` 型と `parseDeck`）、`src/releaseHistory.ts` の先頭数件を読み、`build-deck.mjs` が使っていない便利な要素（新しい図形・フォーム・集計表示など）があれば、`custom` スライドで使うか `build-deck.mjs` に種類を追加する。追加した場合は例で動作確認する。
- これまでに確認した新機能と、スキルでの使い方・使えないものは [vhslide-features.md](reference/vhslide-features.md) にまとめてある。新しい版では差分だけ読み、表に追記する。
- 書体（0.101〜）はテーマの `font`・`headingFont` で自動設定される。入力欄は `hideLabel`（見出しを隠す）や、画像・手描き欄の `placeholder`（貼り付け前の案内文）も使える。
- 0.121〜0.134 の新機能：並べ替えの入力欄（`type: "order"`）、見出しを左に置く入力欄（`labelLeft`）、Webアプリの埋め込み（form の `app`）、記述回答の「言葉の分析」（授業コンソール）、自由入力の入力欄（`type: "free"`、0.135〜）。保存上限は1作品25MB。選択肢を縦に並べる（`optionsVertical`、0.149〜。クイズは自動）。思考ツール（0.136〜、ベン図・Yチャート・座標軸・心情曲線など）と「前の自分の回答」（0.144〜）は、ウェビングと同じくJSONから作れない（場所と準備の手順をノートに書く）。
- ウェビングマップ（0.110〜）とグループはJSONから作れない。必要な授業では、場所と代わりの画像・手描き欄を用意し、発表者ノートで授業前の設定手順を案内する。
- ワークシートの入力欄は `responseField`（source: worksheet）で置く。クラウド保存時に作品へ自動登録される（フォームの引き継ぎ、0.85.0以降）。古い版しかない場合は利用者にその旨を伝える。

## 2. 教材を読み、授業を設計する

**最初に [pedagogy.md](reference/pedagogy.md)（授業スライドを設計する考え方）で、誰がどう使う授業か・授業の型・構造（シート・行・リンク）を決め、子供の動線を描いてから** ページを作る。

指導書から次を抜き出す：学習目標、時数（第◯時／全◯時間）、学習の流れ（導入・展開・まとめと分数）、各活動の発問、指導のポイント・留意点、資料（図・表・グラフの数値）、板書例、評価の観点。

### 指導案から作る場合

指導案（Word・PDF・テキスト・画像のいずれでもよい）が添付されたら、指導案を入力として作る。指導案は先生本人の設計なので、流れと発問の正は指導案である。

- **抜き出すもの**：単元名、本時の位置（第◯時／全◯時間）、本時の目標、展開表（時間配分・学習活動・発問・予想される反応・指導上の留意点・支援）、評価規準（観点別）、板書計画、使用する教材・資料。
- **スライドへの対応付け**：
  - 展開表の学習活動 → スライド列。発問のある活動は `question`/`fields` にし、入力欄を付ける。時間配分はフェーズ（導入・展開・まとめ）の目安にする。
  - 評価規準 → ルーブリックの1行目に**そのまま**使う（観点別の規準が無い指導案では、本時の目標から観点を起こし、その旨を報告する。規準を推測で作らない）。
  - 板書計画 → `board` ページにする。無い場合は展開から要点をまとめて板書ページを作り、その旨を伝える。
  - 指導上の留意点・支援・予想される反応 → 各ページの `notes`（発表者ノート）へ入れる。生徒に見せるスライド本文には入れない。
- **優先順位**：流れ・発問・時間配分は指導案に従う。数値や資料の内容は、教科書・指導書が併せて渡されたらそちらで照合する（食い違えば報告して確認する）。指導案に無い発問・活動は勝手に足さない。足した方がよいと思うものは、提案として報告に分けて書く。
- **複数時間の指導案**（単元全体の計画など）では、設定カードの「範囲」で何時間目まで作るか確認する。
- 指導案の表が読み取りにくい場合（結合セル・縦書きなど）は、読み取った展開を箇条書きで提示してから作り始める。

### 自由進度学習（単元内自由進度・複数時間の単元）から作る場合

計画が複数時間の単元で、生徒が自分のペースで学習を進める形式（自由進度学習、マイプラン・タイム、単元内自由進度学習など）の場合は、1時間の授業スライドの作り方をそのまま単元に広げない。**時間ごとに切り分けない**のが原則である。時間で割ると、進度の異なる生徒に合わなくなり、計画・記録・振り返りが時間ごとに分散してしまう。単元を通して生徒が使い続ける**1つのデッキ**を、「生徒の学びの動き」に沿って構成する。

- **抜き出すもの**：単元の目標・目指す児童生徒像、評価規準（観点別）、学習マップ／課題一覧（ミッション名・内容・ヒント（教科書ページ・資料）・場所・形態（一斉／個別））、時間配分と形態（第1時＝一斉のオリエンテーション、最終時＝一斉の確認・振り返りなど）、支援の手だて（掲示物・動画・教具など「困ったときのサポート」）、記録の仕組み（マイプランシート等の計画・振り返り）、チェックテスト等の確認の仕組み、発展課題（パワーアップ）。
- **構成の型**（配置は `phase-grid`、詳細は [spec-format.md](reference/spec-format.md) の「自由進度学習の組み方」）：
  1. **レッスン（シート）は「共通」と教科ごとに分ける**（シートが分かれ、ワークシートも分かれる。教科を1つのシート・1つのワークシートに混ぜない）。`sectionSlides: false`。
  2. **共通シート**：表紙（学習のてびき）、進め方、困ったときの順序、マイプランシート（`form`：時間ごとの計画と振り返り・計画の修正の欄）。
  3. **教科シート**：行＝ミッション。1行目は「学習マップ」（`form`：ミッション名の四角に `link` で各ミッションの最初のページへ飛べるようにし、横に「完了」のチェック欄（ミッションごとに1つの `checkbox` 欄）を並べる）。lesson に `mapButton: {"text": "学習マップへ", "to": "<マップのid>"}` を付け、どのページからもマップに戻れるようにする。パワーアップ（発展）とチェックテストも行として置く。
  4. **ルーブリックは教科ごと**：学習マップの次に見通しとして示し、最後の行で自己評価する（順序の原則は通常の授業と同じ：振り返りの後に自己評価）。
- **ミッションサポートの作り方**：各ミッションの行に「やること」「ヒント（教科書ページ・場所・資料）」「チェックポイント（ここまでできたら次へ進める目安）」の3点をそろえる（`steps` は最大5件、多い場合は分割）。生徒が「今どこにいて、次に何をすればよいか」を自分で判断できることが目的。チェックポイントは単元の目標・評価規準から作り、計画に無い活動・目安を勝手に足さない。
- **進捗の見える化**：学習マップ上の完了チェック（ミッションごとに1つの `checkbox` 欄）が進捗表示を兼ねる。`checkbox` 型は単一の真偽チェック専用で選択肢は持てない。マップ以外で「終えたミッションの一覧チェック」が要る場合だけ `multiple` 型を使う。
- **記録欄は活動に即した見出しにする**：「調べたことの記録（出典も書く）」「文章構成メモ」「きまりの発見メモ」のように、何を記録する欄かが生徒に分かる見出しにする。汎用の「メモ」だけにしない。
- **計画と修正のサイクル**：計画（スタート）→ 実行（ミッションサポート）→ 記録 → 振り返り（修正）→ 計画の見直し、という循環がデッキの構成そのもので見えるようにする。進め方のページには「計画は、ずれたら直してもよい」など、修正を前提にした計画側の文言を入れる。
- 時間配分・形態は各ページの `notes` に残し、生徒の画面ではミッションを時間で区切らない（一斉で行う導入・確認は「みんなで」のミッションとして学習マップに示す）。ただし共通シートのマイプランシートだけは、時間ごとの計画・振り返りの欄を持つ（計画は時間単位で立てるのが実務だからである）。

実践研究から得られた設計の要点（2026-11-16 調査：文部科学省資料・各校の実践報告・自己調整学習の研究に基づく）：

- **表紙は「学習のてびき」にする**：単元名、単元を貫く問い（導入の短い問いかけ＝「ゼロ番」）、単元のゴール、総時間数と標準ペース、学習の流れ一覧、使える教材・場所・動画の一覧を1〜2枚に収める。
- **学習マップには「完了の目安」を必ず添える**：ミッションごとに内容・ヒント（教科書ページ・資料・場所）・チェック（完了の目安）が分かるようにする。必須／選択（発展）を区別し、「ここまで全員」のラインが分かるようにする。目安ペースは「遅れ」ではなく「現在地の確認」の言葉で書く。
- **完了の条件は「終わった」ではなく理解の確認にする**：ミッションごとに「チェックテストで確認できた」「友達に説明できた」「記録が書けた」など、完了の目安を具体的に定義してマップとサポートに明記する。教師チェックは全ミッションに置かず、3〜4ミッションごとの節目（関所）に絞る。
- **困ったときの順序を固定表示する**：`① てびき・学習マップと教科書を見直す → ② ヒント・既習の掲示物を見る → ③ 友達に聞く・相談する → ④ 先生に聞く`。ヒントは段階制（方向→既習事項→ほぼ解答例）とし、解答例は「自分の答えの妥当性を確かめる」用途と分ける。
- **学習前後の考えを残す（OPPシートの考え方）**：スタートに「単元を貫く問いへの今の考え」欄、まとめに「学習後の考え」欄を対で置き、変容が見えるようにする。
- **毎時間の振り返りは「書き足すログ」にする**：`今の状況（順調／まあまあ／やばい：single）＋振り返りログ（日付・今日学んだこと・次にやることを書き足す：text）` の形にする。理由（うまくいった／いかなかった原因）と「次にやること」を書かせるのが自己調整の要点。
- **単元末の振り返りは3項目に固定する**：`できるようになったこと／次にできるようになりたいこと／つながり（学習前と後の違い・新たな気づき）`。内容の振り返りと、学び方（計画の立て方・修正）の振り返りを分ける。
- **計画は「選んで書ける」形にする**：計画欄の placeholder にはミッション番号で書く例を示し、モデル計画は `notes` かヒントに置く。計画欄と修正の記録を上書きで消さない運用（振り返りログに修正を書き足す）を案内する。
- 教師の声かけは `notes` に問い返し型で入れる：「できた？」ではなく「どうしてできた？」「どう進める？」。

設計の原則：

- **問いを中心に組む。** 活動ごとに「生徒への問い（question/fields）→ 解説（cards/flow/points）」の対を作る。問いのページには必ず入力欄を置く。
- **回答形式を多様化する（記述だけにしない）。** 記述（`text`）は「考えを深める場面」（学習課題への回答・話し合いの結論・ふり返り）だけに絞り、それ以外は選択・操作系の形式を優先する。目安：導入の経験確認・予想アンケート → `single`/`multiple`（`public: true` で集計をその場で見せると導入が締まる）／知識の確認 → `quiz`（もっともらしい誤答を混ぜ、正答と解説は `notes` に書く。2択の素早い確認も有効）／観察・作品・ウェビング → `drawing`／完了確認 → `checkbox`。ワークシート全体で記述は半分以下を目安にし、同じ形式が続かないようにする。記述だけのワークシートは生徒の負担が大きく、飽きやすい（2026-11-17、利用者の指摘）。クイズは回答欄そのものが選択肢になる（文章の二重表示にならない）ので、選択肢の文章は短くする。クイズで対象の図（文様・実物・図版など）を見せたい場合は、直前に `figure` で図を示してからクイズにする。また、クイズの直後に関連する解説を置き、学習課題やルーブリックの提示を間に挟んで思考を途切れさせない（課題・ルーブリックは導入の活動が一区切りしてから示す）。
- **JSON では作れない部品は、枠と準備手順で用意する**：思考ツール（ベン図・Y/X/Tチャート・PMI・マトリックス・KWL・座標軸・数直線・感情メーター・心情円）、心情曲線（VHSlide 0.150〜。物語の場面ごとの気持ちを線で表す。登場人物ごとに最大3本。国語の物語文で心情の変化を追う授業に特に向いている）、「前の自分の回答」（VHSlide 0.144〜。前の時間の自分の考えを本人の画面にだけ表示する部品）、ウェビングマップは、JSON では作れない。使う授業では、スライドにその場所（枠）と説明を用意し、`notes` に授業前の準備の手順を書く（例：「授業前に フォーム →『思考ツール』→ 心情曲線で、場面＝…、登場人物＝… を作り、この枠に配置する」「授業前に『前の自分の回答』で第1時の○○を選び、この枠に置く」）。
- 調べ学習・観察・作品紹介など、画像があると伝わりやすい問いには `type: "drawing"`（画像・手描き）の入力欄を置き、説明用の `text` 欄と横に並べる（`share` で幅の比を指定。古い版でも隠れないよう、画像欄の高さは「幅×0.56＋90」以上にする）。ウェビングや図・絵をかく活動にも使える。
- 入力欄は1時間あたり5〜10個程度。選択式（single/multiple）には `reason: true` で理由欄を、全体で共有したいものには `public: true`（集計公開）を付ける。
- 資料の数値（表・グラフ）は教材から正確に写す。読み取りに自信がない数値は報告に明記し、教科書との照合を頼む。
- 実在の人物名・写真は載せない（記事は要約）。教科書の図をそのまま複製せず、数値から作り直す。
- 指導書の「指導のポイント」「留意点」「評価」は各ページの `notes`（発表者ノート）へ入れる。
- **ルーブリックを必ず付ける。** 各時間の `rubric`（観点 × A/B/C の3段階）を、指導書の「評価の観点」「評価規準」から作る。
  - 1行目は指導書の評価規準そのもの（記録に残す評価）。Bを「おおむね満足」＝評価規準の文言、Aは「より具体的・関連付けて・自分の言葉で」など質的に高い姿、Cは「努力を要する」状況とする。
  - 必要に応じて、授業内の活動（資料の読み取り・ふり返りなど）の観点を2〜3行目に加える（形成的評価・自己評価用であることをノートに書く）。
  - 生徒が読んで分かる言葉で、1マス50字程度まで。観点は2〜4個。
  - 導入（学習課題の直後）に `{"kind":"rubric"}` で見通しとして示し、まとめでは**ふり返りの後に** `{"kind":"rubric","selfCheck":"public"}` で観点ごとのA/B/C自己評価欄を置く（順序：課題への回答→ふり返り→ルーブリック自己評価。利用者の決定）。自己評価はワークシートに入り、集計も見られる。
  - **自己評価は、観点に対応する活動・記述がすべて終わってから行う**（順序の原則）。ふり返りの内容が観点の一つに対応する授業では、ふり返り→自己評価の順にしないと、生徒が証拠を書く前にその観点を自己評価することになる。自己評価ページの案内文も「今日書いた内容をもとに」など、実際に書いたもの全部を指す文にする。板書・ワークシート確認のページは自己評価より後でよい。
- 利用者が紙のワークシート（PDF・画像）を渡して「スライドにして」と言ったら、`form` で入力欄を座標配置して1ページに再構成する。A4縦→16:9横では、項目を左・中・右の列や上下の帯に組み替え、見出しは色帯（`band`）、記入欄は入力欄（写真や絵は `drawing`）にする。項目名・順序は原本に合わせ、1つの入力欄の高さは44以上を目安にする。
- **見た目の質感**：各テーマは装飾の背景（グラデーション・質感・模様）、カードの影、アイコンを自動で付ける（[design.md](reference/design.md) の「質感」）。新しいテーマを作るときも `decor` を必ず設定し、図形だけの平らなページにしない。
- **ページの型を混ぜて単調にしない。** 同じ型が3枚続かないようにし、内容に合った型を選ぶ（[spec-format.md](reference/spec-format.md)）。
  - 数値・結論を印象づける → `statement`（大きな数字・ひと言）／2つの違い → `compare`（VS）／順番のある内容 → `steps`／全員参加の確認 → `quiz`（大きな選択肢タイル＋回答欄）
  - 導入・展開・まとめの切り替わりには、場面の区切りページ（`section`）が自動で入る（`sectionSlides: false` で無効）。
  - `question` は「帯」と「キャラクターの吹き出し」、`cards` は「並べる」と「ボックス（大小のタイル）」を自動で交互に使う（`variant` で固定、`variety: false` で無効）。
- **自由進度学習（単元内自由進度・マイプラン型）** の指導案なら、授業の流れを1本に並べず、教科ごとのシートに「学習マップ（各ミッションへのリンクと完了チェック）＋ミッションごとの行」を作り、全ページに「学習マップへ」ボタンを付ける（[spec-format.md](reference/spec-format.md) の「自由進度学習の組み方」）。
- **国語で本文・古文・詩などを読ませるページは縦書き**（`passage`）にする。
- **複数時間の単元は、時間ごとに見分けがつくようにする**（色・キャラクターの色・「第N時」の印。スキルが自動で付ける）。全体の統一感は保つ。
- 1ページの情報量を絞る。文章は1ボックス3行以内を目安にし、長い説明はページを分ける。

## 3. 図とイラストを作る

- **グラフ**：棒・折れ線・円の1系列は VHSlide のネイティブグラフ（`chart`）を使う（編集できる）。男女比較など複数系列や注釈が要る図は SVG を書いて PNG にする。
- VHSlide のグラフは、幅が狭いと「グラフが小さい」と表示チェックで指摘される（目安：棒グラフは1ページ2つまで・幅430以上）。円グラフは凡例が場所をとり円が小さくなるので、2つ以上を比べるときは SVG で描く。
- **SVG の図**：`width`/`height` 属性付きの SVG ファイルを書き、スライドの `image` に `.svg` のパスを指定すれば自動で PNG 化される。フォントは `font-family="IPAPGothic, sans-serif"`。ただし cairosvg で変換する環境（Muse の VM など）では先頭に `"Noto Sans CJK JP"` を足す（`font-family="Noto Sans CJK JP, IPAPGothic, sans-serif"`。IPAPGothic が無い環境では日本語が豆腐になる）。配色はテーマの色に合わせる（[design.md](reference/design.md)）。**大きさの注意**：背景・キャラクターは変換側が軽い画像（WebP）で作るので気にしなくてよいが、自分で描く SVG の図だけは、本当に必要なページに、単純な形と少ない色で描く。長い単元は時間ごとに作品を分けてもよい。
- **キャラクター**：`scripts/mascot.mjs` の図形キャラクターを自動で配置する（問い＝?、解説＝!、表紙＝♪）。トーンやキャラクターの希望が言葉で来たら（例：「食事が楽しくなる感じ」）、近いものがなければ `themes.mjs`・`mascot.mjs` に新しく作り、`node scripts/prebuild-mascots.mjs` で同梱画像も作り直す。新しい種類が必要なら同じ 260×260 の流儀で `bodies` に追加する。既存作品のキャラクターの模倣はしない。

### 背景（装飾）は自動で入る。容量は種類分だけ

- テーマの `decor` から、表紙・区切り用／見出し帯つきの本文用／全面レイアウト用の最大3種類の背景画像が生成され、全ページの最下層に敷かれる。仕様側で何もしなくてよい。
- 背景は作品の中で使い回されるので、実質の容量は「種類数 × 1枚分」だけ。ページ数が増えても背景の容量はほぼ増えない（ファイル内ではページごとに複写されるが、クラウド保存時に同じ画像は1回だけアップロードされる）。
- ビルド結果に背景が入っていない（警告が出る）ときは描画手段の問題。環境ごとの事情は「動作環境とスキルの場所」を見る。背景なしで渡すときは、その旨を利用者に伝える。

### 生成イラスト（挿絵）を埋め込む

教科書の写真・図の代わりに、内容に合ったイラストを生成して入れると、問いが具体的にイメージできる。著作権のある写真・図そのものは複製しない。

- **作り方**：環境の画像生成で作る。指定の型は「フラットなベクター風／テーマに合う淡い配色／白背景／教科書の挿絵風／文字・数字・記号は入れない／写実にしない／実在の人物にしない」。発達の順序や段階を表すものは、左から右へ順に並ぶ場面にする。生成後は**必ず目で見て**、順序・対象・数量が教材の内容と合っているか確かめる（合わないものは作り直す）。
- **圧縮してから埋め込む**：生成直後の PNG（数百KB〜）をそのまま使わない。`node scripts/prep-image.mjs 元.png assets/名前.jpg --width 1000` で JPEG 化する（横長で細部が要るものは `--width 1200`、問いページの脇に置く小さいものは `--width 800`）。フラットなイラストなら1枚 20〜60KB になる。元の PNG も `assets/` に残す（差し替え・再圧縮のため）。
- **置き方**：
  - 問いのページ：`question` の `image`（＋`alt`）。左側の枠に `hints`/`table`/`chart`/`image`/`body` のいずれか1つだけが入り、`hints` があるとそちらが優先されるので、イラストを出すなら `hints` は外し、要点は問いの文に含める。`split: 0.48` 前後が目安。
  - 図のページ：`figure` に `image`・`lead`（場面の順序や見どころを1行で）・`source` を付けて、対応する解説ページの直後に置く。`source` には「イラスト：教科書 p.◯ 図◯をもとに作成」と、複製でないことを明記する。
  - 枚数の目安は1時間に3〜6枚。全ページに入れない（問いの導入と、順序・変化を見せたい図のところに絞る）。
- **サイズ設計（渡す前に実測して報告する）**：
  - 上限：作品ファイル全体 25MB、画像1枚 1.5MB が目安。JSON への埋め込み（base64）で元サイズの約1.33倍になる。
  - 目標：背景＋挿絵（1枚 20〜60KB × 3〜6枚）＋キャラクターで、完成ファイル 2MB 以内に収めるのが普通の授業の目安。超えそうなら、まず挿絵の `--width` を下げる／枚数を絞る。写真を使う場合も同じ圧縮手順で1枚 300KB 以下にする。
  - 完成後にファイルサイズと内訳（背景・挿絵の枚数と各サイズ）を数えて報告する。「上限に対してどれだけ余裕があるか」まで伝える。
  - 2MB の目安は、VHSlide が開いた作品を端末へ自動保存する容量（ブラウザの保存領域、約5MB）からも来ている。大きすぎると「端末の保存容量が不足」と出るので、25MB の上限より 2MB の目安を優先する。

## 4. レッスン仕様を書いてビルド

仕様の書き方は [spec-format.md](reference/spec-format.md)、完成例は [examples/nutrition.spec.json](examples/nutrition.spec.json)。作業ファイルはスクラッチパッドに置く。

```bash
node "$SKILL/scripts/build-deck.mjs" lesson.spec.json out/lesson.vhslide.json --layout lesson-rows --theme natural
```

`--layout` `--theme` `--mascot` は仕様内の指定より優先される。テーマは JSON ファイルも渡せる。

## 5. 最新版のアプリで検証する（必須）

```bash
node "$SKILL/scripts/check.mjs" out/lesson.vhslide.json --out out/check
```

- 読み込み検査（その版の `parseDeck`）と、ワークシートが1時間ごとに正しく引き継げるかを確認する。
- アプリで実際にJSONを開き、「表示チェック」（見切れ）の結果を読み、全ページを撮影して `contact-*.png` に一覧化する。
- **一覧画像を必ず目で見て**、文字の見切れ・重なり・余白の偏り・図の読みにくさを直し、再ビルド・再検証する。表示チェックが「見切れなし」になるまで繰り返す。
- 初回は依存パッケージの準備に数分かかる。
- ソースに届かない環境では自動で `validate.mjs`（同梱の検査処理）だけを行う。直接 `node "$SKILL/scripts/validate.mjs" out/lesson.vhslide.json` でもよい。
- 撮影できない環境（Muse の VM など）では、`python3 scripts/preview.py <deck>.vhslide.json --out preview` で各ページの近似描画と一覧シートを作り、それで全ページを確認する。

**納品前セルフレビュー（必須）**：できあがったら、プレビュー（撮影または preview.py）で全ページを目視し、次の観点で改善点を自分で探して直してから渡す。検証の合格は「読み込める」ことの確認にすぎず、品質の確認は目視で行う。

- 子供の動線：迷う場所・戻れない場所・何をすればよいか分からないページがないか。クイズ→解説など、思考が続くページが隣り合っているか（間に課題提示などを挟まない）。
- 入力欄の形と大きさ：**描画欄（drawing）は写真の比率（4:3〜16:10）に近い形にする**。横に平たい欄（幅÷高さが3を超える目安）は、写真を貼ると潰れて見えるため、専用ページにするなどして避ける。記述欄は書く量に見合う高さがあるか。クイズの選択肢が1行に収まる長さになっているか。
- 見た目：文字が小さすぎないか・はみ出しや切れがないか。同じページの型が3枚続いていないか。図・挿絵が内容と合っているか（向きや左右など、内容の正しさに関わる部分は特に）。
- 先生の視点：一斉の場面の見やすさと、評価に必要な記録（ワークシート項目）が残るか。クイズの正答・解説、指導のポイントが `notes` に入っているか。
- 直した点と、残した点（理由つき）は納品報告に書く。

## 6. 渡し方

- 完成JSONと一覧画像を利用者に渡す（Claude Code では `SendUserFile`、claude.ai ではダウンロードできるファイルとして出力）。ファイル名は `<単元名>.vhslide.json`。
- **プレビューを一緒に渡す**：撮影（check.mjs）が使えない環境では `preview.py` の一覧シートを一緒に渡し、近似描画である旨と最終確認は VHSlide 実物である旨を添える。
- 伝えること：構成（行・列と各ページ）、入力欄の一覧、使い方（「ファイル → 開く」→ **クラウドに保存** で入力欄が有効になる）、照合してほしい数値・出典、検証の結果、完成ファイルのサイズと上限（25MB）に対する余裕、背景・挿絵が入っているかどうか、セルフレビューで直した点と残した点（理由つき）。
- 授業での使い方も一言添える：授業コンソールで回答一覧・設問ごとの集計・生徒のスライドを確認できること、「全員を集合 → 発表する」で生徒の画面がスライドだけになり回答欄に入力できること。1ページだけのJSONを追加した場合は、ワークシートの統合でまとめられること。
- 報告で伝えてよいこと（VHSlide 0.143〜0.148）：学びの記録の「回答状況」で、生徒×時間の表で誰がどこまで回答したかが分かる（ワークシートは時間ごとに分けて作る）。思考ツールの結果は生徒（班）ごとのチャートでも見られ、よいチャートを全員の画面に大きく見せられる。カードの言葉の分析もできる。写真の保存容量は作成者ごと500MBに広がり、同じ写真は1回だけ数える。「印刷・PDFで出力」で、板書例やワークシートのページを印刷して掲示・配布にも使える。
- VHSlide のリポジトリで作業している場合に限り、残すときは `lessons/<単元>/` に JSON・仕様・図を置く。アプリのコードを変えていなければ、更新履歴・バージョンは変更しない。

## 7. Gemini 版（Gemini のスキル／Gem）

`gemini/` に、このスキルを Gemini アプリで使うための一式がある。

- **Gemini のスキル（推奨。Gem は廃止予定）**：`node gemini/build-skill.mjs` で `gemini/dist/vhslide-lesson-gemini-skill.zip`（標準：約160KB・6ファイル）と `…-full.zip`（背景の装飾つき：`scripts/backdrops.py` を追加）を作る。中身は `vhslide-lesson/SKILL.md`（`gemini/skill/SKILL.md`）、`references/`、`scripts/build_deck.py`（`deck-core.mjs` の Python 移植。テーマの色・アイコン・キャラクターの設計図（SVG）を中に持ち、キャラクターは実行時に Pillow で描く）。Gemini は大きいスキル（数百KB以上）、ファイル数が多いスキル、極端に長い行や長い説明文のあるスキルを保存できないため、小さく保つ。Gemini はコード実行で `build_deck.py` を動かし、.vhslide.json を渡す。
- **Muse（スペース／チャット）＋変換ページ**：`node gemini/build-muse-pack.mjs` で `gemini/dist/vhslide-lesson-muse.zip`（スペースを作らせる指示・チャット用の指示・変換ページ・はじめに）。先生は指導書の画像を送って「授業スライドを作って」と言うだけ。Muse は配置・トーン・キャラクターを1回聞いてから、このスキルと同じ設計の決まりでレッスン仕様JSONを仕上げ、JSON は変換ページで .vhslide.json にする（Gemini 向けに作った数値の検証手順は入れない）。指示の中身は Canvas 用と同じ資料（`dist/shared/`）から作る。
- **Canvas のアプリ＋変換ページ**：`node gemini/build-gem-pack.mjs && node gemini/build-canvas-prompt.mjs` で `gemini/dist/Canvasへの指示.txt` を作る。先生がこれを Gemini の Canvas に貼ると、画像を貼るだけでレッスン仕様JSONを作るアプリ（中から Gemini を呼ぶ）ができる。JSON は変換ページで .vhslide.json にする。Gemini のスキルは同梱のスクリプトを実行できないため、ファイルまでは作れない。
- **Gem＋変換ページ**：`node gemini/build-gem-pack.mjs` で `gemini/dist/vhslide-lesson-gemini.zip`。Gem がレッスン仕様JSONを書き、先生がブラウザーで開く変換ページ（`gemini/converter`、`deck-core.mjs` を共有）で変換する。コードを実行できないときの代わりにも使える。
- **`deck-core.mjs` を変えたら、`gemini/skill/scripts/build_deck.py` にも同じ変更を入れる。** 確認は、同じ仕様を両方で組み立てて、UUID と画像データを除いた JSON が一致すること（`examples/` と `lessons/` の仕様で）。
- テーマ・キャラクター・装飾・ページの型・仕様の書き方を変えたら、両方の zip を作り直して先生に渡す。Gemini 用の手順は `gemini/skill/SKILL.md`・`gemini/gem-instructions.md` にあり、このSKILL.mdの「設計の原則」を変えたらそちらにも反映する。
